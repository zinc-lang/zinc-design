# メモリ管理

## ARC ポインタ

zinc は参照カウントを核心的なメモリ管理戦略として選んだ。ARC は automatic reference counting を表す。この automatic の意味は、参照カウントの加減操作をするとき、コンパイラが原子命令か非原子命令かを自動で選ぶことである。

ヒープ上に割り当てられた各メモリブロックは、強参照と弱参照の二つの参照カウント値を携える。
強参照カウントが 0 に下がったとき：
* 弱参照の値が 0 でなければ、このメモリのデストラクタは呼ばれるが、このメモリは解放されない。弱参照の値も 0 に下がってから、このメモリを解放する。
* 弱参照の値が 0 であれば、デストラクタを呼び、このメモリを直接解放する。

参照カウントポインタは最もよく使うポインタ型であるため、zinc は最も簡潔なポインタ構文を ARC ポインタの意味論に対応させた。`*T` 型は、`T` 型を指す ARC 参照カウントポインタ型を表す。

弱参照ポインタ型は `*weak T` で表す。`T` 型を指す弱参照ポインタは、`T` 型のメンバ変数・メンバ関数にアクセスできず、参照外しもできない。
弱参照ポインタは `std::ptr::upgrade` 関数によって強参照ポインタ `*T` に変換して初めて、`T` のメンバ変数・メンバ関数にアクセスできる。

オブジェクトをヒープ上に割り当てるには `box` キーワードを使う。`box <expr>` 式について、`<expr>` の型が `T` なら、`box <expr>` 式の型は `*T` である。
`box` 式でメモリ割り当てが失敗すると、直接 panic する。
ユーザが本当にメモリ割り当てエラーを手動で処理する必要があるなら、自分で `std::alloc::try_box` 関数を呼び、戻り値を判定してメモリ割り当てが成功したかを確定できる。
メモリ割り当て失敗を手動で処理する必要がある場面は、実は zinc の使用にあまり適さない。結局のところ標準ライブラリ全体の実装は、OOM のときに直接 panic する。応用層だけでメモリ割り当ての成否を判定するのでは足りない。


例は次のとおり：
```rust
let x: MyObj = MyObj::new();  // MyObj::new() が返すのが MyObj 型なら
let y: *MyObj = box MyObj::new(); // box MyObj::new() が返すのは *MyObj 型である

let z = y; // z と y は同じ MyObj 型のオブジェクトを指す
```

静的サイズ型（sized 型を指す。当面 unsized 型は議論しない）を指す ARC ポインタのメモリレイアウトは次のようになる。毎回の動的メモリ割り当てでは、先に `malloc(sizeof(UInt) + sizeof(MyObj))` し、それからポインタをオブジェクトの先頭アドレスへオフセットする。
ARC ポインタでメンバ変数にアクセスするときに必要なオフセット量は、そのメンバのオブジェクト先頭アドレスに対するオフセット量である。
```
                ┌──────────────────────┐
                │ strong_count: UShort │
                │ weak_count: UShort   │
ptr: *MyObj  →  │──────────────────────│
                │ field1               │
                │ ......               │
                └──────────────────────┘
```

環状参照が現れた場合、環上に弱参照ポインタが一つあれば、その環は正常に回収されリークは起きない。しかしいつ弱参照ポインタを使うかは、プログラマ自身が指定する必要がある。

zinc には Rust の ownership 概念もなく、`Box<T>` 意味論に似た型もなく、move-only の「所有権型」もない。

**注意**：`*mut T` 型はない。束縛した変数自体が mut であるかどうかにかかわらず、`*T` 型はそのメンバに対して常に変更権限を持つ。

例：

```rust
struct S { m: i32, n: i32 }
fn main() {
    let p1: *S = box { .m = 1, .n = 2 }:S ;
    p1.m += 10; // OK。たとえ p1 という変数束縛が mut 修飾でなくても、メンバ変数を変更する権限はある

    p1 = box { .m = 10, .n = 20 }:S; // 誤り。p1 という変数束縛に mut 修飾がなく、直接代入できない
}
```

## 値意味論と参照意味論

[値意味論と参照意味論](https://isocpp.org/wiki/faq/value-vs-ref-semantics#val-vs-ref-semantics) の紹介：
1. 値意味論とは、コピーするときに値を複製し、新しい変数と古い変数の間に何の関係もないことを意味する。いずれか一方への変更は、もう一方の変数には現れない。
2. 参照意味論とは、コピーするときにポインタをコピーし、新しい変数と古い変数がデータを共有し、この共有データへの変更が両方の変数に同時に影響することを意味する。

判定基準は、次の疑似コードの論理を使う：
```rust
let mut y: T = x;
modify(&mut y); // y を変更する
print(x);
print(y);
// y への変更がどのようにしても x に影響しないなら、型 T は値意味論の型だと言える。さもなければ、型 T は参照意味論の型である。
```

zinc はユーザが型を定義するとき、それを「値意味論」の型として設計することを奨励する。

値意味論として定義された型 `S` があれば、それに対応する `*S` 型は参照意味論であり、使用側は場面に応じて `S` または `*S` 型を気軽に選べる。
一方、型定義時に直接「参照意味論」型として設計すると、それに対応する「値意味論」型を得るのは難しく、使用者にとって不便である。

## 借用

なぜ借用ポインタが必要なのか？

ARC/WEAK ポインタだけだと、表現能力が足りないからである。
`*T` 型は常に「動的割り当てオブジェクト」の頭部だけを指せる。動的割り当てオブジェクトは必ず参照カウント値を携える。参照カウント値を操作する必要があり、参照カウント値がそれが指すアドレスの固定オフセットにあることを保証する必要があるからである。
オブジェクトの途中を指すポインタが必要なら、`*T` 型のポインタは使えない。

この言語中のすべての安全なポインタがオブジェクト頭部だけを指せるなら、オブジェクトのメモリレイアウトはコンパクトにできない。この設計は値型の発揮に不利である。

オブジェクトの途中部分のアドレスを取り、新しいポインタを得ることを許すなら、次の図のようになる：
```
                ┌───────────────────┐
                │ strong_count: u32 │
                │ weak_count: u32   │
ptr: *MyObj  →  │───────────────────│
                │ field1: i32       │
                │ field2: MyStruct  │ ← borrow_ptr: &MyStruct
                └───────────────────┘
```

するとこの borrow_ptr ポインタは必ず次の特徴を持つ：
1. 実行時に十分な情報がなく、それが指すこのオブジェクト自体が携える参照カウントを見つけられない
2. 実行時に、それが指すこのオブジェクトのライフタイムを能動的に制御する能力がない

したがって、借用ポインタのライフタイムはコンパイル時の静的検査が必ず必要であり、借用ポインタが被借用オブジェクトより短命であることを保証しなければ、ダングリングポインタ問題が起きる。

したがって zinc も rust の借用ポインタとライフタイム引数を残した。借用ポインタは「アドレス取得」操作によってのみ得られ、コンパイラはコンパイル時に借用ポインタの生存範囲を追跡する。
異なる読み書き権限を区別するため、借用ポインタは二種類に分かれ、読み書き可能な `&mut T` 型と読み取り専用の `&T` 型である。対応する演算子式も `&mut <expr>` と `&<expr>` である。

借用ポインタは ARC ポインタの表現能力への良い補完である：
1. ARC ポインタはヒープ上に動的割り当てされたオブジェクトだけを指せる。借用ポインタはヒープ上のオブジェクトもスタック上のオブジェクトも指せる。
2. ARC ポインタはヒープ上に動的割り当てされたオブジェクトの頭部だけを指せ、ポインタ算術演算をサポートしない。借用ポインタはオブジェクトの頭部または途中を指せ、メンバ変数への借用操作によってポインタオフセットを実現できる。
3. `*T` 型はコピー・引数渡しのとき、常に参照カウントの増減が必要で、余分な性能オーバーヘッドがある。借用ポインタの代入、引数渡し、返却は参照カウント値を操作する必要がない。借用ポインタを合理的に使えば、冗長な参照カウント増減演算を減らす助けになる。

zinc と rust の借用ポインタの同じところは：
* いずれもライフタイム検査がある。すなわちコンパイラはコンパイル時に検査し、借用ポインタ自体が被借用オブジェクトより短命であることを保証する。
* いずれも読み書き権限検査がある。`&T` 型借用は読み権限だけがあり書き権限がなく、`&mut T` 型借用は読み書き権限がある。

zinc と rust の借用ポインタの異なるところは：
* 可変性規則が異なる。zinc では、ARC ポインタ型 `*T` は、この変数束縛自体が可変かどうかにかかわらず、常にこの変数を通して `&T` と `&mut T` の二種類の借用を得られる。
* zinc には「所有権型」および「借用検査規則」がない。読み書き可能借用は排他的ではない。意味論規則はずっと緩い。


### 例一：借用がスタック上のアドレスを指す
```rust
struct S { m: Int, n: Int }
fn main() {
  // 一時変数、リテラルを直接指すことを許す。このときコンパイラは匿名の局所変数を自動生成し、借用ポインタにそれを指させる。
  let mut p2: &Int = &1;

  {
    let x1 = { .m = 1, .n = 2 }: S;
    let p1 = &mut x1; // コンパイルエラー。読み取り専用変数 x1 に対して読み書き可能借用を取れない
    p2 = &x1.m; 
  }
  print(p2); // コンパイルエラー。x1 は p2 より短命である

  let mut x2 = { .m = 3, .n = 3 }: S;
  let p3 = &mut x2; // 正しい
  let p4 = &x2.n; // 正しい
  p3.m += 1;    // 正しい。p3 には書き権限がある
  println(p4); // 正しい。p3 と p4 が同時に存在しても問題なく、p3 に排他性はない
}
```

### 例二：借用がヒープ上のアドレスを指す

zinc コードの例は次のとおり：

```rust
fn main() {
  let mut b: *Int = box 1_i;

  let p1: &Int = &*b; // 許される。ヒープ上のアドレスを指す
  let p2: &mut Int = &mut *b; // 許される。ヒープ上のアドレスを指す

  // p1/p2 は同時に存在できる。mut 型借用に排他性はない
  println(f"$(p1)");
  *p2 += 1;
  println(f"$(p2)"); 

  b = box 10_i; // b を再代入する

  // p1/p2/b の読み書きはいずれも問題なく、p1/p2 は無効にならない
  println(f"$(p1)");
  *p2 += 1;
  println(f"$(p2)"); 
  println(f"$(b)");
}
```
上記のコード例を Rust で書き、`*Int` を `Box<i32>` に変えると、コンパイルエラーが起きる。Rust の可変借用は排他的であり、他の借用と同時に存在できないからである。しかし zinc はコンパイルが通り、メモリ安全問題もない。
理由は、zinc では ARC ポインタを通してメンバ変数の借用を取る場面で、コンパイラが一律に余分な一時変数を生成して b をコピーし、参照カウント値が +1 になることを保証してから、メンバ変数の借用を取るからである。この一時変数は現在の block が終わるときに解放され、このとき参照カウントは自動で 1 減る。
したがって後ろの b への代入は、もともと指していたメモリの即時解放を引き起こさず、p1/p2 は関数が終わるまで有効であり、元のそのメモリが解放される。

次は多層 ARC ポインタの場面である：
```rust
struct Obj { p: *Int } // zinc には move セマンティクスのポインタ型がなく、* ポインタしか使えない。

fn main() {
  let mut o: *Obj = box { .p = box 1_i }:Obj;
  let q: &mut Int = &mut *o.p; // このとき p というポインタを一時的に複製するのであり、o を複製するのではない
  *q = 2; // q には変更権限がある

  // ARC ポインタを通して借用ポインタを作る
  let r: &mut Obj = &mut *o;
  r.p = box 10_i; // 許される。コンパイルエラーもなく、ダングリングポインタもない。

  o = box { .p = box 100_i }:Obj; // 許される。コンパイルエラーもなく、ダングリングポインタもない。

  println(*q); // q は依然として元の値を指し、印字結果は 2
  println(*r.p); // r.p は新しい値 100 を指す
}
```

要するに、Arc ポインタを通して新しい借用ポインタを作るとき、zinc が借用ポインタがダングリングポインタになるのを避ける方法は、保護的に参照カウントを増やし、メモリ解放を遅延することである。
コンパイラは一つの関数内部で局所静的解析をするだけで、メモリ安全を保証するのに十分である。

実行性能の観点から議論すると：この設計は確かに一部の実行性能を犠牲にするが、影響はそれほど大きくないはずである。

1. 前述は意味論の観点からコードの期待される振る舞いを説明しただけであり、最適化の観点から具体的な命令を記述したものではない。

   最適化の観点から見ると、新しい借用ポインタを作るたびに一律に参照カウントを増やす必要はない。コンパイラがコンパイル時に、借用ポインタが指すオブジェクトがこの区間内で必ず生存することを保証できないときだけ、保険として自動で参照カウントを増やし、メモリの早すぎる解放を避ける。
   多くの場面でコンパイラは十分な情報を持ち、これらの余分な参照カウント増減操作を直接最適化して消せる。

2. Rust に比べ、一部のヒープ上の動的割り当てオブジェクトの解放時機が遅延される。

   メモリ安全を保証するという観点から見ると、実はマークスイープ式の GC も似た発想である：まだポインタがこのメモリを指している限り、ランタイムはこのメモリを解放しないことを保証する。
   違いは、マークスイープ式の GC は循環参照を処理でき、ARC は処理できないことだけである。
   注意してほしい。関数内部で作った借用ポインタは、本関数より長く生きることは決してない。したがって、あるメモリが借用ポインタの存在によって解放遅延されているなら、その借用ポインタがあるコードブロックが終わったあと、そのメモリも解放でき、遅延は長くない。

3. 借用ポインタを合理的に利用しさえすれば、すべての場所で ARC を使う設計に比べ、多くの場合は参照カウントの発生頻度を減らせる。
   1. 一つの借用ポインタは、代入、引数渡し、返却で使うとき、参照カウントを変更する必要がない
   2. 一つの借用ポインタを通してそのメンバの借用ポインタを得るとき、メンバ変数が ARC ポインタ型でなければ、参照カウントを変更する必要がない
   3. ARC ポインタ型のメンバ変数の借用を取る場合でも、最適化によって一部の冗長な参照カウント変更を削除できる。この最適化は、コンパイラがある ARC ポインタが指すオブジェクトがあるライフタイム区間内で確実に解放されるリスクがないことを知るのに十分な情報があるかどうかに依存する。


使いやすさの観点から議論すると：この設計は Rust の大幅な簡略化である。**borrow checker を取り除き、&mut 型借用が排他的であるという制限がなくなった**。型の層で、move only 型を取り除いた。


メモリレイアウトの観点から議論すると：ARC と借用ポインタの組み合わせは、プログラマのメモリレイアウト制御力を保証できる。
1. すべての型について、そのメモリレイアウトは決定的であり、コンパイラは隠れたメンバを暗黙に挿入しない。
2. `box` キーワードでヒープ上にメモリを割り当てることを明確に使うときだけ、動的割り当てメモリの頭部に参照カウントを記録し、このとき余分な参照カウントメモリオーバーヘッドがある。スタック上で使う局所変数には、余分な参照カウントメモリオーバーヘッドはない。
3. 任意の型をメンバとして使うとき、いずれも直接平坦に並び、余分な参照カウントメモリオーバーヘッドはない。プログラマがメンバ変数を ARC 型と指定しない限り、コンパイラは暗黙に box 操作と参照カウント値を挿入しない。

## もう少し複雑な借用取得操作

Zinc のコンテナ型、たとえば `Vec<T>` も要素への借用取得操作をサポートする。例は次のとおり：

```rust
fn main() {
    let mut vec = (type Vec<Int>)::from(&[1i,2i,3i,4i] as Slice<Int>);
    let p: &Int = vec.index(1); // 今後演算子オーバーロード機能を追加すれば、&vec[1] と書ける
    vec.push(5); // ここで vec の拡張が起きうる
    println(*p); // どのように p が合法であることを保証するか？
}
```

ここでの戦略は依然として、借用 `p: &Int` を作るときに下層配列の参照カウントを増やし、`p` が死ぬときに参照カウントを減らすことである。

問題は：`p` が一つの借用であるなら、コンパイラはどうやって、この借用変数が死ぬときに参照カウント操作をすべきこと、どのアドレスで参照カウント操作をすべきことを知るのか？

答：上のコードがコンパイルできるのは、コンパイラと標準ライブラリの共同の協力による。ここでの借用取得操作 `vec.index(1)` が実際に返すのは、原生の借用型 `&Int` ではなく、追加データを携えた構造体であり、「借用型に似たスマートポインタ型」である。
それからこの一時変数を通してさらに `deref` 操作をし、最終的な `p: &Int` 借用ポインタを得る。

```rust
// この型は Deref trait を実装しており、コンパイラが挿入する自動参照外しによって &T 型を得られ、それから &T 型で要素にアクセスする。
// この型は Drop trait を実装しており、デストラクタ時に対応する配列の参照カウントを減らせる
struct ItemRef<'a, T> {
    ptr: *Shared<T>, // 配列頭部を指す
    item: &'a T, // 本当の借用
}
```

上記のコードはコンパイラ脱糖のあと、実際には次の意味である：

```rust
fn main() {
    let mut vec = (type Vec<Int>)::from(&[1i,2i,3i,4i] as Slice<Int>);
    let _temp: ItemRef<Int> = vec.index(1); // コンパイラが暗黙に追加する局所変数。これは「ファット借用ポインタ」である
    let p: &Int = _temp.deref(); // コンパイラが暗黙に追加する「自動参照外し」操作
    // 注意：index の戻り値を局所変数に束縛しなければ、この _temp は index 文が終わったあとすぐにデストラクタされるべきであり、文ブロックが終わってからではない。

    vec.push(5); // 拡張時に copy-on-write 条件が成立し、新しい空間を割り当てるが、古い空間の参照カウントは 0 より大きく、解放されず、p は依然として合法である
    println(*p);
    // コンパイラが暗黙に _temp 変数をデストラクタし、このとき古い空間の参照カウントが 0 になり、元の配列中の内容を解放する
}
```

注：「自動参照外し」の規則は、パターンマッチ、引数渡し、返却の場面で、`T: Deref<U>` が存在するなら、`T` は `deref` メンバ関数の自動呼び出しによって `U` 型に変換できる、ということである。

上記の目標に達するため、zinc 標準ライブラリ中の Index trait は次のように定義されている：
```
pub trait Index<Idx>
{
    type Output<'a>;

    fn index<'s>(&'s self, index: Idx) -> Self::Output<'s>;
}
```

注意してほしい。index 関数の戻り型は、もはや固定の原生借用型 `&Item` ではなく、`&Item` とその他のデータを一緒にカプセル化した構造体型 `struct ItemRef<'a, Item>` である。
これをカスタムスマートポインタ型と見なせ、「原生借用型に追加のメタデータを携えさせた」型であり、「ファット借用ポインタ」の一種と見なせる。
したがってこの `Output` 関連型も、一種の型コンストラクタ、すなわち Rust の generic associated type として定義しなければならない。
このポインタには具体要素への借用だけでなく、内部配列頭部へのポインタも含まれ、かつこのファットポインタはデストラクタを持ち、実行時に参照カウントの値を正しく維持するのに十分な情報がある。

意味解析の観点からだけ見ると、こうするのは性能への影響が大きいように見える。しかしここで使う `index` `deref` `drop` といういくつかの重要な関数をすべてインライン化することを考えれば、性能最適化段階で余分な参照カウント操作を完全に削除できる：
1. main 関数中で push などの変更関数を呼んだことがなく、vec の可変借用を取ったことがなければ、コンパイラはこのメモリに解放リスクがないことを知る十分な情報を持ち、すべての余分な参照カウント加減操作と余分な局所変数を完全に削除できる；
2. main 関数中で vec の可変借用を取って他の関数に渡して使うことがあれば、コンパイラは vec が変更されうるかどうかを確定できず、このとき保護的な参照カウント操作は不可欠であり、これは性能の無駄ではない。

## zinc は古典的なイテレータ無効化問題をどのように解決するか

Rust のメモリ安全特性を解説するとき、次は古典的な例である：

```rust
///// Rust code
fn main() {
    let mut vec: Vec<i32> = Vec::from(&[1i,2i,3i]);
    for ref _i in &vec {
        vec.push(4);
    }
}
```

Rust はこの例をコンパイルエラーにする。`vec.iter()` が `vec` に対する読み取り専用借用を作り、それをイテレータの中に保存する一方、`vec.push` は `vec` に対する読み書き可能借用を作る必要があるからである。
Rust の借用検査規則によれば、この二つは衝突するため、コンパイラはエラーを出し、イテレータ無効化問題を有効に防ぎ、C++ でよく見られる一種の未定義動作を避ける。これは Rust が称賛に値する利点である。

Zinc は別の仕方で安全を保証する。次は Zinc の対応するコードであり、ソースコードの層ではよく似て見えるが、実際の実行効果は Rust と大きく異なる：

```rust
fn main() {
    let mut vec: Vec<Int> = (type Vec<Int>)::from(&[1i,2i,3i,4i] as Slice<Int>);
    for ref _i in vec {
        vec.push(4);
    }
}
```

1. zinc には「所有権型」がないため、`Vec<T>` は move セマンティクスではなく copy セマンティクスである。自由に `let vec2 = vec;` でき、しかも引き続き `vec` 変数を使える。
2. `Vec<T>` が copy セマンティクスであることは、コピー実行時にすぐにすべてのメンバをコピーすることを意味せず、copy-on-write 最適化を実装している。
`Vec<T>` をコピーするときは浅いコピーであり、内部のヒープ上に割り当てられた配列の参照カウントを 1 増やすだけで、要素内容は本当にはコピーされない。
3. 深いコピーは `Vec<T>` 変数の変更時に起きる。変更時に内部配列の参照カウントが 1 より大きいとわかれば、すべての要素をコピーしてから変更する。
4. 上例では、イテレータを作るときに内部配列の参照カウントを 1 増やす。反復中に `vec` への書き操作がなければ、深いコピーは決して起きない。
反復中に `vec.push` が起きれば、このとき深いコピーを起こす必要があるとわかり、`vec` 内部に新しい配列が作られ、末尾に 4 が加えられる。
5. しかしイテレータが指す配列は変化しておらず、解放も変更もされておらず、反復は続行される。イテレータと `vec` はすでに完全に異なる二つの配列を指しているため、未定義動作は一切ない。
6. for ループの実行が終わったあと、イテレータのライフタイムが終わり、デストラクタ時に元の配列の参照カウントを 1 減らし、このとき初めて元の配列のデストラクタと解放が起きる。

したがって zinc も同じく「未定義動作」を避け、「メモリ不安全」を導入していないが、一定の性能コストを払っており、push 操作の実行時に元の `Vec<T>` 型が暗黙に一度深いコピーをする。
このコストは受け入れられる。C++ のように未定義動作を持ちたくもなく、Rust のように過度に厳しいコンパイル時検査を持ちたくもなく、「安全」と「使いやすさ」を保証したうえで、実行性能の損失はすでに払う必要のある最小のコストである。
ユーザがこの深いコピーを節約したいなら、ループ過程で元の vec を変更しないよう、自分で注意する必要がある。

Rust にとって、メモリ安全とスレッド安全は **設計目標** である。「可変と共有の排他原則」（alias XOR mutation principle）は目標へ至る **理論的基礎** である。
所有権（ownership）と借用検査器（borrow checker）は **実現手段** である。Zinc は書き時コピー（copy-on-write）技術を使って同じ目標を実現することを選び、行き着く先は同じである。
あるいは別の角度で言えば、Zinc のこの設計は、コンパイル段階の「可変と共有の排他」（alias XOR mutation）静的検査を、実行段階の保証に変えたものである。
copy-on-write は本質的に、メモリ変更時にこのメモリに alias が一つだけあることを保証しており、ownership + borrow checker と同じ目標を異なる手段で実現している。詳細な比較は次のとおり：

* Rust のコンパイル時 ownership + borrow checker 検査は、コンパイル時に、オブジェクトに唯一の mutable alias しかないことを保証する。ただし複数の immutable alias は同時に存在できる。

  alias XOR mutation 原則に違反すれば、コンパイルエラーになる。

* Rust の `RefCell<T>` は `borrow` `borrow_mut` メンバ関数を通して使う。実行時に、オブジェクトに唯一の mutable alias しかないことを保証するが、複数の immutable alias は同時に存在できる。

  alias XOR mutation 原則に違反すれば、実行時に panic し、続行を拒否する。

* Rust の `RwLock<T>` は `read` `write` メンバ関数を通して使う。実行時に、オブジェクトに唯一の mutable alias しかないことを保証するが、複数の immutable alias は同時に存在できる。

  alias XOR mutation 原則に違反すれば、実行時に現在のスレッドをブロックして待ち、条件を満たしてから続行する。`Mutex<T>` も同様であり、一塊のデータに同時に訪問者が一人だけであること（読み書きを問わず）を保証する。

* Zinc の copy-on-write の実現方式は、immutable method の中では ref-count 検査をせず、mutable method の中で ref-count 検査をし、変更時にオブジェクトに唯一の alias しかないことを保証することである。

  alias XOR mutation 原則に違反すれば、このヒープ上に割り当てられたオブジェクトをコピーする。メモリ変更／メモリ解放時に alias が一つだけであることを保証した。

上記のすべての実現技術は、同じ "alias XOR mutation" 原則を満たせ、いずれも「メモリ安全」という目標に到達できる。Rust の設計は「メモリ安全」を実現する選択肢の一つにすぎず、決して唯一の実行可能な設計方案ではない。

## ライフタイム

いわゆるライフタイムとは、ある変数がプログラム実行過程中のどの区間で生きているかを指す。変数のライフタイムはそれが作られたときに始まり、それが破棄されるときに終わる。

### グローバル変数のライフタイム

グローバル変数はプログラム全体の実行過程中ずっと生存するため、そのライフタイムはプログラム開始からプログラム終了までずっと存在する。

### 一時変数のライフタイム

一時変数とは、式によって生成されるが、具体的な名前に束縛されていない変数を指す。

一時変数のライフタイムが終わる時機には二通りある：一つは現在の文が終わるときに終わること、もう一つは現在の文ブロックが終わるときに終わることである。これは、より長いライフタイムの変数に借用されたかどうかによる。

例は次のとおり：
```rust
fn f() -> S { ... }
// S にメンバメソッド method があると仮定する
impl S {
  fn method(&self) -> &S { return self; }
}

fn test() {
  f(); // f() が返すこの変数が一時変数であり、変数名に束縛されていない。この一時変数は文が終わるときにライフタイムが終わる。

  let p1: &S = &f(); // f() が返す一時変数は借用され、しかも借用のライフタイムがこの文を超える。するとこの一時変数のライフタイムは文ブロック終了位置まで延長され、関数が終わるときに一時変数が破棄される。

  let p2: &S = f().method(); // f() が返す一時変数は借用され、しかも借用のライフタイムがこの文を超える。するとこの一時変数のライフタイムは文ブロック終了位置まで延長され、関数が終わるときに一時変数が破棄される。
  // p1 p2 を使う
}
```

### 局所変数のライフタイム

一般の場合、局所変数（関数引数を含む）のライフタイムは、それが作られたときに始まり、現在のコードブロックが終わるときに終わる。

non-lexical-lifetime のようなものはなく、必要もない。Rust がこれを導入したのは、mut borrow 型の排他性のためであり、解析が十分に精密でないと多くの不要なコンパイルエラーを引き起こし、ユーザの表現能力を制限するからである。コンパイル時に mut borrow の排他性を検査するという規則がなければ、コンパイル検査規則を緩める方法を考える必要もない。

* カスタム型については、`Drop trait` を実装でき、この型の変数はライフタイムが終わるときに対応するデストラクタを自動で呼ぶ。
* ARC 型については、ライフタイムが終わるときに、指しているヒープメモリ空間の参照カウントを自動で 1 減らす。
* 借用型については、そのデストラクタは何もしない。

例は次のとおり：
```rust
struct S { m: i32 }
impl Drop for S {
  fn drop(&mut self) {
    println("drop S");
  }
}

fn test() {
  let s1 = { .m = 1 }:S;
  let s2 = s1; // ここでコピーが起きる

  // s1 と s2 は test が終わるときにデストラクタされる
}
```

先に「一般の場合、コードブロックが終わるときに局所変数のライフタイムが終わる」と言ったのは、「特殊な場合」もあるということである。特殊な場合が `move` 式である。

zinc 言語では、move キーワードの後ろに一つの式を続けられ、これを move 式と呼ぶ。このとき移動意味論が起き、コピー意味論ではない。

```rust
fn test() {
  let x = { .m = 1 }:S;
  let y = move x;
  println(x.m); // コンパイルエラー。x のライフタイムはすでに終わっており、後ろで x を使えなくなる
}
```

move するのが ARC ポインタなら、この機能を利用して一部の場面での参照カウント増減操作を減らせる：
```rust
fn f(arg: *S) { }

fn test() {
  let s: *S = box { .m = 1 }:S;
  f(s); // こう呼ぶと、引数渡し時にコピーが起き、参照カウントが 1 増え、f 関数本体末尾で参照カウントが 1 減る。test 関数を抜けるときに参照カウントがさらに 1 減る。
  f(move s); // こう呼ぶと、引数渡し時に参照カウントが自動で 1 増えず、test 関数本体末尾で参照カウントが 1 減ることもないことを保証できる。s のライフタイムは f の関数本体の維持へ移る。
  // s が move されたあと、s を使うとコンパイルエラーになる

  // ...
}
```

変数 `x` のライフタイムを早めに終わらせたいなら、`move x;` 文を使い、move 式の結果をどの変数にも束縛しなければ、この x はその場でデストラクタされ、文ブロック末尾まで待ってデストラクタされるのではない。

要するに、zinc の move セマンティクスは、選択権が「型定義」にはなく、すべての型はもともとコピーも移動もできる。
move セマンティクスを使うかどうかの選択権は「式」にある。zinc が提供するのは move セマンティクスの「式」であり、move セマンティクスの「型」ではない。

`return` 文はデフォルトで move セマンティクスであり、`return expr;` は `return move expr;` に等しく、`move` キーワードを明示する必要はない。

## デストラクタと `Drop`

デストラクタはオブジェクトのメンバ関数である。オブジェクトのライフタイムが終わるとき、コンパイラが自動で命令を挿入してデストラクタを呼ぶ。

デストラクタは次のことをする：
1. その型が実装した `Drop::drop` 関数を呼ぶ。なければ呼ばない
2. メンバ変数の `Drop::drop` 関数を呼ぶ
3. その型が含むすべての Arc ポインタと Weak ポインタ型のメンバ変数について、対応する参照カウントを 1 減らす。ある ARC ポインタが指すオブジェクトの参照カウントが 0 まで下がれば、そのオブジェクトのデストラクタを自動で呼ぶ。

デストラクタは常にコンパイラが自動生成し、ユーザが制御できるのは `Drop::drop` 関数の振る舞いだけであり、それはデストラクタ過程の一部にすぎない。
ある型とそのすべてのメンバに `Drop::drop` 関数も参照カウント型のポインタもなければ、その型のデストラクタは空である。

一般に、ユーザはオブジェクトのデストラクタを能動的に呼ぶべきではない。しかし unsafe コードを書くときは、ユーザが `unsafe fn destruct_in_place` 関数を通してオブジェクトのデストラクタを強制的に呼ぶことを許す。

`Drop::drop` 関数は、ユーザが明示的に呼ぶことは決してできない。

ユーザ定義型が `impl std::mem::Drop` trait する例は次のとおり：

```rust
struct S {
  p: *i32,
  m: String,
}

impl Drop for S {
  fn drop(&mut self) {
    println("S is dropped.")
  }
}
```

注意：カスタム `Drop::drop` 関数は、メンバ変数のデストラクタとメモリ解放を気にする必要はなく、メンバ変数のデストラクタは自動で呼ばれる。
