# 제네릭과 trait

## 제네릭

타입 정의와 함수 정의 모두 제네릭 매개변수를 선언할 수 있습니다.

### 제네릭 타입

사용자 정의 타입은 제네릭 매개변수를 가질 수 있습니다.
제네릭 매개변수는 두 가지입니다: 수명 제네릭 매개변수, 타입 제네릭 매개변수. 제네릭 매개변수 목록에서 배열 순서는 수명 매개변수가 타입 매개변수 앞입니다.

todo: 이후 상수 제네릭 특성을 넣어야 할지 고려해야 하며, swift가 이 특성을 지원하지 않는 이유를 주의해야 합니다

```rust
struct S<'a, T> {
    p: &'a T
}

enum E<T> {
    A(T), B(Int)
}
```

타입 정의는 선택적 `where` 절을 지원합니다. `where` 절은 수명 사이의 생존 관계, 그리고 타입이 trait 제약을 만족하는지의 관계를 표현할 수 있습니다.

제네릭 타입을 쓰려면 제네릭 실인자를 제공해야 합니다.

```rust
fn main() {
    let v = 1;
    let x: S<Int> = S { .p = &v };
}
```

### 제네릭 함수

함수도 제네릭을 지원합니다. 제네릭 타입과 마찬가지로, 제네릭 매개변수도 수명 제네릭 매개변수, 타입 제네릭 매개변수를 지원합니다.
제네릭 함수도 선택적 `where` 절을 지원합니다.

```
fn swap<'a, T>(lhs: &'a mut T, rhs: &'a mut T) {}
```

주의: zinc에서 제네릭 함수 호출 문법이 바뀌어, rust의 turbo fish 문법을 피합니다.

<details>

<summary>turbo fish 문법이 무엇인가</summary>

<div style="border: 1px solid black; padding: 10px;">

Rust의 문법 설계에서, 제네릭 함수 호출이 제네릭 함수 정의와 같은 문법을 그대로 쓰면 문법 중의가 생깁니다. 예시는 다음과 같습니다:
```rust
fn main() {
    let (the, guardian, stands, resolute) = ("the", "Turbofish", "remains", "undefeated");
    let _: (Bool, Bool) = (the<guardian, stands>(resolute)); // 이 줄은 무슨 뜻인가?
}
```

이 중의의 핵심은 작다 연산자와 제네릭 꺾쇠괄호가 같은 기호를 재사용해, 위 줄에 두 가지 이해 방식이 생긴다는 것입니다:
1. 이는 소괄호 안의 제네릭 함수 호출이며, 함수 이름은 `the`, 제네릭 매개변수는 `guardian` `stands`, 함수 매개변수는 `resolute`입니다
2. 이는 원소가 두 개인 tuple입니다. 첫 번째 원소는 `the<guardian`으로 이루어진 비교 연산이고, 두 번째 원소는 `stands>(resolute)`로 이루어진 비교 연산입니다.

이 문법 충돌을 해결하기 위해, Rust는 제네릭 함수를 호출할 때 함수 이름 뒤에 `::`를 붙이도록 요구하므로, 올바른 호출 문법은 다음과 같습니다:
```
the::<guardian, stands>(resolute)
```

이것이 turbo fish 문법입니다. 예: `Vec::<i32>::with_capacity(16)`.

</div>
</details>

<br/>

Rust의 turbo fish 문법은 문법 분석의 중의 문제를 없앴지만, 문법의 불일치를 가져왔고 충분히 아름답지 않습니다.
Zinc는 다른 설계를 채택해, 문법 중의 문제를 피하면서 문법의 일관성도 유지합니다.

1. fully-qualified-call-syntax에 제네릭 타입이 나타나면, 일률적으로 `type` 키워드로 시작해야 합니다. 예시는 다음과 같습니다:
    * `(type Vec<Int>)::with_capacity(4)`  
      `Vec`가 제네릭 실인자를 명시적으로 가지고 있으므로, `Vec<Int>::with_capacity(4)`는 문법 오류입니다.
    * `Vec::with_capacity(4)`  
      `Vec`의 제네릭 매개변수를 지정하지 않아도 되며, 제네릭 매개변수는 컨텍스트에서 추론할 수 있습니다. 이때 type 접두사를 쓰지 않아도 됩니다.
    * `(type Vec<String> as Default)::default()`  
      타입 이름과 대응하는 trait 이름을 명확히 지정해, 완전 한정 문법으로 특정 함수를 호출할 수 있습니다. 이는 서로 다른 trait의 멤버 함수가 이름이 같아도 되고, 같은 타입에 대해 impl해도 충돌이 나지 않음을 뜻합니다.

2. 구조체 초기화와 패턴 매칭은 일률적으로 타입 후치 문법을 채택합니다. 예시는 다음과 같습니다:
    * 구조체 초기화: `let v = { .x = 1 } : S<Int>;`
    * 구조체 패턴 매칭: `expr is { .x = 1 } : S<Int>`

3. 제네릭 함수 호출에서 제네릭 매개변수 목록은 소괄호 안에 써야 합니다. 예시는 다음과 같습니다:
    * `std::mem::size_of(<Int>)`

위 수정의 핵심 논리는, 제네릭이 붙은 모든 타입 이름이 특정 식별을 접두사로 하는 컨텍스트에 나타나게 하는 것입니다.
이렇게 하면 컴파일러가 문법 분석을 할 때, 대응하는 기호나 키워드를 만나면 뒤에 나타나는 것이 반드시 표현식이 아니라 타입임을 알고, 이런 곳에서 나타나는 `<` `>` 기호를 작다/크다 기호가 아니라 꺾쇠괄호로 이해해야 합니다.

아래에서 제네릭 함수 호출 문법을 중점적으로 이야기합니다:
```
// 함수 정의 문법은 변하지 않음
fn f<T>(arg: T) {}

// 함수 호출 문법은 변화가 있음
fn main() {
    f(<Int>, 1); // 제네릭 실인자 타입을 명시적으로 지정
    f(1); // 타입 추론 방식, 제네릭 실인자를 생략한 표기
}
```

이렇게 문법을 설계한 주요 이유는, 첫째 turbo fish 같은 추한 문법을 피하기 위함이고, 둘째 zinc의 제네릭 함수 구현 방식과 맞추기 위함입니다.

특수한 장면의 컴파일러 최적화를 고려하지 않으면, zinc의 제네릭 함수는 구현 관점에서 기본이 테이블 전달 방식으로 구현됩니다. 컴파일러는 위의 함수 f를 다음과 같이 번역합니다:
```
// 함수 정의 f에 대응하는 의사 C 코드:
void f(ZnTypeMeta * typeof_T, void * arg) { }
```

`f(<Int>, 1)`과 같은 함수 호출을 실행할 때, 호출 측은 정말로 `Int`에 대응하는 ZnTypeMeta를 얻어 그것을 함수 실인자로 f 안에 전달합니다.
따라서 함수의 제네릭 실인자 목록을 소괄호 안에 쓰는 것이 zinc 제네릭 함수의 실행 의미론에 더 맞습니다.

zinc의 함수 포인터 타입은 제네릭을 포함할 수 있습니다. `let pf: fn<T>(T)->() = f;`
zinc는 함수 커링(currying)을 허용하지 않으며, 이렇게 쓰면 `let pf: fn(Int)->() = f(<Int>);` 컴파일이 실패합니다.
이런 함수 인스턴스화 장면은 lambda를 사용하십시오. 이렇게 쓰면 됩니다: `let pf: fn(Int)->() = .{ (arg: Int)->() => f(<Int>, arg); };`

제네릭 함수를 이렇게 구현하는 주요 이점은, 제네릭 함수도 동적 링크 라이브러리로 배포할 수 있다는 것입니다. 이는 Swift 언어의 설계 장점입니다.

이는 이런 장면에 매우 유용합니다:
동적 링크 라이브러리 `a.so`를 설계했고, 그것이 제네릭 함수 인터페이스를 외부에 노출해 애플리케이션 `b.exe`가 사용한다고 가정합니다.
그렇다면 `a.so`의 내부 구현을 업데이트할 때(물론 API 파괴적 수정은 할 수 없음) `b.exe`를 다시 컴파일하지 않아도, 프로그램이 자동으로 정상 동작하게 할 수 있습니다.
제네릭이 인스턴스화 방식으로 구현되면, 이 장면을 지원하기 어렵습니다. 상위 라이브러리를 업데이트하면 하위 애플리케이션을 반드시 다시 컴파일하고 다시 배포해야 합니다.

이 외에, 이 설계는 몇 가지 다른 이점도 딸려 있습니다:
1. `virtual` 함수가 제네릭을 갖는 것을 지원합니다. `virtual` 함수는 아래 장을 참고하십시오.
2. code size를 줄이고, 컴파일 시간을 줄입니다.

치르는 대가는 물론 실행 효율이 낮아지는 것입니다. 이렇게 하면 컴파일러의 많은 최적화를 막고, 캐시에도 비친화적이며, 실행 시간에 불리합니다.
하지만 우리는 여전히 구현 층면에서, 어떤 특정 장면에서 추가 컴파일 옵션을 통해 제네릭 인스턴스화를 성능 최적화 수단으로 쓰는 것을 허용해, code size와 실행 효율 사이에서 더 나은 균형을 얻을 수 있습니다.
1. 라이브러리가 아니라 실행 프로그램을 컴파일할 때는, 인스턴스화 방식으로 제네릭을 구현해도 완전히 괜찮습니다
2. 라이브러리를 컴파일할 때도, 동적 링크 라이브러리를 단독으로 배포·배치할 필요가 없다면, 인스턴스화 방식으로 제네릭을 구현할 수 있습니다

// 동등:
trait AnonymousTR {}

## trait

trait 정의 문법 예시는 다음과 같습니다:

```
trait TrName<T> : SuperTrait1 + SuperTrait2 where T: Condition {
    type AssocType;

    virtual fn method(&self);

    fn static_method() -> Self;
}
```

trait 정의는 다음을 지원합니다:
1. 선택적 제네릭 매개변수
2. 선택적 부모 타입 trait, 여러 부모 trait을 지원하며 `+`로 구분
3. 선택적 where 조건 절

trait 정의 본체에는 다음을 포함할 수 있습니다:
1. 연관 타입
2. 연관 상수
3. 연관 함수

### impl trait

trait은 서로 다른 타입을 통일 추상하는 데 쓸 수 있습니다. 어떤 구체 타입 `SomeType`이 어떤 trait `TrName`을 구현했음을 지정하는 문법 예시는 다음과 같습니다:

```
impl TrName for SomeType {

}
```

impl 블록
1. 내부 함수는 단독으로 pub을 지정할 수 없습니다
2. virtual도 지정할 수 없습니다

impl Trait for Trait은 허용되지 않습니다.

### trait을 가리키는 포인터

trait의 두 가지 사용 장면은 다음과 같습니다:
1. 제네릭 제약의 상한으로 사용
2. trait을 가리키는 포인터 타입으로 사용

전역 변수, 지역 변수, 멤버 변수는 trait을 타입으로 직접 쓸 수 없습니다. 하지만 trait을 가리키는 포인터를 타입으로 쓸 수 있습니다.

타입 `S`가 `trait R`을 구현했다면, `S`를 가리키는 포인터는 `R`을 가리키는 포인터로 업캐스트할 수 있습니다. 예시는 다음과 같습니다:

```rust
struct S {}
trait R {
    virtual fn f(&self);
}
impl R for S {
    fn f(&self) {}
}

fn test(p: *S) {
    let p1: *R = p; // ok, 업캐스트
    p1.f();
}
```

### virtual 함수

trait을 가리키는 포인터는 trait의 멤버 함수를 호출할 수 있습니다. 하지만 제한이 있습니다. virtual로 표시된 멤버 함수만 trait을 가리키는 포인터로 호출할 수 있습니다.

> 주:
> Rust는 `where Self: Sized` 문법으로 trait의 멤버 함수를 표시해 "non-virtual"임을 나타낼 수 있습니다. 이 문법은 매우 기이하고 이해하기 어렵습니다. zinc는 키워드를 직접 도입해 표시하는 편이 더 읽기 쉽습니다.
>

예시는 다음과 같습니다:

```rust
trait TR {
    virtual fn f1(&self);
    fn f2(&self);
}

fn test(p: &TR) {
    p.f1(); // OK
    p.f2(); // 컴파일 오류, f2는 virtual 함수가 아니므로 trait을 가리키는 포인터로 호출할 수 없음
}

fn test2<T>(arg: T) where T: TR {
    arg.f2(); // OK. 비 virtual 함수는 여전히 제네릭 형식으로 호출할 수 있음.
}
```

동시에 주의할 점은, trait에 쓴 모든 함수를 virtual로 수식할 수 있는 것은 아니라는 것입니다. virtual로 수식할 수 있는 함수는 다음 요구를 만족해야 합니다:
1. 첫 번째 매개변수 이름은 반드시 `self`여야 하고, 타입은 `Self`를 가리키는 포인터 타입이어야 합니다. `&self` `&mut self` `*self` `*weak self` 모두 가능합니다.
2. 첫 번째 매개변수 외에, 다른 매개변수는 `Self` 타입과 연관 타입을 쓸 수 없습니다
3. 함수의 반환 타입은 `Self` 타입과 연관 타입을 쓸 수 없습니다

예시는 다음과 같습니다:
```
trait TR {
    virtual fn clone()->Self; // 컴파일 오류, virtual로 수식할 수 없음. self 매개변수가 없고, 반환 타입에 Self를 씀.
    virtual fn g(arg: Int); // 컴파일 오류, virtual로 수식할 수 없음. self 매개변수가 없음.
    virtual fn h(self);  // 컴파일 오류, virtual로 수식할 수 없음. self 매개변수가 포인터 타입이 아님.
}
```

**주의**: virtual 함수는 새로운 제네릭 매개변수를 도입하는 것을 지원합니다. 예시는 다음과 같습니다:
```
trait TR {
    virtual fn f<T>(&self, arg: T) where T: Hash + Ord + Default; // OK
}
```

> **계획 중인 기능**: 이후 `* Trait1 + Trait2 + 'a` 표기를 지원할 수 있습니다:
1. `+`를 쓸 때는 구체 타입일 수 없고, trait과 trait을 더하는 것만 가능합니다
2. non-marker trait 타입은 하나만 있을 수 있습니다. 자기 자신과 더하는 것도 안 됩니다.
3. `* Trait1 + Trait2`는 `*Trait1` 또는 `*Trait2`로 암시 변환할 수 있습니다

이 특성은 어떤 장면에서 필수 기능일 수 있습니다. 예를 들어 `* MyTrait + Sync`로, 가리키는 타입이 MyTrait 제약뿐 아니라 Sync 제약도 만족함을 표현하고 싶을 때입니다.
다른 방법으로는 표현할 수 없습니다.

### 연관 타입

연관 타입은 trait에 정의된 타입 자리 표시자이며, trait을 구현할 때 구체 타입을 지정해야 합니다.

예시:
```rust
trait Container {
    type Item;
    
    fn add(&mut self, item: Self::Item);
    fn get(&self) -> Option<Self::Item>;
}

struct IntContainer {
    items: Vec<Int>,
}

impl Container for IntContainer {
    type Item = Int;
    
    fn add(&mut self, item: Int) {
        self.items.push(item);
    }
    
    fn get(&self) -> Option<Int> {
        self.items.last().copied()
    }
}
```

`Self` 타입은 trait을 구현하는 구체 타입을 나타냅니다.

### trait 상속

zinc의 trait은 상속을 지원합니다. trait을 정의할 때 부모 trait을 0개 또는 여러 개 지정하는 것을 허용합니다.

상속 관계가 있는 trait에서, 자식 타입 trait을 가리키는 포인터는 부모 타입 trait을 가리키는 포인터로 암시 변환할 수 있습니다(ARC / BORROW 포인터 모두 가능). 예시는 다음과 같습니다:
```
trait TR: TR1 + TR2 + TR3 {}

fn test(p: *TR) {
    let p1: *TR1 = p; // OK
    let p2: *TR2 = p; // OK
    let p3: *TR3 = p; // OK
}
```

부모 타입 trait을 가리키는 포인터도 패턴 매칭을 통해 자식 타입 trait의 포인터로 다운캐스트할 수 있습니다. 예를 들어 `is` `match` 모두 가능합니다.

```
trait TR: TR1 + TR2 + TR3 {}

fn test(p: *TR1) {
    if (p is p1: *TR) { // 다운캐스트를 시도하며, 실패할 수 있음
        // p1 변수 사용
    }

    match (p) {
        p2: *TR => {}
        _ => {}
    }
}
```

다른 기능은 다음과 같습니다:
1. 자식 trait에서 associated type / const의 값을 지정하는 것을 허용합니다
2. 자식 trait에서 부모 trait의 함수 본체를 override하는 것을 허용합니다
3. 다중 상속을 지원하며, 다중 상속 장면의 함수 이름 충돌 문제를 고려해야 합니다
    1. 다중 상속 장면에서는 이름 충돌을 금지합니다
    2. 다중 상속 장면에서는 부모 타입을 추가하거나 상속 순서를 조정하면 ABI에 영향을 줍니다
    3. `trait TR1 : TR2 {}`와 `trait TR1 where Self: TR2 {}`의 의미가 다릅니다.

### reuse

reuse 메커니즘의 목적은 멤버 변수, 멤버 함수를 재사용하는 것입니다. reuse는 일종의 문법 설탕으로, 사용자가 한 구현을 다른 타입에 위임하기 쉽게 합니다. 예시는 다음과 같습니다:

```
struct S1 { }
impl TR1 for S1 {
    fn f1(&self, arg: Int) {}
}

struct S2 {
    base: S1  // 멤버 변수 이름에 제한이 없으며, 무엇이든 상관없음
}
impl TR1 for S2 {
    reuse self.base;  // 의미는 이 impl 블록의 멤버 함수가 모두 self.base가 구현한 같은 trait의 멤버 함수를 재사용한다는 것
}

// 위 코드는 다음과 동등:
impl TR1 for S2 {
    // 모든 멤버 함수를 한 번씩 구현하고, 함수 본체는 모두 대응하는 `self.base`의 멤버 함수를 호출함.
    fn f1(&self, arg: Int) {
        self.base.f1(arg);
    }
}

```

### 객체지향 프로그래밍 패러다임

위의 언어 특성을 조합하면 zinc도 객체지향 프로그래밍 패러다임을 지원할 수 있지만, 업계에서 흔한 스타일(예: C++/Java/C#/Swift)과는 다릅니다.
Zinc의 주요 특징은 `class`와 class 상속을 지원하지 않는다는 것입니다. Zinc는 trait만 상속할 수 있고, trait을 가리키는 포인터만 동적 디스패치를 할 수 있습니다.

아래에서 몇 가지 측면으로, 왜 이렇게 설계했는지 설명합니다.

1. 참조 의미론의 `class` 타입은 메모리 레이아웃이 충분히 유연하지 않습니다

    메모리 레이아웃 관점에서, 다른 언어의 참조 의미론 class는 Zinc의 `ARC 포인터+구조체`를 합친 것으로 볼 수 있습니다. 참조 의미론만 쓸 수 있고, 그에 대응하는 값 의미론 구조체는 쓸 수 없습니다.
    이는 class 타입 변수를 지역 변수, 멤버 변수로 쓸 때 모두 동적 메모리 할당이 있고, 한 층의 추가 포인터 간접 참조가 있음을 뜻합니다. 이는 사실 표현 능력의 퇴화이지 강화가 아닙니다.
    반면 `ARC 포인터`와 `구조체`를 사용자에게 각각 제공하면, 예를 들어 `Vec<S>`와 `Vec<*S>`는 다른 타입이라 서로 다른 장면에서 필요에 따라 고를 수 있어 더 유연하고, 사용자에게 더 큰 자유도가 있습니다.

    참조 의미론 class는 어떤 장면에서도 각 객체 내부에 “객체 머리” 포인터를 자체적으로 가지고 있습니다. Zinc의 이런 설계는 객체 자체의 메모리 레이아웃에 영향을 주지 않습니다.

2. `class`라는 참조 의미론 타입을 추가하면 Zinc의 타입 시스템에 불일치가 나타나고, 많은 장면에서 특수 규칙이 필요해 구현이 복잡해집니다

    참조 의미론 class는 Zinc의 타입 시스템에 일련의 추가 규칙을 가져와 수지가 맞지 않습니다. 특히 각종 포인터와 class를 함께 쓸 때입니다.
    zinc에는 이미 여러 포인터 타입이 존재하며, “참조 의미론 class” 자체는 “암시적 포인터+구조체”의 조합으로 이해할 수 있습니다.
    이 기능은 다른 언어 특성과 직교하지 않습니다. 이 “암시적 포인터”가 도대체 ARC인지 weak인지 빌림인지, 사용자에게 선택권이 부족하기 때문입니다.

    이런 장면을 생각해 봅시다. `T`가 class일 때 `&T`가 나타내는 의미는 무엇인가. 이 빌림은 이 포인터 변수 자체를 가리키는가, 아니면 이 객체의 첫 주소를 가리키는가?
    class는 `ARC 포인터`와 `구조체`를 강제로 묶어 두므로, 어떤 설계 방안을 선택하든 약간의 번거로움이 생깁니다.
    포인터와 구조체를 나누면 의미 표현이 더 명확합니다. 타입 `&S`는 `S`에 대한 빌림이고, 타입 `&*S`는 `*S`에 대한 빌림입니다. 의미가 명확하고 구현도 간단합니다.

    아래 제네릭 장면의 예를 보면, 제네릭에서 값 의미론 struct와 참조 의미론 class를 통일하기가 매우 번거롭다는 것을 알게 됩니다:
    ```
    fn test<T>(arg: T) {
        // 참조 의미론 class를 도입하면, 빌림 취하기 표현식과 역참조 표현식이 값 의미론 타입과 참조 의미론 타입에 대해 동작이 달라짐.
        // 제네릭 장면을 생각하면, 런타임에 추가 판단을 해야 이 두 경우를 제네릭으로 통일 추상할 수 있음.
        let p: &T = &arg;
        let c: T = *p;
    }
    ```

3. C++처럼 class와 상속을 도입하되, class가 참조 의미론이 아니면 될까요?

    C++의 class와 struct는 의미 차이가 크지 않습니다. 값 타입을 지원하며 포인터와 묶이지 않습니다.
    하지만 class의 상속은 자식 타입이 부모 타입이 구현한 모든 인터페이스를 받아들여야 함을 뜻하며, 이는 문제가 있습니다.

    전통적인 상속 설계에서, 자식 타입 class는 반드시 부모 타입 class의 모든 인터페이스(interface/protocol)를 구현합니다.

    Zinc의 `Send` 같은 trait을 생각해 봅시다. 모든 멤버 변수가 `Send`를 만족해야 합니다. 상속을 도입하면 이런 상황이 나타납니다. 부모 타입이 `Send`를 구현했고,
    자식 타입이 부모 타입을 상속했지만 non-`Send` 멤버 변수를 추가했습니다. 우리는 자식 타입이 부모 타입의 모든 멤버 변수, 멤버 메서드를 재사용하되 `Send`는 구현하지 않기를 바라지만, 전통 상속 설계에서는 이것이 불가능합니다.

    상속을 쓰는 설계에서, 자식 타입은 부모 타입에서 일부 인터페이스만 골라 구현할 수 없습니다. 위 목적을 달성하려면 상속도 포기하고 조합으로 구현해야 합니다. 따라서 상속은 일부 장면에서만 코드 재사용을 편리하게 할 뿐, 모든 장면에 적응할 수 없습니다.

4. class의 상속은 특수 장면에 대해 특수 규칙을 설계해야 합니다

    1. 전형적인 장면 하나는 다중 상속 장면입니다.
    전통적인 상속 지원 설계 방안에 따라, 한 class가 여러 class를 상속하는 것을 지원하면 “다이아몬드 상속” 장면을 반드시 고려해야 합니다.
    C++는 이 장면에 대해 특수한 문법·의미 규칙을 설계했고, 동시에 많은 프로그래밍 규범도 이 특성에 많은 제약을 둡니다.
    Java/C#/Swift 등 언어는 다중 상속을 직접 지원하지 않아, 코드 재사용 능력을 제한하고 의미 규칙을 단순화했습니다.

    2. 또 다른 전형적인 장면은 생성자 장면입니다. 언어마다 규칙이 다릅니다. C++에서 생성자 안에서 가상 함수를 호출하면 가상 함수 효과가 없습니다.
    Java/C#의 생성자는 초기화되지 않은 변수에 접근하지 않으며, 필드의 “0값 초기화”에 의존합니다.
    Swift는 “0값 초기화”를 지원할 수 없으면서, 생성자 안에서 초기화되지 않은 멤버에 영원히 접근하지 않기를 바라므로, 규칙이 가장 복잡합니다.
    생성자는 함수 이름을 제한하며, 이는 생성자를 지원하려면 타입 기반 함수 오버로드를 지원해야 함을 뜻합니다. 생성자는 반환 타입을 제한하며, 이는 반환 타입으로 오류 처리를 할 수 없음을 뜻합니다.
    이런 설계 이념은 모두 zinc와 맞지 않습니다.

    요약하면, 전통 프로그래밍 언어는 class의 상속을 지원했지만, class 상속이라는 특성에는 추가적인 특수 의미 규칙이 붙어 있고, 언어마다 규칙이 달라 그리 아름답지 않습니다.

Zinc는 Rust의 설계 사고를 따라, 더 간결한 설계를 채택했습니다. trait 상속만 허용합니다.

Zinc의 설계는 사용자가 이해하고 사용하기 더 쉽습니다:
* 모든 멤버 변수의 재사용은 일률적으로 “조합” 모드를 채택합니다.
* 모든 멤버 메서드의 재사용은 일률적으로 “reuse 메커니즘”을 채택합니다.
* 여러 타입에 통일된 공용 인터페이스가 필요한 모든 장면은 일률적으로 “trait+impl”로 완료합니다.
* 동적 디스패치가 필요한 모든 장면은 일률적으로 “trait을 가리키는 포인터”로 완료합니다.

위 규칙은 모든 타입에 적용됩니다(내장 타입, enum, struct, tuple, 문자열, 배열 등). 특례가 없습니다. 위 규칙은 OOP 프로그래밍 패러다임을 충분히 완전하게 지원합니다. 표현 능력에 문제가 없으며, 전통 언어가 지원하는 기능을 모두 표현할 수 있고, 어떤 경우 문법이 조금 번거로울 뿐입니다.

의미 규칙은 간결하고, 일관되며, 직교합니다.

### 메모리 레이아웃

trait을 가리키는 포인터는 뚱뚱한 포인터입니다. 이 절에서 언급하는 포인터 타입은 `*T`, `*weak T`, `&T`, `&mut T`, `*raw T`, `*raw mut T` 여섯 가지를 포함합니다.

```rust
trait TRBase { virtual fn f1(&self); }
trait TRSub : TRBase { virtual fn f2(&self); }

struct S { i: Int }
impl TRBase for S { fn f1(&self) {} }
impl TRSub for S { fn f2(&self) {} }

fn main() {
    let p1: *S = box S{.i = 1}; // p1은 얇은 포인터
    let p2: *TRSub = p1; // p2는 뚱뚱한 포인터
    let p3: *TRBase = p2; // 업캐스트

    if p3 is psub: *TRSub {
        // 다운캐스트
    }
    if p2 is ps: *S {
        // 다운캐스트
    }
}
```

Zinc의 뚱뚱한 포인터 레이아웃은 Rust와 다릅니다. trait을 가리키는 포인터는 멤버가 3개입니다:
```
      p2
┌───────────────────┐
│ object_ptr        │→ 객체의 머리를 가리킴. 객체는 내장 타입, 사용자 정의 struct, enum 등 모두 가능.
│───────────────────│
│ typemeta_ptr      │→ 객체의 구체 타입의 TypeMeta를 가리킴. 타입의 name, size 등 정보를 포함하며, 소멸자 포인터, 복사 함수 포인터 등도 포함
│───────────────────│
│ vtable_ptr        │→ 이 구체 타입이 이 trait에 대응하는 가상 함수 테이블을 가리킴. 함수 포인터로 이루어진 배열
└───────────────────┘
```

* trait을 가리키는 포인터는 trait의 virtual 멤버 함수 호출을 지원합니다. 멤버 함수를 호출할 때는 vtable에서 대응하는 위치의 함수 포인터를 꺼내 다시 호출하며, 오프셋은 컴파일 타임에 결정됩니다.

* trait을 가리키는 포인터는 패턴 매칭을 통해 다른 타입의 포인터로 변환하는 것을 지원합니다. 뚱뚱한 포인터에 객체의 런타임 타입 정보가 저장되어 있기 때문입니다. 런타임에 이 trait 포인터가 가리키는 구체 타입이 무엇인지 판단할 수 있고, 매칭에 성공하면 포함된 object_ptr을 꺼내 구체 타입의 포인터로 쓰면 됩니다. 다운캐스트도 지원합니다. `*TRBase`가 런타임에 `*TRSub` 타입인지 판단할 수 있습니다.

* trait을 가리키는 포인터는 업캐스트를 지원합니다. `*TRSub` 타입은 `*TRBase` 타입으로 변환할 수 있습니다.

> 주:
> Rust에서 trait을 가리키는 포인터를 trait object라고 하며, 이 또한 뚱뚱한 포인터이지만 다운캐스트를 지원하지 않습니다. `Any`라는 특수 trait만 다운캐스트를 지원하고, 다른 trait은 지원하지 않습니다.
> 포인터 크기가 두 개뿐이라 조금 뚱뚱하지만 충분히 뚱뚱하지 않아, Zinc가 지원하고자 하는 모든 객체지향 프로그래밍 패러다임을 지원하기에 부족합니다.
>
> Swift의 Protocol 메모리 레이아웃을 참고하면, 포인터를 하나만 더 추가하면 됨을 알 수 있습니다. Zinc가 뚱뚱한 포인터를 위해 설계한 두 개의 메타데이터 포인터는 swift의 value witness table과 protocol witness table에 비유할 수 있습니다.

## 공변 & 반변

|           |   'a   |   T   |   U   |
|-----------|--------|-------|-------|
| &'a T     |  공변  |  공변  |       |
| &'a mut T |  공변  |  불변  |       |
| *T        |        |  공변  |       |
| Mutable<T>|        |  불변  |       |
| Vec<T>    |        |  공변  |       |
| fn(T)->U  |        |  반변  |  공변  |
| *raw T    |        |  공변  |       |
| *raw mut T|        |  불변  |       |

이후 타입의 공변, 반변 기능을 계속 지원할 수 있습니다.
`in` `out` 키워드는 이미 예약되어 있습니다.

사용 장면 예:
1. `Option<*Sub>`를 `Option<*Base>`로 변환
2. `Result<*SubR, *SubE>`를 `Result<*BaseR, *BaseE>`로 변환
3. `(*Sub, *Sub)`를 `(*Base, *Base)`로 변환
4. `fn(*Base)->*Sub`를 `fn(*Sub)->*Base`로 변환
