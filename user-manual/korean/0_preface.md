# 서문

<img src="../../assets/zinc-logo.png" width="10%" align=center />

Zinc 프로그래밍 언어는 Rust에서 영감을 받은, 더 쓰기 쉬운 시스템 레벨 프로그래밍 언어입니다.

## 특징

1. 정적 타입, 경량 런타임, GC 없음
  * 타입 안전
  * 가상 머신 없이 기계어로 직접 컴파일되어 시작이 빠름
  * GC가 없어 메모리 오버헤드가 작음
  * 메모리 레이아웃을 제어할 수 있음
  * LLVM 프레임워크를 백엔드로 사용하여 크로스 플랫폼이 용이함
  * 상호 운용이 편리함

2. 안전성
  * 기본적으로 메모리 안전하며, unsafe를 써야만 미정의 동작을 만들 수 있음
  * 기본적으로 스레드 안전하며, unsafe를 써야만 데이터 레이스를 만들 수 있음

3. 사용성
  * 제로 코스트 추상화를 추구하지 않음
  * move 의미론을 가진 타입은 없고, move 의미론을 가진 표현식만 지원함
  * 빌림 타입은 있지만 borrow checker는 없어서, ownership + borrow checker가 전체 프로그래밍 모델에 미치는 거대한 영향을 피하고 Rust의 사용성을 크게 개선함

4. 제네릭 함수는 주로 테이블 전달(dictionary passing)로 구현
  * 동적 링크 라이브러리로 컴포넌트를 배포할 수 있으며, 컴포넌트는 제네릭을 포함한 복잡한 인터페이스를 지원함
  * virtual 함수가 제네릭 인자를 가질 수 있음
  * 장기적으로는 ABI 안정을 지원하여, 컴포넌트를 단독으로 업데이트하고 하위 의존 항목을 다시 컴파일하지 않아도 되게 하고자 함
  * 컴파일 옵션을 제공하여, ABI 안정을 고려하지 않는 장면에서는 제네릭 함수를 인스턴스화해 성능을 더 최적화할 수 있음

### Rust와의 비교

1. 문법이 Rust와 가깝고, 표준 라이브러리 스타일도 Rust와 가깝습니다. 마찬가지로 메모리 안전, 스레드 안전 특성을 지원합니다.
2. 메모리 관리는 주로 소유권 메커니즘이 아니라 참조 카운팅을 사용합니다.
3. 사용성 향상: 빌림은 지원하지만 borrow checker는 제거합니다. move 의미론 표현식은 지원하지만 move 의미론 타입은 지원하지 않습니다.
4. 객체지향 프로그래밍 패러다임을 더 잘 지원합니다.
5. 제네릭 구현을 바꿔, 인스턴스화 방식과 테이블 전달(dictionary passing) 방식을 동시에 지원하고 컴파일 옵션으로 선택합니다.
6. 일부 문법이 단순해졌습니다.

### Swift와의 비교

1. 더 나은 스레드 안전 지원, 컴파일 타임에 thread-safety를 보장
2. 플랫폼 중립적이며, macOS를 주력 플랫폼으로 삼지 않음
3. obj-C와의 상호 운용을 포기하고, C/C++와의 상호 운용을 더 고려함
4. OOP 프로그래밍 패러다임 지원 방식이 다름. 예를 들어 class와 상속 특성을 지원하지 않음
5. move/빌림 기능의 지원 방식이 다름

### C++와의 비교

1. zinc가 더 안전합니다. unsafe를 사용하지 않으면 미정의 동작이 없습니다.
2. 제네릭 구현 방식이 다릅니다. zinc의 제네릭 함수는 가상 함수로 쓸 수 있고, 제네릭 함수를 바이너리 코드로 컴파일해 동적 링크 라이브러리로 배포할 수도 있습니다.
3. 장기적으로 zinc는 ABI 안정을 달성할 수 있습니다.
4. 실행 성능은 C/C++보다 상당히 떨어지지만, 애플리케이션 개발의 성능 요구는 충족할 수 있어야 합니다.
5. 더 단순한 언어 특성, 더 적은 역사적 짐, 더 나은 런타임 동적 특성 지원, 더 작은 코드 크기

### Go와의 비교

1. GC가 없어 메모리 자원 요구가 더 낮음
2. 제네릭, trait, enum, 패턴 매칭 등 더 나은 언어 특성 지원
3. 동적 링크 라이브러리로 컴포넌트를 배포하기에 더 적합
4. 더 나은 스레드 안전 지원
5. 더 나은 교차 언어 상호 작용. Go 언어는 GC를 내장하고 있어, 다른 GC를 내장한 언어와 상호 운용하기 어렵습니다.

## 자주 묻는 질문

### 1. Zinc 언어의 포지셔닝은 무엇인가요?

Zinc 언어의 초심은 Rust 언어의 사용성을 개선하는 것입니다.

시스템 프로그래밍 언어 설계에는 세 가지 흔한 평가 차원이 있습니다: 안전, 성능, 사용성. Rust 언어는 안전과 성능에서 극한을 달성했지만, 사용성은 줄곧 아픈 지점입니다.
Zinc 언어는 안전성을 계속 유지하면서, 극한의 성능을 포기하고 사용성 개선을 얻었습니다.

이런 수정을 한 이유는, 저자가 관찰한 바에 따르면 일반 개발자가 맞닥뜨리는 대다수 장면에서 CPU 성능이 병목이 아니며, CPU 극한을 쥐어짜는 장면은 결국 극소수이기 때문입니다.
대부분의 경우 사람들이 가비지 컬렉션이 없는 시스템 프로그래밍 언어를 선택하는 것은 극한 성능을 위해서가 아니라, 다양한 다른 이유 때문입니다. 포함하되 이에 국한되지 않습니다:

* 강한 메모리 레이아웃 제어력과 실행 성능의 예측 가능성을 원함
* 크로스 플랫폼 요구가 있고, 어떤 플랫폼에서는 가상 머신 런타임을 이식하기 어려움
* 어떤 플랫폼에서는 메모리 자원이 빠듯하여 자동 가비지 컬렉션 메커니즘을 쓸 수 없음
* 서로 다른 GC 메커니즘을 쓰는 다양한 고급 언어가 호출할 수 있는 기초 공용 컴포넌트 라이브러리를 작성하고 싶음. GC를 내장한 언어는, 다른 GC를 쓰는 언어와 한 프로세스 안에서 효율적으로 상호 운용하기 어렵습니다

따라서 이렇게 포지셔닝한 프로그래밍 언어에는 적합한 사용 장면이 있어야 합니다:
1. 자동 가비지 컬렉션 메커니즘이 없어 크로스 플랫폼이 쉽고, 다른 다양한 고급 언어와 상호 운용하기 쉽습니다. 공용 범용 모듈을 작성하기에 적합합니다.
2. 안전을 보장하는 전제 하에 사용성이 좋습니다. 개발자에 대한 요구가 낮고, 개발 생산성이 충분합니다.
3. 성능 수준은 충분하지만, 극한 성능을 추구할 필요는 없고, 하드웨어의 모든 잠재력을 쥐어짤 필요는 없습니다.

이런 설계는 Rust 언어의 포지셔닝과 맞지 않으므로, 이런 변경은 새로운 프로그래밍 언어를 시작해서 시도할 수밖에 없습니다.

Zinc 언어의 포지셔닝은 Swift 언어와 비슷하며, 핵심 특징은 가비지 컬렉션 없음 + 안전 + 사용성입니다.
동시에 스레드 안전이라는 장점도 갖추고 있으며, 이는 Swift가 갖추지 못한 점입니다.

### 2. Zinc 언어와 Rust 언어의 대비는?

* Rust는 “제로 코스트 추상화” 원칙을 고수하고, Zinc는 그 설계 원칙을 포기합니다. 실행 성능과 사용성을 동시에 챙길 수 없을 때 사용성을 우선 선택합니다.
* Rust는 “소유권+수명” 메커니즘으로 메모리 안전을 보장하고, 빌림 검사기가 컴파일 타임에 aliasing XOR mutation을 검사합니다. Zinc는 참조 카운팅과 빌림 메커니즘으로 메모리 안전을 보장하며, 컴파일 검사 규칙이 훨씬 느슨합니다. borrow checker를 제거함으로써 Zinc의 사용성이 Rust에 비해 크게 개선됩니다.
* Rust는 인스턴스화 방식으로 제네릭을 구현하고, Zinc는 테이블 전달 방식으로 제네릭을 구현합니다. 이는 Rust가 제네릭 코드를 바이너리 라이브러리로 컴파일해 외부에 배포하기에 적합하지 않은 반면, Zinc는 가능하다는 뜻입니다. 동적 링크 라이브러리와 ABI 안정성 지원은 Zinc 언어의 이후 중요 목표입니다.
* Rust는 메모리 안전, 스레드 안전을 보장하고, Zinc 언어도 마찬가지로 메모리 안전, 스레드 안전을 보장합니다. 안전성 측면에서 약화한 것이 아니라, 일정한 성능 대가를 치렀을 뿐입니다.

요약하면, 문법·의미론 층면에서 Zinc는 Rust 언어와 매우 가깝고, 실행 층면에서는 Zinc가 Swift 언어와 매우 가깝습니다.

### 3. 왜 이름이 Zinc인가요?

Rust는 녹슬음, 부식을 나타내고, Zinc는 아연 금속을 나타냅니다. 아연이라는 금속에는 한 가지 특징이 있습니다:

>
> 아연은 공기 중에서 산소와 쉽게 반응하여 아연 산화물 층을 형성합니다. 이것이 아연 잉곳 표면의 부동태층입니다.
> 부동태층은 일정 정도의 보호 작용이 있어, 추가 산화 부식을 억제할 수 있습니다.
> 아연의 가장 주요한 응용은 부식 방지용 철 아연 도금입니다.
>
> Zinc is most commonly used as an anti-corrosion agent, and galvanization (coating of iron or steel) is the most familiar form.
> (from: https://en.wikipedia.org/wiki/Zinc)
>

이 단어는 이 언어의 본질을 반영합니다. Zinc 언어는 겉보기에는 Rust 언어처럼 보이지만, 표면 문법 아래에서 그 사상 핵심은 Rust와 맞지 않습니다.

우연하게도, 이 단어는 중국어로 읽으면 비교적 듣기 좋고, “새 언어”와 비슷한 발음입니다.

### 4. 왜 참조 카운팅 reference counting (RC)을 주요 메모리 관리 메커니즘으로 선택했나요?

RC의 장점:
* RC의 한 가지 장점은 메모리 안전을 편리하게 구현할 수 있다는 것입니다. 메모리 안전을 구현하는 이론 기반은 "aliasing xor mutation"입니다. RC는 aliasing을 추적하기에 특히 적합하며, 이를 바탕으로 copy-on-write를 결합하면 좋은 안전성을 구현할 수 있습니다.
* RC는 Zinc 언어의 스레드 안전 설계와 매우 잘 맞습니다. 스레드 안전과 RC 메모리 관리는 서로 맞물리고 서로 성취합니다. 이것이 Zinc가 GC를 쓸 수 없는 핵심 이유입니다. GC를 채택하면 Zinc는 현재의 스레드 안전 수준에 도달할 수 없습니다.
* RC의 또 다른 매우 좋은 장점은 단순하다는 것입니다. 이는 외부 환경에 대한 제약 조건이 적다는 뜻이라, 다른 어떤 언어와도 상호 운용이 간단합니다. 반면 GC는 구현 세부사항이 너무 복잡해, 서로 다른 GC 메커니즘이 같은 프로세스에서 효율적으로 공존하기 어렵습니다. GC를 내장한 언어가 다른 GC 메커니즘의 언어와 상호 운용하면 스스로 고생을 자초하는 일이라 매우 불편합니다.

RC의 단점:
* RC의 한 가지 단점은 순환 참조로 인한 누수 문제를 해결할 수 없다는 것입니다. 하지만 이것은 메모리 안전 문제가 아니며, 영향은 상대적으로 작습니다. 게다가 시스템 프로그래밍 언어 범위에서는 C++/Rust/Swift를 포함한 다른 언어들도 이 문제를 해결하지 못했습니다. 메모리 할당기와 디버거가 잘 협력하게만 하면, 이 문제는 개발과 테스트 단계에서 발견하고 해결하기 어렵지 않습니다. 순전히 이 문제를 해결하려고 런타임에 마크-앤-스윕 메커니즘을 추가하는 것은 대가가 너무 커서 Zinc의 포지셔닝에 맞지 않습니다. 물론 테스트 단계에서만 사용하는 힙 메모리 스캐너를 구현해, 자동화 테스트와 결합하여 테스트 케이스의 순환 참조 문제를 보조 발견하는 것은 반대하지 않습니다.
* RC의 또 다른 단점은, 원자 명령을 고빈도로 사용해 참조 카운트를 증감하면 실행 성능이 좋지 않다는 것입니다.

하지만 몇 가지 최적화 수단을 써서 실행 성능을 조금 끌어올릴 수 있습니다:
1. Zinc는 본질적으로 값 의미론 타입 사용을 장려하므로, 많은 경우 동적 메모리 할당이 필요 없고, 객체 메모리 레이아웃 제어 능력도 비교적 좋습니다. 이는 캐시에 친화적이며, 참조 카운트 포인터가 나타나는 장면도 줄일 수 있습니다.
2. Zinc는 빌림 포인터 타입을 유지합니다. 빌림 포인터 타입의 복사, 인자 전달, 반환은 모두 참조 카운트를 수정하지 않습니다. 많은 장면에서는 빌림 포인터가 RC 포인터보다 더 합리적입니다.
3. Zinc는 move 의미론을 유지합니다. 이 특성을 합리적으로 사용하면 참조 카운트가 발생하는 빈도를 크게 줄일 수 있습니다.
4. Zinc의 RC 포인터는 라이브러리로 흉내 낸 것이 아니라 언어 내장 타입입니다. 따라서 컴파일러가 일부 장면에서 컴파일러 최적화를 통해 중복된 참조 카운트 증감 연산을 삭제할 기회가 있습니다.
5. 사용자는 libc 자체의 malloc/free를 더 선진적인 메모리 할당기(예: mimalloc)로 대체해, 동적 메모리 할당과 해제의 실행 효율을 높일 기회가 있습니다.
6. 스레드 안전 언어 특성을 이용해, 컴파일러는 어떤 RC 포인터와 그 모든 복사본이 반드시 현재 스레드 내부에서만 사용될 수 있음을 분석할 수 있으므로, 해당 포인터의 참조 카운트 증감 연산을 비원자 명령으로 번역할 수 있습니다. Zinc에서 포인터가 가리키는 타입이 `Sync` 제약을 만족할 때만, 그 포인터를 안전하게 스레드를 넘어 사용할 수 있습니다. 포인터가 가리키는 타입이 non-`Sync` 타입이라면, 그 포인터와 그 모든 복사본이 스레드를 넘어 사용될 수 없음을 확신할 수 있으므로, 여기에 최적화 기회가 있어 비원자 명령을 사용합니다. **이것이 바로 이것을 자동 참조 카운트 포인터라고 부르는 이유입니다(automatic reference counting). 여기서 글자 A는 Automatic을 나타내며 Atomic이 아닙니다. “자동”의 주요 의미는, 컴파일러가 원자 명령인지 비원자 명령인지를 자동으로 선택해 준다는 것입니다.**

이상의 차이는, 다른 언어에서 전통적인 atomic-rc에 기반한 참조 카운팅 메커니즘의 성능 수준 결론이 zinc에는 적용되지 않음을 보여 줍니다. 전통적인 atomic-rc에 비해 Zinc는 더 나은 성능 최적화 잠재력을 갖습니다.

요약하면, 안전, 성능, 사용성은 불가능한 삼각형입니다.
Zinc가 안전과 사용성을 선택했을 때, “제로 코스트 추상화”를 달성할 수 없음이 정해졌고, C/C++에 비해 일정 정도의 성능 손실은 받아들일 수 있습니다.
하지만 우리는 여전히 일련의 최적화 수단으로 실행 성능이 특별히 나빠지지 않도록 보장할 수 있습니다.

개인적으로 Arc가 Zinc의 성능 병목이 아니라, 제네릭 구현 방안이 병목일 것이라고 추측합니다.

### 5. 이 프로젝트의 목표는 무엇인가요?

Rust의 많은 측면의 설계가 매우 좋다는 것은 모두가 목격하는 바입니다. 하지만 그와 동시에 Rust의 학습과 사용 문턱을 낮추자는 목소리도 끊이지 않았습니다.
저는 줄곧, 안전한 시스템 프로그래밍 언어 범위에서 Rust의 설계 방향이 유일한 해가 아니며, 다른 설계 공간이 있다고 생각해 왔습니다.
본 프로젝트의 목적은 “안전한 시스템 프로그래밍 언어” 범위에서 다른 설계 가능성을 탐색하는 것입니다.

하지만 막연히 우리가 어떻게 어떻게 설계할 수 있다고만 말하면 아무도 듣지 않습니다. 프로그래머 업계에는 매우 유명한 말이 있습니다:
> 
> Talk is cheap, show me your code.
>

그래서 저는 모든 생각을 실제로 구현해 낼 프로젝트가 필요합니다. 그래야 설득력이 있습니다.

이 프로젝트의 핵심 설계 방향은 다음과 같습니다:
**Rust의 안전성을 유지하면서 실행 성능을 조금 희생하고 더 나은 사용성을 얻는다면, 어떤 모습이 될 수 있을까.**

그 위에 몇 가지 부차 목표도 있습니다:
1. 언어 특성을 단순화하고, 크고 완전한 것을 탐하지 않습니다. 서로 다른 언어 특성이 가능한 한 직교하게 하여 서로 영향을 주지 않고, 언어 특성 간에 자유롭게 조합해 사용할 수 있게 합니다. 의미 규칙에 패치를 치고 각종 특수 규칙을 두지 않으려 합니다. 사용자의 사고 부담을 줄입니다.
2. 컴파일러 구현을 단순화합니다. Rust 컴파일러는 현재 이미 너무 복잡해져, 완전히 이해할 수 있는 사람이 거의 없습니다. 이런 초복잡 프로젝트는 지속적인 진보와 진화가 어렵습니다. 어떤 언어 특성의 구현이 너무 복잡하다면, 종종 그 언어의 사용자도 그 특성을 완전히 파악하지 못할 가능성이 크다는 뜻이므로, 처음부터 그런 특성을 도입하지 말아야 합니다.
3. 대형 프로젝트의 컴파일 속도 문제를 관심 갖고, 좋은 IDE 힌트 기능을 제공합니다. 이는 컴파일러 구현 문제일 뿐 아니라 언어 특성 설계 문제이기도 합니다.
4. 컴파일이 곧 서비스라는 이념을 실천합니다. 컴파일러를 블랙박스로 만들지 말고, 그 자체의 각 컴포넌트를 공용 라이브러리로 커뮤니티에 공개해야 합니다. 컴파일러의 각 컴포넌트는 사용하기 좋은 공개 API를 가져야 합니다. 이는 주변 생태계의 발전을 크게 촉진할 것입니다.
5. 컴파일 언어에 기반한 더 나은 동적성 지원. 포함: 제네릭 함수를 바이너리 산출물로 배포, 제네릭 함수를 가상 함수로 사용, 동적 링크 라이브러리를 바이너리 배포물로 사용, ABI 안정, 동적 로딩, 일정 정도의 런타임 리플렉션 등 능력. 이들은 모두 Rust가 잘하지 못하지만 Swift가 더 잘 보여주는 측면입니다.

### 6. Zinc 언어에는 특별한 혁신점이 없고, 이미 있는 다른 언어의 특성을 다시 배열·조합했을 뿐인데, 의미가 있나요?

의미가 있습니다. 본 프로젝트의 목적이 혁신이 아니라 안전과 사용성이기 때문입니다. 이런 특성 조합의 최종 결과가 사용자에게 안전, 사용성, 요구 장면에 부합함을 느끼게 한다면 충분합니다. 사용자 요구를 충족하는 것이 저의 목표이지, 혁신을 위한 혁신이 아닙니다.

시스템 프로그래밍 영역에서 선택 가능한 프로그래밍 언어가 그리 풍부하지 않습니다. 저자는 여전히 어떤 장면에서는 특별히 적합한 프로그래밍 언어가 없다고 생각합니다.

* C/C++는 매우 강력하지만, 코드에 미정의 동작이 나타날 때 대규모 코드에서 버그를 찾는 것은 극히 고통스러운 일입니다. 일반 사용자에게는 대다수 장면에서 극한 성능이 필요하지 않으며, 약간의 실행 성능을 희생하고 안전성 향상을 얻는 것이 이런 상황에서 수지맞는 선택입니다.
* Rust는 꽤 좋은 프로그래밍 언어이지만, 어떤 특성이 너무 복잡하게 설계되어 있고, 프로그래밍 패러다임이 많은 사용자에게 충분히 친화적이지 않으며, 개발 생산성이 낮고, 동적 링크 라이브러리에 비친화적이며, 동적성이 필요한 장면에도 적합하지 않습니다.
* Swift도 꽤 좋으며, native 언어로서 동적성 지원이 좋고 바이너리 호환성도 지원합니다. 이는 모두 좋은 성질입니다. 하지만 애플이 장악하고 있어 기본적으로 애플 플랫폼 지원에만 집중합니다. 많은 장면에서 쓰고 싶어도 쓸 수 없습니다. 스레드 안전 문제도 마찬가지로 존재합니다.
* Zig는 신흥 시스템 프로그래밍 언어로서 아직 충분히 성숙하지 않습니다. 그리고 마찬가지로 메모리 안전, 스레드 안전 문제가 있습니다.
* Zinc는 Rust와 Swift 언어의 장점을 가능한 한 흡수해 만들어졌습니다. 첫째, 안전 측면에서 Rust에 맞춰 컴파일 타임에 메모리 안전, 스레드 안전을 보장합니다. 둘째, 언어 특성을 단순화해 사용 난이도를 낮췄습니다. 셋째, 더 나은 동적성 지원으로 동적 링크 라이브러리의 바이너리 호환 진화를 지원합니다.

공학 영역에는 마법이 없고, 서로 다른 목표에 대한 저울질과 취사선택만 있을 뿐입니다. 비교적 흔한 사용 장면을 찾아 요구를 충족하는 언어 특성을 설계하는 것이 Zinc 언어 설계의 주요 도전입니다.
저자는 "무GC & 안전성 & 개발 사용성"이라는 요구가 비교적 흔하며, 시장에는 요구를 완전히 충족할 만큼 경쟁력 있는 프로그래밍 언어가 부족하다고 생각합니다.
"극한 성능", "zero-cost abstraction"을 추구하는 장면은 실제 실천에서 매우 적으며, 성능을 최우선으로 하는 프로젝트는 C/C++/Rust를 사용하기를 권합니다.
Zinc 언어 설계는 이런 요구를 최우선으로 두어서는 안 됩니다.

이 설계가 유용하다고 느끼신다면, 아낌없이 좋아요를 눌러 주시거나, 제안을 주시거나, PR을 만들어 이 언어의 설계와 구현에 참여해 주시기 바랍니다.

### 7. Zinc 언어는 현재 어떤 상태에 도달했나요?

메모리 관리, 스레드 안전 등 핵심 특성은 이미 설계가 끝났고, 기초적인 표준 라이브러리가 있습니다. 그리고 이런 기초 특성을 바탕으로 컴파일러의 부트스트랩을 구현했습니다.

현재 상태는 개념 검증 단계(proof of concept)라고 할 수 있으며, 시작만 했을 뿐 실제로 쓸 수 있기까지는 아직 멀었습니다.
많은 핵심 언어 특성은, 부트스트랩을 방해하지 않는 한, 구현되지 않았습니다. 그리고 계획 중인 성능 최적화, 주변 도구, 표준 라이브러리 정비 등도 아직 하지 않았습니다.
이후의 지속 발전과 성숙에는 작업량이 아직 많으며, 오픈소스 커뮤니티의 힘을 빌려야 완성할 수 있을 것입니다.

### 8. 어떤 경우가 Zinc 사용에 비교적 적합한가요? 어떻게 보급할 계획인가요?

저는 새 언어가 이미 있는 성숙한 생태계의 옛 언어 영역을 빼앗으려 하면 난이도가 극히 크다고 생각합니다. 반대로 맹아기에 있는 업종을 찾아 새 장면을 깊게 파고 새 생태계를 구축한다면, 보급 난이도가 상대적으로 훨씬 낮아집니다.
증량을 확대하고 기존 점유를 빼앗지 않으면, 보급 비용을 크게 낮출 수 있습니다.

잠재력 있는 몇 가지 새 장면:

1. 지능형 커넥티드 자동차 제품
2. 로봇 장면
3. IoT 기기, 임베디드 기기, 각종 소형 지능화 기기
4. 인공지능 영역


### 9. Zinc 언어는 어떤 오픈소스 라이선스를 선택했나요?

Zinc는 가장 느슨한 MIT 오픈소스 라이선스를 선택했습니다. 현재 이 시대에 충분히 개방적이지 않은 프로그래밍 언어는 충분한 커뮤니티 참여자를 끌어들이지 못해 반드시 죽으며, 아무런 의미가 없기 때문입니다.
저는 이 프로젝트가 오픈소스일 뿐 아니라 개방적이기를 바랍니다. 여러분의 의견과 제안을 매우 기꺼이 듣겠으며, 친구 여러분이 Zinc 언어의 설계와 구현에 참여해 주시기를 환영합니다.
