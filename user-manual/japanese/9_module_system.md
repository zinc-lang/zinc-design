# モジュールシステム

## コンポーネント (component)

zinc のコンパイル単位はコンポーネントである。rust の crate に対応する。

> In C and C++ programming language terminology, a translation unit (or more casually a compilation unit) is the ultimate input to a C or C++ compiler from which an object file is generated.

コンパイル単位とは、コンパイラプロセスを一度実行するのに必要なソースファイルを指す。これらのソースファイルは、コンパイラが一度のコンパイルを実行する最小入力単位であり、これ以上分割できない。分割を続ければ、一度のコンパイルを実行できなくなる。

C/C++ コンパイラにとって、コンパイル単位は一つの .c または .cpp ソースファイル、およびそれが直接・間接に `#include` してくるすべてのファイルである。

Rust コンパイラにとって、コンパイル単位は一つの crate である。ユーザが一つの crate 内部の複数の mod をそれぞれコンパイルすることはできない。

Zinc コンパイラにとって、コンパイル単位は一つのコンポーネント (component) である。コンパイラが毎回実行する入力は、一つの完全なコンポーネントのソースコードである。ユーザが一つのコンポーネントの複数のソースファイルをそれぞれコンパイルし、それから一つのコンポーネントに組み立てることはできず、コンパイラにその能力はない。一つのコンポーネントは全体としてコンパイルしなければならない。

コンポーネントとコンポーネントの間は循環依存できない。

コンポーネント内部にはモジュール (mod) があり、コンポーネント内部のモジュール同士は循環依存できる。同一コンポーネント内のすべてのモジュールは、一つのコンパイラプロセス中で一緒にコンパイルされるからである。

コンポーネントはコンパイル後、機械語を含む `.o` ファイル、およびそのコンポーネントの対外公開インタフェース `.zno` ファイルを生成する。zno の命名は「酸化亜鉛」物質に由来する。

`.zno` ファイルは C 言語の「ヘッダファイル」として理解できる。ただしヘッダファイルは人手で書くものであり、`.zno` ファイルはコンパイラが自動生成する。

`.zno` ファイルの内容は、すべての公開関数シグネチャ、型定義、グローバル変数宣言、impl 宣言などを含む。さらに、コンポーネントをまたいでインライン化できるすべての関数の関数本体も含む。

## `export`

コンポーネントがライブラリなら、ユーザは `export component_name;` を使ってこのコンポーネントの名前を宣言する必要がある。
コンポーネントが実行可能プログラムなら、ユーザは root mod の中に `fn main()` 関数を定義し、プログラム入口とする必要がある。
一つのコンポーネント中でこの二つがどちらもなければ、コンパイラはエラーを出す。

Rust では crate の名前はコンパイルオプション `--crate-name NAME` で指定されるが、自分はこれは不合理だと考え、コンポーネントの名前はそのソースコードが指定すべきである。
結局のところコンポーネントの名前はバイナリ中のシンボルの mangle name に影響し、コンポーネント名がコンパイルオプションで制御されると、異なるコンパイル環境でのコンパイル結果の一貫性を保証しにくい。

## `import`

コンポーネント a が別のコンポーネント b に依存することを記述するときは、a のソースコード中に `import b;` と書く必要がある。これは基本的に Rust の `extern crate b;` の意味に等しい。

C/C++ 言語で類比するなら、単純に `#include "b.h"` の意味として理解できる。

## mod の紹介

モジュール（mod）は Zinc 中でコードを組織する基本単位である。モジュールは関数、型、定数、および他のモジュールを含められる。

### モジュール定義

`mod` キーワードでモジュールを定義する：

```rust
// ファイル中でモジュールを定義する
mod my_module {
    fn helper() -> Int {
        return 42;
    }
    
    pub fn public_function() {
        println(f"helper returned $(helper())");
    }
}
```

### ファイルシステムモジュール

モジュールはファイルシステムによって組織することもできる。モジュールに内容がなければ、コンパイラは同名のファイルまたはディレクトリを探す：

```rust
// main.zn 中で
mod network;

// コンパイラは次を探す：
// 1. network.zn ファイル
// 2. network/mod.zn ファイル
```

### 可視性

モジュール中の項はデフォルトでプライベートであり、それを定義したモジュール内部でのみアクセスできる。`pub` キーワードを使うと項を対外的に可視にできる：

```rust
mod my_module {
    pub fn public_function() {
        // 外部からアクセスできる
    }
    
    fn private_function() {
        // my_module 内部でのみアクセスできる
    }
    
    pub struct PublicStruct {
        pub field: Int,      // 公開メンバ
        private_field: Int,  // プライベートメンバ
    }
}
```

### 入れ子モジュール

モジュールは入れ子に定義でき、木構造を形成する：

```rust
mod outer {
    pub fn outer_function() {}
    
    mod inner {
        pub fn inner_function() {}
        
        mod deeply_nested {
            pub fn deep_function() {}
        }
    }
}
```

### モジュールパス

`::` 演算子でモジュール中の項にアクセスする：

```rust
fn main() {
    outer::outer_function();
    outer::inner::inner_function();
    outer::inner::deeply_nested::deep_function();
}
```

### 可視性修飾子

Zinc は次の可視性修飾子をサポートする：

1. **デフォルト（プライベート）**：それを定義したモジュール内部でのみアクセスできる
2. **`pub`**：すべてのモジュールに可視である
3. **`pub(in path)`**：指定パスのモジュール内でのみ可視である（> **計画中の機能**：将来サポートする）

```rust
mod my_module {
    pub fn public_api() {}
    
    fn internal_helper() {}
    
    // 将来サポート：親モジュールでのみ可視
    // pub(super) fn parent_visible() {}
}
```

### 再エクスポート

`pub use` を使うと、他のモジュールの項を再エクスポートできる：

```rust
mod inner {
    pub fn helper() {}
}

mod outer {
    // inner::helper を再エクスポートする
    pub use inner::helper;
}

fn main() {
    // outer::helper を通してアクセスできる
    outer::helper();
}
```

### モジュールとコンポーネントの関係

> **計画中の機能**：export path と import path 機能のサポートを検討する。すなわち `export ident;` `import ident;` という書き方だけでなく、`export ident1::ident2::ident3;` および `import ident1::ident2::ident3;` という書き方も許すべきである。

主に、コンポーネント同士に並列関係しかなく包含関係がないと、十分に柔軟でないことを考慮してである。
一つのコンポーネント内部の論理構造は木構造であり、コンポーネント同士に包含関係がなく並列関係だけだと、あるコンポーネントの規模が過大でコンパイル時間が長すぎ、リファクタが必要なとき、リファクタ自体が必然的にコンポーネントの論理構造を変えてしまう。これは適切でない。

コンポーネント内部のある部分木もコンポーネントであってよく、モジュールだけではない、と許すことを検討できる。大規模コンポーネントを異なるコンパイル単位に分割する助けになり、コンポーネント内部の論理構造に影響しない。

二つの原則を変えない必要がある：
1. 一つのコンポーネントの論理構造は木であり、森ではない
2. コンポーネントとコンポーネントの間は循環依存できない

## use 文

`use` 文は、他のモジュール中の項を現在のスコープに導入するために使い、毎回完全なパスを書くのを避ける。

### 基本的な使い方

```rust
use std::collections::HashMap;

fn main() {
    let map = HashMap::new();
    // HashMap を直接使え、完全なパスを書く必要はない
}
```

### パスキーワード

- `self`：現在の mod にアクセスできる
- `super`：現在の mod の一つ上の mod にアクセスできる
- `::ident`：グローバル範囲の名前、すなわち component 名にアクセスできる。合法な名前には、export 中で定義した自分の名前、import してきた依存項の名前、および std 標準ライブラリが含まれる。
- `::self`：現在の component のトップレベル mod にアクセスできる。`::ident` で始めて本コンポーネントのトップレベル名にアクセスすることと等価である。注：Rust とは違いがある。Rust では、`crate::` キーワードによってトップレベル mod にアクセスする。

### 例

```rust
mod outer {
    pub fn outer_fn() {}
    
    mod inner {
        pub fn inner_fn() {}
        
        fn example() {
            // self を使って現在のモジュールにアクセスする
            self::inner_fn();
            
            // super を使って親モジュールにアクセスする
            super::outer_fn();
        }
    }
}

// use を使ってインポートする
use outer::inner::inner_fn;

fn main() {
    inner_fn();
}
```

### リネームインポート

`as` キーワードを使うと、インポートした項をリネームできる：

```rust
use std::collections::HashMap as Map;

fn main() {
    let map = Map::new();
}
```

### 複数の項のインポート

```rust
use std::collections::{HashMap, HashSet};

fn main() {
    let map = HashMap::new();
    let set = HashSet::new();
}
```
