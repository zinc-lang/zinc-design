

## zno ファイル形式

コンパイラがライブラリコンポーネントをコンパイルするとき、対応する `.o` バイナリファイルを生成するほかに、C 言語の「ヘッダファイル」に似たものも生成する必要があり、すべての公開インタフェースのシグネチャを含み、下流ライブラリに使わせる。
zinc 言語が生成する「ヘッダファイル」は `.zno` をファイル拡張子とし、「酸化亜鉛」の意を取る。

`.zno` ファイルの内容は、すべての公開関数シグネチャ、型定義、グローバル変数宣言、impl 宣言などを含む。さらに、コンポーネントをまたいでインライン化できるすべての関数の関数本体も含む。

`.zno` ファイル形式は純テキスト形式、あるいは任意の一種のカスタムバイナリ形式を使え、原理上はいずれも問題ない。しかしコンパイル速度を上げるため、最終的に sqlite ファイルを採用して実装した。以下ではこうする理由を説明する。

次のような場面を考える。大きなプロジェクトに多くの複雑なコンポーネントが含まれる。コンポーネント a はコンポーネント b に依存し、b はさらに他のコンポーネント c、d、e などに依存する。
単純なテキストファイル形式を使うと、コンポーネント a をコンパイルするとき、コンポーネント b の zno ファイルをすべて読み込むだけでなく、コンポーネント b が依存する他のすべてのコンポーネントの zno ファイルもすべて読み込み、それから構文・意味解析をする必要がある。
C/C++ コンパイラの `#include` 機能はこう実装されている。
しかし Zinc のモジュールシステムにとっては、C/C++ の設計を直接コピーするのは適さない。C/C++ はファイルをコンパイル単位とし、Zinc は component をコンパイル単位とし、コンパイル単位の体量がより大きいからである。
類比すると、一つの C/C++ のかなり大きなモジュールが直接・間接に使うすべてのヘッダファイルを一つの巨大ファイルに合併し、他のファイルがいつでもこの巨大なヘッダファイルを include し、手動でいくつかの小型ヘッダファイルに分割しないことに相当する。
しかもコンポーネント横断インラインの需要も考える必要があり、一部の関数の関数本体もこのヘッダファイル中に記録する必要がある。
大規模プロジェクトにとって、過大なヘッダファイルはコンパイル時間の大きな浪費である。この大量の zno の中の大部分の内容は、コンポーネント a をコンパイルするときに使わないからである。
したがって、zno にオンデマンド読み取り機能をサポートさせ、a をコンパイルするときに必要なものを読む、ということを考えられないか？各「宣言」の粒度で zno ファイルを切り分け、ファイルを粒度として全体を読み込むのではない。
たとえばコンポーネント a がコンポーネント b 中の一つの関数 `fn f();` を単純に使っただけなら、b の中の他の関数宣言、型定義などはすべてコンポーネント a と関係がなく、b の依存項も a と関係がないとわかる。
`b.zno` ファイルからそのような一つの関数シグネチャだけを単独で取り出し、構文・意味解析をし、他の内容は気にしなくてよい。b の zno ファイルがどれほど巨大でも、その依存木がどれほど複雑でも、これは a のコンパイルと何の関係もない。

上記の目標に達するため、ヘッダファイル全体を異なる宣言ごとに複数の部分に切り分け、インデックスを立てて照会しやすくする必要があり、これこそ sqlite が手伝ってうまくできることである。

sqlite 形式を使う利点は：
1. sqlite は「オンデマンド読み取り機能」を最も便利にサポートする形式であり、自分のファイル形式を設計して同じ効果に達しようとすると、最終的にはより簡略で、より使いにくく、bug の多い sqlite 形式ファイルを作ることになる可能性が高い。
2. 読み書きが速く、ファイルサイズも適切である。既存の補助ツールがあり、成熟して安定しており、デバッグが便利である。今後 schema を変更して機能を拡張するのも便利である。
3. 現段階では実装を単純にするため、sqlite 中にシリアライズしたソースコードを直接保存しているが、今後は中間コード IR を保存するよう変更し、さらにコンパイル速度を上げることもできる。これは全体設計の変更を必要としない。

zno ファイルは人間可読性を気にする必要はない。このファイルはコンパイラ用であり、人間が読むものではないからである。
人間が読む機能はドキュメント生成ツールに含めるべきであり、doc generator ツールを提供し、美しい HTML 形式のドキュメントを生成し、優美な組版、コードハイライト、ハイパーリンク、検索機能などを備え、人間の読書に便利にすべきである。

## セルフホスト bootstrapping

zinc コンパイラの最初の版は C++ 実装であり、その後フロントエンドを zinc で改めて実装し直した（もちろんバックエンドに使う LLVM フレームワークは含まない）。こうする目的はいくつかある：

1. プログラミング界には名言がある。「Eating your own dog food」。設計者はまず自分が設計した製品を愛し、長期に重度に自分の製品を使い、こうして Plan-Do-Check-Act 循環を有効に形成でき、問題を早く発見して改善する助けになる。自分の日常仕事のプログラミング言語が zinc であってほしいと非常に願い、それを直接使って自分のコンパイラを書けば、第一手の使用体験を最も速く蓄積でき、問題を速く発見・改善できる。最初の版を Rust で実装しなかったこともこれに関係する。Rust の思考習慣・設計パターンは zinc と大きく異なるからである。たとえば Rust 実装のコンパイラ内部の多くのデータ構造は、ポインタの代わりにインデックスを使う必要があり、この思考方式は他の言語との違いが大きい。後で zinc で書き直すことが早くから決まっていたのなら、最初の版は C++ で書いた方が、二番目の版は主体アーキテクチャを変えずにシームレスに移行できる。
2. オープンソース後に他の開発者の貢献を受け入れやすくする。コンパイラ自体が C++ 実装だと、互いに知らないオープンソース貢献者の PR に対して、個人的にコードレビューをうまくし、コード品質を維持するのが難しいと感じる。一方、安全なプログラミング言語で実装された機能をレビューするのは、ずっと単純である。
3. compiler as a service の理念を実践する。周知のとおり、一つのプログラミング言語はコンパイラを一つ実装するだけでなく、一揃いの生態系があって初めて本当に役に立つ。この生態系中のツールチェーン部分には、統合開発環境 IDE サポート、コード自動フォーマットツール、パッケージ管理ツール、ドキュメント生成ツール、カスタム lint 警告、コード品質分析など一連のツールが含まれる。これらのツールの多くは、コンパイラと同一の論理を共有する必要がある。したがって、コンパイラ自体の各部分を、比較的呼び出しやすい library にし、安全で使いやすい API を持たせられれば、周辺ツールの構築は半分の労力で倍の成果になる。逆に、コンパイラがブラックボックスで、そのコンポーネントを気軽に再利用できなければ、周辺ツールの構築には大量の反復作業があり、倍の労力で半分の成果になる。C++ をコンパイラ自体の各サブコンポーネントの対外 API インタフェースとするのは、十分に安全でも使いやすくもない。
4. 今後のメタプログラミング（マクロ、カスタム lint など）機能の基礎を築く。いわゆるメタプログラミングは、実装の層から言えば、実はコンパイラプラグイン機能である。コンパイラがいくつかのモジュールを動的ロードし、コンパイル過程中にこれらのプラグインの機能を実行する必要がある。マクロ定義自体が zinc で実装されることをもちろん望む。しかも zinc は動的リンクライブラリにコンパイルするのに比較的適した言語であり、コンパイルしたライブラリの API はジェネリクス、trait などの高級機能もサポートできる。コンパイラが呼び出し側として、zinc 実装でもあれば、このプラグイン機構は非常に清潔で簡潔である。逆に C++ で zinc の動的リンクライブラリを動的ロードするのは、できないわけではないが、明らかに枝葉を生やす面倒事である。

## コンパイラ構造の簡単な紹介

コンパイラは次のコンポーネントに分かれる：
* zinc_cli 実行可能プログラム。以下のいくつかのコンポーネントに依存する。内部には主にコマンドライン処理機能が含まれる。
    * options
    * session
* zinc_frontend コンパイラフロントエンド。構文・意味検査を担当し、複数のサブモジュールを含む。その中で二つの最も主要なモジュールは：
    * zinc_syntax  主な入力はソースコード、出力は SyntaxTree というデータ構造である。構文エラー報告機能を含む。lexer もこのコンポーネントに含まれる。
    * zinc_semantic  主な入力は SyntaxTree というデータ構造、出力は SemanticModel というデータ構造である。意味エラー報告機能を含む。
        * hir
        * mir
* zinc_backend コンパイラバックエンド。性能最適化とコード生成を担当し、複数のサブモジュールを含む。その中で二つの最も主要なモジュールは：
    * optimization 性能最適化。入力は SemanticModel というデータ構造であり、それに対して変更・変換をする
    * llvm_ir_gen 主な入力は SemanticModel というデータ構造、出力は LLVM IR である。その中にもいくつかの性能最適化が含まれる。


これらはいずれも zinc_std に依存し、これは zinc の標準ライブラリである。

## 引数型に基づく関数オーバーロードをサポートしない

主な目的は、動的リンクライブラリに基づくコンポーネント公開をよりよくサポートするためである。

核心的な場面は：あるコンポーネントを動的リンクライブラリで対外公開するとき、今後ライブラリの版を更新するときに、下流ユーザがコードを再コンパイルする必要がなく、直接リンクして使えるようにしたい、ということである。

ここで、引数型に基づく関数オーバーロードをサポートすると仮定し、次の状況を考える：
lib_v1 に一つの関数があり、シグネチャは `fn f(arg: *Base);` である。lib_v2 版で新しいオーバーロード版 `fn f(arg: *Sub);` を追加したい。ここで `Sub` は `Base` を継承した trait である。
下流ユーザがコードを再コンパイルせず、lib_v2 と一緒に使うとき、コードは依然として実行できるが、常に `Base` 版を呼ぶ。この新規オーバーロードは全く効かない。

「引数型に基づく関数オーバーロードをサポートしない」と言うとき、実際の意味は「コンパイル期に引数型に基づいて関数版を解決することをサポートしない」であり、ユーザに実行期に関数版を解決するよう強制する。

依然として上の場面で、ユーザが lib_v2 中で `*Sub` 型の引数に追加の処理をしたいなら、ユーザは元の関数の関数本体を変更する必要があり、オーバーロード版の関数シグネチャを新規追加するのではない:
```
fn f(arg: *Base) {
    if (arg is s:*Sub) {
        // パターンマッチで判定し、arg が *Sub 型なら、特殊な論理を実行する
    } else {

    }
}
```
新しい版 lib_v2 の動的リンクライブラリ公開後、実行可能プログラムは再コンパイルする必要がなく、この応用の振る舞いは自動で更新される。

こうするのはもちろん実行効率を犠牲にする。しかし動的リンクライブラリの透過的な更新を実現するため、このランタイム代価は必ず払う必要がある。コンパイル期にオーバーロード解決をすると、このような動的性は得られない。

この設計には表現能力の問題はなく、実行性能の問題だけがある。そして実行性能は、さまざまな最適化措置によって一部を補う機会がある。特にユーザが「ABI 安定な動的リンクライブラリを公開する」という需要を必要としないときは、コンパイルオプションでコンパイラに伝え、より積極的な最適化を開ける。

## 例外 (exception)、スタック巻き戻し (unwind) がない

zinc 言語は `panic` キーワードを提供し、他の言語の `throw` キーワードに類比できる。しかしそれは他の言語の `throw` や rust 中の `panic!` とは同じものではない。

Rust の panic には二通りの振る舞いモードがあり、それぞれ `abort` と `unwind` であり、`rustc` の次のコンパイルオプションで指定できる。
```
-C    panic=val -- panic strategy to compile crate with
```
* rust 中の `panic` は `abort` 戦略の下では、プロセスを直接終了し、`catch_unwind` 関数は働かない。libc の `abort` 関数を呼ぶことに等しい。
* rust 中の `panic` は `unwind` 戦略の下では、スタック巻き戻し (unwind) を実行し、各層の関数中の局所変数のデストラクタを呼び、ARC ポインタの参照カウント自動減一などの操作を含み、しかも `catch_unwind` で捕捉でき、スタック巻き戻しの過程を終了できる。この過程は他の言語の exception に似ている。

zinc 中の `panic` は単純に関数呼び出しスタックを印字してから abort する。unwind の過程はなく、捕捉できず、rust 中の `panic` が `abort` 戦略の下での振る舞いに相当するだけである。zinc は `unwind` という振る舞いをサポートしない。

この設計は nikomatsakis のこの [ブログ](https://smallcultfollowing.com/babysteps/blog/2024/05/02/unwind-considered-harmful/) に着想を得て、こうすることを選んだ。理由は次のとおりである：

1. unwind はコンパイラ、標準ライブラリの実装難度を増やす
    1. unwind はコード体積を増やす。各関数呼び出しでスタック巻き戻しが起きうるため、コンパイラはスタック巻き戻しが起きうる各場所でどの局所変数のデストラクタを呼ぶかを記録する必要がある。
    2. unwind は最適化機会を減らす。コードの制御フローグラフが複雑になり、多くの場所に unwind が起きうる制御フローが一つ増え、これはコンパイラの静的解析に影響する。
    3. unwind は標準ライブラリが実装時に例外安全 (exception safety) という問題を考慮することを要求する。
2. unwind はユーザの学習と使用のコストを増やす
    1. zinc は後発言語として、独立した生態を築くのは難しい。ほとんどの応用で、皆は zinc でその中のある一つのモジュールを開発するだけである可能性が高く、これは相互運用が重要であることを意味する。zinc が unwind 機構を導入すると、既存の C++ の exception、Rust の panic とどういう関係か、互いに捕捉できるのか。zinc で書いた下層モジュールを上層言語 Go/C#/Java/Javascript/Python などから呼べるようにしたいなら、これらの高級言語は zinc が投げた panic を捕捉できるのか。この機構はユーザにとって結局便利なのか、それとも混乱を足すのか。
    2. 言語中に unwind 機構を導入すると、すべての第三者ライブラリが設計時に例外安全 (exception safety) という問題を考慮することが要求される。特に unsafe および相互運用に関わるとき、このことは難しい。zinc の位置づけは単純で使いやすいことを強調しており、普通の開発者にも例外安全設計を考慮するよう要求するのは、要求が高すぎないか。
    3. どのようなエラー処理場面が、`Option` `Result` では表現しにくく、捕捉可能な unwind で必ずやらなければならないのか。この特性を実装したら、どのような場面が恩恵を受けられ、それらの場面は十分に説得力があるのか。

自分は、zinc の生態は次のように建設すべきだと考える：すべての「回復可能なエラー」は一律 `Option/Result` 型を返し、この種のエラーは、本プロセスがこの種のエラーに遭遇したときに処理手段があることを意味する。すべての「回復不能なエラー」は一律 `panic` を使い、この種のエラーの意味は、現在のアプリケーションが実行段階でこの種のエラーに対していかなる処理手段もなく、これはコード中の bug であり、唯一の解決方法は戻ってコードを修正し、プログラムを再コンパイルし、再実行することである。

この決定に同意しない人がいれば、完全な設計提案を書いて議論を始める必要があり、内容は上記の疑問に十分に解答すべきである。
