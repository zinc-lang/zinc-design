# まえがき

<img src="../../assets/zinc-logo.png" width="10%" align=center />

Zinc プログラミング言語は、Rust に着想を得た、より使いやすいシステムプログラミング言語である。

## 特徴

1. 静的型付け、軽量ランタイム、GC なし
  * 型安全
  * 仮想マシンを介さず機械語へ直接コンパイルするため、起動が速い
  * GC がなく、メモリオーバーヘッドが小さい
  * メモリレイアウトを制御できる
  * バックエンドに LLVM フレームワークを用い、クロスプラットフォームが容易
  * 相互運用が容易

2. 安全性
  * デフォルトでメモリ安全であり、未定義動作を起こせるのは unsafe を使った場合だけである
  * デフォルトでスレッド安全であり、データ競合を起こせるのは unsafe を使った場合だけである

3. 使いやすさ
  * ゼロコスト抽象を追求しない
  * move セマンティクスを持つ型はなく、move セマンティクスを持つ式だけをサポートする
  * 借用型はあるが borrow checker はない。ownership + borrow checker がプログラミング全体の流儀に与える大きな影響を避け、Rust の使いやすさを大幅に改善する

4. ジェネリック関数は主に表渡し（dictionary passing）で実装する
  * 動的リンクライブラリとしてコンポーネントを公開でき、ジェネリクスを含む複雑なインタフェースをサポートする
  * virtual 関数がジェネリック引数を持てる
  * 将来的には ABI 安定を目指し、下流の依存を再コンパイルせずにコンポーネントだけを更新できるようにしたい
  * コンパイルオプションを提供し、ABI 安定を考慮しない場面ではジェネリック関数をインスタンス化して、さらに性能を最適化できるようにする

### Rust との比較

1. 構文は Rust に近く、標準ライブラリの流儀も Rust に近い。同じくメモリ安全・スレッド安全をサポートする。
2. メモリ管理は所有権機構ではなく、主に参照カウントを用いる。
3. 使いやすさの向上：借用はサポートするが borrow checker を削除する。move セマンティクスの式はサポートするが、move セマンティクスの型はサポートしない。
4. オブジェクト指向プログラミングパラダイムをよりよくサポートする
5. ジェネリクス実装を改め、インスタンス化方式と表渡し（dictionary passing）方式の両方をサポートし、コンパイルオプションで選択する
6. 一部の構文が簡略化されている

### Swift との比較

1. より良いスレッド安全サポート。コンパイル時に thread-safety を保証する
2. プラットフォーム中立であり、macOS を主力プラットフォームとしない
3. Objective-C との相互運用を捨て、C/C++ との相互運用をより重視する
4. OOP パラダイムのサポートの仕方が異なる。たとえば class や継承はサポートしない
5. move / 借用機能のサポートの仕方が異なる

### C++ との比較

1. zinc はより安全であり、unsafe を使わない限り未定義動作はない
2. ジェネリクスの実装方式が異なる。zinc のジェネリック関数は仮想関数として使え、ジェネリック関数をバイナリコードにコンパイルして動的リンクライブラリとして公開することもできる
3. 長期的には、zinc は ABI 安定を達成できる
4. 実行性能は C/C++ よりかなり劣るが、アプリケーション開発の性能要件は満たせるはずである
5. より単純な言語機能、より少ない歴史的負債、より良いランタイム動的特性のサポート、より小さなコードサイズ

### Go との比較

1. GC がなく、メモリ資源への要求がより低い
2. ジェネリクス、trait、enum、パターンマッチなど、より良い言語機能サポート
3. 動的リンクライブラリとしてコンポーネントを公開するのに適している
4. より良いスレッド安全サポート
5. より良い言語間相互運用。Go は GC を内蔵しており、他の GC 付き言語との相互運用が難しい。

## よくある質問

### 1. Zinc 言語の位置づけは何か？

Zinc 言語の当初の目的は、Rust 言語の使いやすさを改善することである。

システムプログラミング言語の設計には、よく使われる評価軸が三つある：安全、性能、使いやすさ。Rust は安全と性能で極限まで到達しているが、使いやすさは一貫して課題である。
Zinc は安全性を保ちつつ、極限の性能を捨て、使いやすさの改善と引き換えにした。

このような変更をしたのは、著者が次のように観察したからである。普通の開発者が直面するほとんどの場面では、CPU 性能はボトルネックではなく、CPU の限界を搾り取る場面はごく少数である。
多くの場合、人々がガベージコレクションのないシステムプログラミング言語を選ぶのは、極限性能のためではなく、さまざまな他の理由による。それには次のようなものが含まれるが、これらに限らない：

* 強いメモリレイアウト制御力と、実行性能の予測可能性が欲しい
* クロスプラットフォームの要求があり、一部のプラットフォームでは仮想マシンランタイムの移植が難しい
* 一部のプラットフォームではメモリ資源が逼迫しており、自動ガベージコレクション機構を使えない
* さまざまな異なる GC 機構を持つ高級言語から呼べる基盤的な共通コンポーネントライブラリを書きたい。GC を内蔵する言語は、異なる GC を使う言語と同一プロセス内で効率よく相互運用するのが難しい

したがって、このような位置づけのプログラミング言語には、適切な利用場面があるはずである：
1. 自動ガベージコレクション機構がなく、クロスプラットフォームが容易で、他のさまざまな高級言語と相互運用しやすい。共通汎用モジュールの実装に適する。
2. 安全を保証したうえで、使いやすさが良い。開発者への要求が低く、開発生産性が十分にある。
3. 性能水準は実用的だが、極限性能を追求する必要はなく、ハードウェアの潜在能力をすべて搾り取る必要もない。

このような設計は Rust 言語の位置づけとは合わないため、この変更は新しいプログラミング言語を始めて試みるしかない。

Zinc 言語の位置づけは Swift 言語に似ており、核心的な特徴は：ガベージコレクションなし + 安全 + 使いやすさ、である。
同時にスレッド安全という利点も備えており、これは Swift にはない。

### 2. Zinc 言語と Rust 言語の比較は？

* Rust は「ゼロコスト抽象」原則を堅持し、Zinc はこの設計原則を捨てた。実行性能と使いやすさを両立できないときは、使いやすさを優先する。
* Rust は「所有権 + ライフタイム」機構でメモリ安全を保証し、借用検査器がコンパイル時に aliasing XOR mutation を検査する。Zinc は参照カウントと借用機構でメモリ安全を保証し、コンパイル検査規則はずっと緩い。borrow checker を削除したことで、Zinc の使いやすさは Rust に比べて大幅に改善されている。
* Rust はインスタンス化方式でジェネリクスを実装し、Zinc は表渡し方式でジェネリクスを実装する。これは、Rust はジェネリックコードをバイナリライブラリとして対外公開するのに向かず、Zinc はそれができることを意味する。動的リンクライブラリと ABI 安定性のサポートは、Zinc 言語の今後の重要な目標である。
* Rust はメモリ安全・スレッド安全を保証し、Zinc 言語も同じくメモリ安全・スレッド安全を保証する。安全性の面では弱めておらず、一定の性能コストを払っているだけである。

要するに、構文・意味論の層では Zinc は Rust 言語に非常に近く、実行層では Zinc は Swift 言語に非常に近い。

### 3. なぜ Zinc と名付けたのか？

Rust は錆び・腐食を表し、Zinc は亜鉛金属を表す。亜鉛という金属には次の特徴がある：

>
> 亜鉛は空気中で酸素と反応しやすく、酸化亜鉛層、すなわち亜鉛塊表面の不動態層を形成する。
> 不動態層には一定の保護作用があり、さらなる酸化腐食を抑制できる。
> 亜鉛の最も主要な用途は、腐食防止のための鉄の亜鉛めっきである。
>
> Zinc is most commonly used as an anti-corrosion agent, and galvanization (coating of iron or steel) is the most familiar form.
> (from: https://en.wikipedia.org/wiki/Zinc)
>

この単語は、この言語の本質を反映している：Zinc 言語は表面的には Rust 言語に似ているが、表層の構文の下では、その思想の核は Rust とは相容れない。

偶然にも、この語は中国語では耳当たりが良く、「新言語」と同音である。

### 4. なぜ主なメモリ管理機構として参照カウント reference counting (RC) を選んだのか？

RC の利点：
* RC の一つの利点は、メモリ安全を容易に実現できることである。メモリ安全を実現する理論的基礎は "aliasing xor mutation" である。RC は aliasing の追跡に特に適しており、その上で copy-on-write を組み合わせれば、良い安全性を実現できる。
* RC は Zinc 言語のスレッド安全に関する設計と非常によく合う。スレッド安全と RC メモリ管理は、互いに補い合い、互いに成り立たせ合う。これが Zinc が GC を使えない核心的な理由である。GC を採用すると、Zinc は現在のスレッド安全水準に到達できない。
* RC のもう一つの非常に良い利点は、単純であることである。これは外部環境への制約条件が少ないことを意味し、したがって他のどの言語との相互運用も単純である。一方 GC は実装の細部が複雑すぎ、異なる GC 機構を同一プロセス内で効率よく共存させるのは難しい。GC を内蔵する言語が、異なる GC 機構の言語と相互運用するのは、自ら苦労を買うことになり、非常に不便である。

RC の欠点：
* RC の一つの欠点は、循環参照によるリーク問題を解決できないことである。しかしこれはメモリ安全問題ではなく、影響は相対的に小さい。しかもシステムプログラミング言語の範囲では、他の言語（C++/Rust/Swift を含む）もこの問題を解決していない。メモリアロケータとデバッガをうまく連携させれば、この問題は開発・テスト段階で発見・解決しにくいものではない。この問題だけを解決するために、実行時にマークスイープ機構を足すのは代償が大きすぎ、Zinc の位置づけに合わない。もちろん、テスト段階でのみ使うヒープメモリスキャナを実装し、自動テストと組み合わせて、テストケース中の循環参照問題の発見を補助することには反対しない。
* RC のもう一つの欠点は、参照カウントの増減に原子命令を高頻度で使うと、実行性能があまり良くないことである。

しかし、いくつかの最適化手段を使って、実行性能をいくらか取り戻すことができる：
1. Zinc はもともと値意味論型の使用を奨励しており、多くの場合は動的メモリ割り当てが不要で、オブジェクトのメモリレイアウト制御能力も比較的良い。これはキャッシュに友好的であり、参照カウントポインタが現れる場面も減らせる。
2. Zinc は借用ポインタ型を残しており、借用ポインタ型のコピー、引数渡し、返却はいずれも参照カウントを変更しない。多くの場面では借用ポインタの方が RC ポインタより合理的である。
3. Zinc は move セマンティクスを残しており、この特性を合理的に使えば、参照カウントの発生頻度を大幅に減らせる。
4. Zinc の RC ポインタは言語組み込み型であり、ライブラリで模擬したものではない。したがってコンパイラは一部の場面で、コンパイラ最適化によって冗長な参照カウント増減操作を削除できる機会がある。
5. ユーザはより先進的なメモリアロケータ（mimalloc など）を libc 付属の malloc/free の代わりに使い、動的メモリの割り当てと解放の実行効率を上げる機会がある。
6. スレッド安全な言語特性を利用し、コンパイラはある RC ポインタとそのすべての複製が、確実に本スレッド内部でしか使われないと解析できる場合、それらのポインタに対応する参照カウント増減操作を非原子命令に翻訳できる。Zinc では、ポインタが指す型が `Sync` 制約を満たすときだけ、そのポインタは安全にスレッドをまたいで使える。ポインタが指すのが non-`Sync` 型であれば、そのポインタとそのすべての複製がスレッドをまたいで使われることはあり得ないと確信でき、ここに最適化の機会があり、非原子命令を使える。**これが、それを自動参照カウントポインタ（automatic reference counting）と呼ぶ理由でもある。ここでの文字 A は Automatic を表し、Atomic ではない。「自動」の主な意味は、コンパイラが原子命令か非原子命令かを自動で選んでくれることである。**

以上の違いは、他の言語で伝統的な atomic-rc に基づいて実装された参照カウント機構の性能水準に関する結論が、zinc には当てはまらないことを示している。伝統的な atomic-rc に比べ、Zinc はより良い性能最適化の潜在能力を持つ。

要するに、安全、性能、使いやすさは不可能三角である。
Zinc が安全と使いやすさを選んだとき、「ゼロコスト抽象」はできないことが運命づけられ、C/C++ と比べてある程度の性能損失は受け入れられる。
しかし、実行性能が特に悪くならないようにするための一連の最適化手段は依然としてある。

個人的な推測では、Arc は Zinc の性能ボトルネックではなく、ジェネリクス実装方式こそがボトルネックである。

### 5. このプロジェクトの目標は何か？

Rust の多くの面での設計は非常に優れており、それは周知の事実である。しかし同時に、Rust の学習と使用の敷居を下げたいという声も絶えない。
自分はずっと、安全なシステムプログラミング言語の範囲では、Rust の設計方向が唯一の解ではなく、他の設計空間もあると考えている。
本プロジェクトの目的は、「安全なシステムプログラミング言語」の範囲で、他の設計可能性を探ることである。

しかし、漠然と「このようにも設計できる」と語るだけでは、誰も聞かない。プログラマのコミュニティには、非常に有名な言葉がある：
> 
> Talk is cheap, show me your code.
>

したがって、すべての考えを本当に実装するプロジェクトが必要であり、そうしてこそ説得力がある。

このプロジェクトの核心的な設計方向は：
**Rust の安全性を保ち、実行性能を少し犠牲にして、より良い使いやすさと引き換えにしたら、どのような姿になるか。**

その上で、いくつかの副次的な目標もある：
1. 言語機能を簡略化し、大風呂敷を広げることに反対する。異なる言語機能をできるだけ直交させ、互いに影響させず、言語機能同士を自由に組み合わせて使えるようにする。意味論規則にパッチを当て、さまざまな特殊規則を設けることをできるだけ避ける。ユーザの思考負担を軽くする。
2. コンパイラの実装を簡略化する。Rust コンパイラはすでに複雑すぎ、完全に理解できる人はほとんどいない。このような超複雑なプロジェクトは、持続的に進歩・進化するのが難しい。ある言語機能の実装が複雑すぎるなら、それはしばしば、言語の利用者もその機能を完全に掌握できない可能性が高いことを意味する。それでは、そのような機能は最初から導入すべきではない。
3. 大規模プロジェクトのコンパイル速度問題に関心を持ち、良好な IDE ヒント機能を提供する。これはコンパイラの実装問題であるだけでなく、言語機能の設計問題でもある。
4. コンパイル即サービス（compiler as a service）の理念を実践する。コンパイラをブラックボックスにせず、それ自体の各コンポーネントを公共ライブラリとしてコミュニティに公開して使うべきである。コンパイラの各コンポーネントは、使いやすい公開 API を持つべきである。これは周辺生態の発展を大いに促進する。
5. コンパイル型言語に基づく、より良い動的性のサポート。これには、ジェネリック関数をバイナリ成果物として公開すること、ジェネリック関数を仮想関数として使うこと、動的リンクライブラリをバイナリ配布物として使うこと、ABI 安定、動的ロード、ある程度のランタイムリフレクションなどの能力が含まれる。これらはいずれも Rust があまり得意でなく、Swift の方が良い面である。

### 6. Zinc 言語には特に革新的なところがなく、既存の他言語の特性を並べ替えて組み合わせただけだが、意味はあるのか？

意味はある。本プロジェクトの目的は革新ではなく、安全と使いやすさのためである。これらの特性の組み合わせの最終結果として、ユーザが安全、使いやすさ、需要場面への適合を感じられれば十分である。ユーザの需要を満たすことこそが自分の目標であり、革新のための革新ではない。

システムプログラミング分野で選べるプログラミング言語は、それほど豊富ではない。著者は、依然として、特に適したプログラミング言語がない場面が存在すると考える。

* C/C++ は非常に強力だが、コード中に未定義動作が現れたとき、大規模なコードから bug を探すのは極めて苦痛である。普通のユーザにとって、ほとんどの場面では極限性能は不要であり、わずかな実行性能を犠牲にして安全性を上げるのは、そうした状況では割に合うやり方である。
* Rust は優れたプログラミング言語だが、一部の特性が複雑すぎ、プログラミングパラダイムが多くのユーザに友好的でなく、開発生産性が低く、動的リンクライブラリに友好的でなく、動的性が必要な場面にも向かない。
* Swift も優れており、native 言語として良い動的性サポートを持ち、同時にバイナリ互換性もサポートしており、これらはいずれも良い性質である。しかし Apple 社が掌握しており、基本的に Apple のプラットフォームのサポートに専念している。多くの場面で使いたいが使えない。同じくスレッド安全問題もある。
* Zig は新興のシステムプログラミング言語として、まだ十分に成熟していない。同じくメモリ安全・スレッド安全の問題もある。
* Zinc は、Rust と Swift 言語の利点をできるだけ吸収して作られたものである。第一に、安全面では Rust に揃え、コンパイル時にメモリ安全・スレッド安全を保証する。第二に、言語機能を簡略化し、使用難度を下げた。第三に、より良い動的性サポートであり、動的リンクライブラリのバイナリ互換な進化をサポートする。

工学分野に魔法はなく、異なる目標に対するトレードオフと取捨があるだけである。比較的よくある利用場面を見つけ、需要を満たす言語特性を設計することが、Zinc 言語設計の主な挑戦である。
著者は「GC なし & 安全性 & 開発の使いやすさ」という要求は比較的よくあり、市場には需要を完全に満たす十分な競争力のあるプログラミング言語が欠けていると考える。
「極限性能」「zero-cost abstraction」を追求する場面は、実際の実践では非常に少なく、性能を最優先とするプロジェクトには C/C++/Rust の使用を勧める。
Zinc 言語設計は、こうした需要を最優先にしてはならない。

この設計が有用だと思われたら、ぜひスターを付けるか、提案を出すか、PR を作成して、この言語の設計と実装に参加してほしい。

### 7. Zinc 言語は現在どのような状態か？

メモリ管理、スレッド安全などの核心特性はすでに設計が終わり、基礎的な標準ライブラリがある。これらの基礎特性に基づき、コンパイラのセルフホストも実現した。

現在の状態は概念実証段階（proof of concept）と言え、始めたばかりであり、本当に使える状態からはまだ遠い。
多くの重要な言語特性は、セルフホストを妨げない限り、実装していない。計画中の性能最適化、周辺ツール、標準ライブラリの充実なども、まだやっていない。
今後の継続的な発展と成熟には、まだ作業量が大きく、オープンソースコミュニティの力を借りて初めて完成しうる。

### 8. どのような場面が Zinc の使用に比較的適しているか？どのように普及させるつもりか？

新しい言語が、既存の成熟した生態を持つ古い言語の領域を奪おうとすると、難度は極めて高いと思う。逆に、萌芽期にある業界を見つけ、新しい場面を深く耕し、新しい生態を構築できれば、普及の難度は相対的にずっと低くなる。
ストックを奪うのではなくインクリメントを広げることで、普及コストを大幅に下げられる。

潜在力のあるいくつかの新しい場面：

1. スマートコネクテッドカー製品
2. ロボット場面
3. IoT デバイス、組み込みデバイス、さまざまな小型知能化デバイス
4. 人工知能分野


### 9. Zinc 言語はどのオープンソースライセンスを選んだか？

Zinc は最も緩い MIT オープンソースライセンスを選んだ。現在の時代、十分にオープンでないプログラミング言語は十分なコミュニティ参加者を引きつけられず、必ず死ぬ運命にあり、何の意味もないからである。
自分はこのプロジェクトがオープンソースであるだけでなく、オープンであってほしいと願っている。皆さんの意見と提案を非常に聞きたいし、皆さんに Zinc 言語の設計と実装への参加を歓迎する。
