# ジェネリクスと trait

## ジェネリクス

型定義と関数定義は、いずれもジェネリック引数を宣言できる。

### ジェネリック型

ユーザ定義型は、ジェネリック引数を持てる。
ジェネリック引数には二種類ある：ライフタイムジェネリック引数、型ジェネリック引数。ジェネリック引数リスト中の並び順は：ライフタイム引数が型引数の前である。

todo: 今後、定数ジェネリクス特性を入れるべきかどうかを検討する必要がある。swift がこの特性をサポートしない理由に注意する必要がある

```rust
struct S<'a, T> {
    p: &'a T
}

enum E<T> {
    A(T), B(Int)
}
```

型定義は任意の `where` 節をサポートする。`where` 節は次を表現できる：ライフタイム同士の生存関係、および型が trait 制約を満たすかどうかの関係。

ジェネリック型の使用には、ジェネリック実引数を提供する必要がある。

```rust
fn main() {
    let v = 1;
    let x: S<Int> = S { .p = &v };
}
```

### ジェネリック関数

関数もジェネリクスをサポートする。ジェネリック型と同様に、ジェネリック引数もライフタイムジェネリック引数、型ジェネリック引数をサポートする。
ジェネリック関数も任意の `where` 節をサポートする。

```
fn swap<'a, T>(lhs: &'a mut T, rhs: &'a mut T) {}
```

注意：zinc ではジェネリック関数呼び出し構文が変わっており、rust の turbo fish 構文を避ける。

<details>

<summary>turbo fish 構文とは何か</summary>

<div style="border: 1px solid black; padding: 10px;">

Rust の構文設計では、ジェネリック関数呼び出しで、ジェネリック関数定義と同じ構文を直接使うと、構文曖昧性が起きる。例は次のとおり：
```rust
fn main() {
    let (the, guardian, stands, resolute) = ("the", "Turbofish", "remains", "undefeated");
    let _: (Bool, Bool) = (the<guardian, stands>(resolute)); // この行はどういう意味か？
}
```

この曖昧性の核心は、小なり演算子とジェネリクスの山括弧が同じ記号を再利用していることであり、上のこの行には二通りの理解の仕方がある：
1. これは丸括弧の中の一つのジェネリック関数呼び出しであり、関数名は `the`、ジェネリック引数は `guardian` `stands`、関数引数は `resolute` である
2. これは二つの要素を持つ tuple である。最初の要素は `the<guardian` からなる比較演算、二番目の要素は `stands>(resolute)` からなる比較演算である。

この構文衝突問題を解決するため、Rust はジェネリック関数を呼び出すとき、関数名の後ろに `::` を付けることを要求する。したがって正しい呼び出し構文は：
```
the::<guardian, stands>(resolute)
```

これが turbo fish 構文である。たとえば `Vec::<i32>::with_capacity(16)`。

</details>

<br/>

Rust の turbo fish 構文は構文解析の曖昧性問題を解消したが、構文の不一致をもたらし、美しくない。
Zinc は別の設計を採用し、構文曖昧性問題を避けつつ、構文の一貫性も保った。

1. fully-qualified-call-syntax 中にジェネリック型が現れる場合は、一律 `type` キーワードで始める必要がある。例は次のとおり：
    * `(type Vec<Int>)::with_capacity(4)`  
      `Vec` が明示的にジェネリック実引数を携えているため、`Vec<Int>::with_capacity(4)` は構文エラーである。
    * `Vec::with_capacity(4)`  
      `Vec` のジェネリック引数を指定しなくてもよく、ジェネリック引数は文脈から推論でき、このとき type 接頭辞を書かなくてもよい。
    * `(type Vec<String> as Default)::default()`  
      型名と対応する trait 名を明確に指定し、完全限定構文で特定の関数を呼ぶことを許す。これは、異なる trait 中のメンバ関数が同名であってよく、かつ同じ型に対して impl しても衝突が起きないことを意味する。

2. 構造体初期化およびパターンマッチは、一律型後置構文を採用する。例は次のとおり：
    * 構造体初期化: `let v = { .x = 1 } : S<Int>;`
    * 構造体パターンマッチ: `expr is { .x = 1 } : S<Int>`

3. ジェネリック関数呼び出しでは、ジェネリック引数リストを丸括弧の内部に書く必要がある。例は次のとおり：
    * `std::mem::size_of(<Int>)`

上記の変更の核心的な論理は、ジェネリクス付きの型名をすべて、特定の標識を接頭辞とする文脈中に一律に現れるようにすることである。
こうするとコンパイラは構文解析をするとき、対応する記号またはキーワードに出会えば、後ろに現れるのは必ず型であって式ではなく、これらの場所に現れる `<` `>` 記号は山括弧として理解すべきであり、小なり記号と大なり記号ではない、とわかる。

以下ではジェネリック関数呼び出し構文を重点的に述べる：
```
// 関数定義の構文は変わっていない
fn f<T>(arg: T) {}

// 関数呼び出しの構文は変わっている
fn main() {
    f(<Int>, 1); // ジェネリック実引数型を明示指定する
    f(1); // 型推論方式。ジェネリック実引数を省略する書き方
}
```

こう構文を設計する主な理由は、一つは turbo fish のような醜い構文を避けるため、もう一つは zinc のジェネリック関数の実装方式に合わせるためである。

特殊な場面のコンパイラ最適化を考えなければ、zinc のジェネリック関数は実装の観点から、デフォルトで表渡し方式によって実装される。コンパイラは上のこの関数 f を次のように翻訳する：
```
// 関数定義 f に対応する疑似 C コード:
void f(ZnTypeMeta * typeof_T, void * arg) { }
```

`f(<Int>, 1)` のような関数呼び出しを実行するとき、呼び出し側は本当に `Int` に対応する ZnTypeMeta を取り、それを一つの関数実引数としてこの f の中へ渡す。
したがって関数のジェネリック実引数リストを丸括弧の中に書く方が、zinc のジェネリック関数の実行意味論により合う。

zinc の関数ポインタ型は、ジェネリクスを含められる。`let pf: fn<T>(T)->() = f;`。
zinc は関数のカリー化（currying）を許さない。こう書くと `let pf: fn(Int)->() = f(<Int>);` はコンパイル失敗する。
このような関数インスタンス化場面では lambda を使ってほしい。こう書くことはできる：`let pf: fn(Int)->() = .{ (arg: Int)->() => f(<Int>, arg); };`。

ジェネリック関数をこう実装する主な利点は：ジェネリック関数も動的リンクライブラリで配布できることである。これは Swift 言語の一つの設計上の利点である。

このことは次のような場面で非常に有用である：
動的リンクライブラリ `a.so` を設計し、それが対外的にジェネリック関数インタフェースを公開し、アプリケーション `b.exe` に使われると仮定する。
すると、`a.so` の内部実装を更新するとき（もちろん API 破壊的変更はできない）、`b.exe` を再コンパイルせずに、プログラムも自動で正常に動作できる。
ジェネリクスがインスタンス化方式で実装されていると、この場面はサポートしにくい。上流ライブラリを更新すると、下流アプリケーションは再コンパイル・再デプロイしなければならない。

このほか、この設計にはいくつかの他の利点も付随する：
1. `virtual` 関数がジェネリクスを持てる。`virtual` 関数については後述の章を参照。
2. code size を減らし、コンパイル時間を減らす。

払う代償は、もちろん実行効率の低下である。こうすると多くのコンパイラ最適化が妨げられ、キャッシュにも友好的でなく、実行時間に不利である。
しかし実装の層では、ある特定の場面で、追加のコンパイルオプションによってジェネリクスインスタンス化を性能最適化手段として使うことを許し、code size と実行効率の間でより良い均衡を取ることができる。
1. 実行可能プログラムをコンパイルするとき（ライブラリではなく）は、完全にインスタンス化方式でジェネリクスを実装できる
2. ライブラリをコンパイルするときでも、動的リンクライブラリを単独で配布・デプロイする必要がなければ、インスタンス化方式でジェネリクスを実装できる

## trait

trait 定義の構文例は次のとおり：

```
trait TrName<T> : SuperTrait1 + SuperTrait2 where T: Condition {
    type AssocType;

    virtual fn method(&self);

    fn static_method() -> Self;
}
```

trait 定義は次をサポートする：
1. 任意のジェネリック引数
2. 任意の親型 trait。複数の親 trait をサポートし、`+` で区切る
3. 任意の where 条件節

trait 定義本体には次を含められる：
1. 関連型
2. 関連定数
3. 関連関数

### impl trait

trait は、異なる型に対する統一的な抽象に使える。ある具体型 `SomeType` がある trait `TrName` を実装したと指定する構文例は次のとおり：

```
impl TrName for SomeType {

}
```

impl ブロック
1. 内部の関数は単独で pub を指定できない
2. virtual も指定できない

impl Trait for Trait は許さない。

### trait を指すポインタ

trait の二通りの使用場面は：
1. ジェネリック制約の上限として使う
2. trait を指すポインタ型として使う

グローバル変数、局所変数、メンバ変数は、いずれも trait を型として直接使えない。しかし trait を指すポインタを型として使える。

型 `S` が `trait R` を実装していれば、`S` を指すポインタは、`R` を指すポインタへアップキャストできる。例は次のとおり：

```rust
struct S {}
trait R {
    virtual fn f(&self);
}
impl R for S {
    fn f(&self) {}
}

fn test(p: *S) {
    let p1: *R = p; // ok, アップキャスト
    p1.f();
}
```

### virtual 関数

trait を指すポインタは、trait のメンバ関数を呼べる。しかし制限があり、virtual で印したメンバ関数だけが、trait を指すポインタを通して呼べる。

> 注：
> Rust は `where Self: Sized` 構文を使って trait 中のメンバ関数を印し、それが "non-virtual" であることを示すことを許す。この構文は非常に異様で理解しにくい。zinc はキーワードを直接導入して印す方が読みやすい。
>

例は次のとおり：

```rust
trait TR {
    virtual fn f1(&self);
    fn f2(&self);
}

fn test(p: &TR) {
    p.f1(); // OK
    p.f2(); // コンパイルエラー。f2 は virtual 関数ではなく、trait を指すポインタを通して呼ぶことを許さない
}

fn test2<T>(arg: T) where T: TR {
    arg.f2(); // OK. 非 virtual 関数は依然としてジェネリクスの形式で呼べる。
}
```

同時に注意してほしい。trait 中に書いたすべての関数が virtual で修飾できるわけではない。virtual で修飾できる関数は、次の要求を満たす必要がある：
1. 最初の引数名は `self` でなければならず、型は `Self` を指すポインタ型である。`&self` `&mut self` `*self` `*weak self` はいずれもよい。
2. 最初の引数以外の他の引数は、`Self` 型および関連型を使えない
3. 関数の戻り型は、`Self` 型および関連型を使えない

例は次のとおり：
```
trait TR {
    virtual fn clone()->Self; // コンパイルエラー。virtual で修飾することを許さない。self 引数がなく、戻り型に Self を使っている。
    virtual fn g(arg: Int); // コンパイルエラー。virtual で修飾することを許さない。self 引数がない。
    virtual fn h(self);  // コンパイルエラー。virtual で修飾することを許さない。self 引数がポインタ型でない。
}
```

**注意**：virtual 関数は新しいジェネリック引数の導入をサポートする。例は次のとおり：
```
trait TR {
    virtual fn f<T>(&self, arg: T) where T: Hash + Ord + Default; // OK
}
```

> **計画中の機能**：今後 `* Trait1 + Trait2 + 'a` という書き方をサポートできる：
1. `+` を使うとき、具体型であってはならず、trait と trait の加算だけである
2. non-marker trait 型は一つだけである。自分自身との加算も不可である。
3. `* Trait1 + Trait2` は `*Trait1` または `*Trait2` へ暗黙変換できる

この特性はある場面では必須の機能になりうる。たとえば、`* MyTrait + Sync` によって、指す型が MyTrait 制約を満たすだけでなく Sync 制約も満たすことを表したい、という場合である。
他の方法では表現できない。

### 関連型

関連型は trait 中で定義する型プレースホルダであり、trait を実装するときに具体型を指定する必要がある。

例：
```rust
trait Container {
    type Item;
    
    fn add(&mut self, item: Self::Item);
    fn get(&self) -> Option<Self::Item>;
}

struct IntContainer {
    items: Vec<Int>,
}

impl Container for IntContainer {
    type Item = Int;
    
    fn add(&mut self, item: Int) {
        self.items.push(item);
    }
    
    fn get(&self) -> Option<Int> {
        self.items.last().copied()
    }
}
```

`Self` 型は、trait を実装する具体型を表す。

### trait 継承

zinc 中の trait は継承をサポートする。trait を定義するときに、ゼロ個または複数の親 trait を指定することを許す。

継承関係を持つ trait では、子型 trait を指すポインタは、親型 trait を指すポインタへ暗黙変換できる（ARC / BORROW ポインタはいずれもよい）。例は次のとおり：
```
trait TR: TR1 + TR2 + TR3 {}

fn test(p: *TR) {
    let p1: *TR1 = p; // OK
    let p2: *TR2 = p; // OK
    let p3: *TR3 = p; // OK
}
```

親型 trait を指すポインタも、パターンマッチによって子型 trait のポインタへダウンキャストできる。たとえば `is` `match` はいずれもできる。

```
trait TR: TR1 + TR2 + TR3 {}

fn test(p: *TR1) {
    if (p is p1: *TR) { // ダウンキャストを試みる。失敗しうる
        // p1 変数を使う
    }

    match (p) {
        p2: *TR => {}
        _ => {}
    }
}
```

その他の機能には次が含まれる：
1. 子 trait 中で associated type / const の値を指定することを許す
2. 子 trait 中で親 trait の関数本体を override することを許す
3. 多重継承をサポートし、多重継承場面の関数名衝突問題を考慮する必要がある
    1. 多重継承場面では、名前衝突を禁止する
    2. 多重継承場面では、親型の追加、継承順の調整は、いずれも ABI に影響する
    3. `trait TR1 : TR2 {}` と `trait TR1 where Self: TR2 {}` の意味は異なる。

### reuse

reuse 機構の目的は、メンバ変数・メンバ関数を再利用することである。reuse は一種の糖衣構文であり、ユーザがある実装を別の型へ委譲しやすくする。例は次のとおり：

```
struct S1 { }
impl TR1 for S1 {
    fn f1(&self, arg: Int) {}
}

struct S2 {
    base: S1  // メンバ変数の名前に制限はなく、何でもよい
}
impl TR1 for S2 {
    reuse self.base;  // 意味はこの impl ブロック中のメンバ関数が、いずれも self.base が実装した同じ trait のメンバ関数を再利用することである
}

// 以上のコードは次と等価である：
impl TR1 for S2 {
    // すべてのメンバ関数を一通り実装し、かつ関数本体はいずれも対応する `self.base` のメンバ関数を呼ぶ。
    fn f1(&self, arg: Int) {
        self.base.f1(arg);
    }
}

```

### オブジェクト指向プログラミングパラダイム

上記の言語特性の組み合わせによって、zinc もオブジェクト指向プログラミングパラダイムをサポートできるが、業界でよく見られる流儀（C++/Java/C#/Swift など）とは異なる。
Zinc の主な特徴は：`class` と class 継承をサポートしないことである。Zinc では trait だけが継承でき、trait を指すポインタだけが動的ディスパッチできる。

以下ではいくつかの面から、なぜこう設計するかを解説する。

1. 参照意味論の `class` 型は、メモリレイアウトが十分に柔軟でない

    メモリレイアウトの観点から、他の言語の参照意味論の class は、Zinc の中の `ARCポインタ+構造体` を合わせたものと見なせる。参照意味論だけを使うことを許し、それに対応するこの値意味論の構造体の使用を許さない。
    これは、class 型の変数を局所変数・メンバ変数として使うとき、いずれも動的メモリ割り当てがあり、いずれも一層の余分なポインタ間接参照があることを意味する。これは実際には表現能力の退化であり、強化ではない。
    一方、`ARCポインタ` と `構造体` をそれぞれユーザに提供して使わせれば、たとえば `Vec<S>` と `Vec<*S>` は異なる型であり、異なる場面で必要に応じて選べ、こうする方が柔軟で、ユーザにより大きな自由度がある。

    参照意味論の class は、どの場面でも、各オブジェクト内部に「オブジェクトヘッダ」ポインタを自前で持つ。一方 zinc のこの設計は、オブジェクト自体のメモリレイアウトに影響しない。

2. 参照意味論の型である `class` を増やすと、Zinc の型システムに不一致が現れ、多くの場面で特殊規則が必要になり、実装が複雑になる

    参照意味論の class は Zinc の型システムに一連の追加規則をもたらし、割に合わない。特に各種ポインタと class を組み合わせて使うときである。
    zinc にはすでに複数種のポインタ型が存在し、「参照意味論の class」自体は「暗黙のポインタ+構造体」の組み合わせとして理解できる。
    この機能は他の言語特性と直交しておらず、この「暗黙のポインタ」が結局 ARC なのか weak なのか借用なのか、ユーザに選択権が欠けているからである。

    次の場面を考える：`T` が class のとき、`&T` が表す意味は何か。この借用が指すのはこのポインタ変数自体なのか、それともこのオブジェクトの先頭アドレスなのか。
    class は `ARCポインタ` と `構造体` を強制的に結び付けているため、どの設計方案を選んでもいくつかの面倒がもたらされる。
    ポインタと構造体を分けた方が、意味論の表現がより明確である。型 `&S` は `S` への借用であり、型 `&*S` は `*S` への借用である。意味論が明確で、実装も単純である。

    次のジェネリクス場面の例を考えると、ジェネリクス中で値意味論の struct と参照意味論の class を統一するのが非常に面倒だとわかる：
    ```
    fn test<T>(arg: T) {
        // 参照意味論の class を導入すると、借用取得式と参照外し式は、値意味論型と参照意味論型に対する振る舞いが異なる。
        // ジェネリクス場面を考えると、実行時にいくつかの追加判定をして初めて、ジェネリクスでこの二通りの場合を統一抽象できる。
        let p: &T = &arg;
        let c: T = *p;
    }
    ```

3. C++ のように class および継承を導入するが、class は参照意味論でない、というやり方は可能か？

    C++ の中の class と struct の意味論の差は大きくない。値型をサポートし、ポインタと結び付いていない。
    しかし class の継承は、子型が親型の実装するすべてのインタフェースを受け入れなければならないことを意味し、これは問題がある。

    伝統的な継承の設計では、子型 class は必然的に親型 class のすべてのインタフェース（interface/protocol）を実装する。

    Zinc 中の `Send` のような trait を考えると、それはすべてのメンバ変数が `Send` を満たすことを要求する。継承を導入すると、次のような状況が現れる：親型が `Send` を実装し、
    子型が親型を継承したが、non-`Send` のメンバ変数を一つ増やし、子型に親型のすべてのメンバ変数・メンバメソッドを再利用させたいが `Send` は実装したくない、というのが、伝統的な継承の設計ではできない。

    継承を使う設計では、子型は親型から一部のインタフェースだけを選んで実装できない。上記の目的を達するには、継承を捨て、合成で実装するしかない。したがって継承は一部の場面でコード再利用を便利にするだけで、すべての場面に適応できない。

4. class の継承は、特殊な場面に対して特殊な規則を設計する必要がある

    1. 典型的な場面の一つは、多重継承場面である。
    伝統的な継承サポートの設計方案によれば、一つの class が複数の class を継承することをサポートするなら、「菱形継承」の場面を考えなければならない。
    C++ はこの場面に対して特殊な構文・意味論規則を設計し、同時に多くのプログラミング規範もこの特性に多くの制約を課している。
    Java/C#/Swift などの言語は、多重継承を直接サポートせず、コード再利用能力を制限し、意味論規則を簡略化した。

    2. もう一つの典型的な場面は、コンストラクタ場面である。言語ごとに規則が異なる。C++ ではコンストラクタ中で仮想関数を呼んでも、仮想関数効果がない。
    Java/C# のコンストラクタは未初期化変数にアクセスせず、フィールドの「0 値初期化」に依存する。
    Swift は「0 値初期化」をサポートできず、しかもコンストラクタ中で未初期化メンバに決してアクセスしないことを望むため、その規則が最も複雑である。
    コンストラクタは関数名を制限し、これはコンストラクタをサポートするには型に基づく関数オーバーロードをサポートしなければならないことを意味する。コンストラクタは戻り型を制限し、これは戻り型によってエラー処理ができないことを意味する。
    これらの設計理念はいずれも zinc と合わない。

    要するに、伝統的なプログラミング言語は class の継承をサポートしたが、class 継承という特性にはいくつかの追加の特殊な意味論規則が付随し、言語ごとに規則が異なり、あまり美しくない。

Zinc は Rust の設計発想に従い、より簡潔な一種の設計を採用した：trait 継承だけを許す。

Zinc の設計はユーザにとって理解と使用がより容易である：
* すべてのメンバ変数の再利用は、一律「合成」の様式を採用する；
* すべてのメンバメソッドの再利用は、一律「reuse 機構」を採用する；
* 複数の型に統一的な公共インタフェースが必要なすべての場面は、一律「trait+impl」で完了する；
* 動的ディスパッチが必要なすべての場面は、一律「trait を指すポインタ」で完了する。

以上の規則はすべての型に適用される（組み込み型、enum、struct、tuple、文字列、配列など）。特例はない。以上の規則は OOP プログラミングパラダイムを十分完全にサポートする。表現能力に問題はなく、伝統言語がサポートする機能はすべて表現できる。一部の場合に構文がやや煩雑なだけである。

意味論規則は精簡で、一貫しており、直交している。

### メモリレイアウト

trait を指すポインタはファットポインタである。本節で言及するポインタ型には、`*T`, `*weak T`, `&T`, `&mut T`, `*raw T`, `*raw mut T` の六種が含まれる。

```rust
trait TRBase { virtual fn f1(&self); }
trait TRSub : TRBase { virtual fn f2(&self); }

struct S { i: Int }
impl TRBase for S { fn f1(&self) {} }
impl TRSub for S { fn f2(&self) {} }

fn main() {
    let p1: *S = box S{.i = 1}; // p1 は細いポインタである
    let p2: *TRSub = p1; // p2 はファットポインタである
    let p3: *TRBase = p2; // アップキャスト

    if p3 is psub: *TRSub {
        // ダウンキャスト
    }
    if p2 is ps: *S {
        // ダウンキャスト
    }
}
```

Zinc のファットポインタレイアウトは Rust と異なる。trait を指すポインタは 3 つのメンバを含む：
```
      p2
┌───────────────────┐
│ object_ptr        │→ オブジェクトの頭部を指す。オブジェクトは組み込み型、ユーザ定義の struct、enum など、いずれもよい。
│───────────────────│
│ typemeta_ptr      │→ オブジェクトの具体型の TypeMeta を指す。型の name, size などの情報を含み、デストラクタ関数ポインタ、コピー関数ポインタなども含む
│───────────────────│
│ vtable_ptr        │→ この具体型がこの trait に対応する仮想関数表を指す。関数ポインタからなる配列である
└───────────────────┘
```

* trait を指すポインタは、trait の virtual メンバ関数の呼び出しをサポートする。メンバ関数を呼ぶときは、vtable から対応位置の関数ポインタを取り出してから呼び、オフセット量はコンパイル時に確定する。

* trait を指すポインタは、パターンマッチによって他の型のポインタへの変換をサポートする。ファットポインタ中にオブジェクトのランタイム型情報が保存されているからである。実行時に、この trait ポインタが指すのがどの具体型かを判定でき、マッチが成功すれば、それが含む object_ptr を取り出して具体型のポインタとして使えばよい。ダウンキャストもサポートできる：`*TRBase` は実行時に `*TRSub` 型かどうかを判定できる。

* trait を指すポインタは、アップキャストをサポートする。`*TRSub` 型は `*TRBase` 型へ変換できる。

> 注：
> Rust の中で trait を指すポインタは trait object と呼ばれ、それもファットポインタであるが、ダウンキャストをサポートしない。`Any` という特殊な trait だけがダウンキャストをサポートでき、他の trait はいずれもサポートしない。
> ポインタ二つ分の大きさしかなく、やや太いが、十分には太くなく、Zinc がサポートしたいすべてのオブジェクト指向プログラミングパラダイムをサポートするには足りない。
>
> Swift の Protocol のメモリレイアウトを参考にすると、もう一つポインタを増やすだけでよいとわかる。Zinc がファットポインタのために設計した二つのメタデータ指向ポインタは、swift の value witness table と protocol witness table に類比できる。
>

## 共変 & 反変

|           |   'a   |   T   |   U   |
|-----------|--------|-------|-------|
| &'a T     |  共変  |  共変  |       |
| &'a mut T |  共変  |  不変  |       |
| *T        |        |  共変  |       |
| Mutable<T>|        |  不変  |       |
| Vec<T>    |        |  共変  |       |
| fn(T)->U  |        |  反変  |  共変  |
| *raw T    |        |  共変  |       |
| *raw mut T|        |  不変  |       |

今後、型の共変・反変機能を引き続きサポートできる。
`in` `out` キーワードはすでに予約済みである。

使用場面の例：
1. `Option<*Sub>` を `Option<*Base>` へ変換する
2. `Result<*SubR, *SubE>` を `Result<*BaseR, *BaseE>` へ変換する
3. `(*Sub, *Sub)` を `(*Base, *Base)` へ変換する
4. `fn(*Base)->*Sub` を `fn(*Sub)->*Base` へ変換する
