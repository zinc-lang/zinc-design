

## zno 파일 형식

컴파일러가 라이브러리 컴포넌트를 컴파일할 때, 대응하는 `.o` 바이너리 파일을 생성하는 것 외에, C 언어의 “헤더 파일”과 비슷한 것도 생성해야 하며, 모든 공개 인터페이스의 시그니처를 담아 하위 라이브러리가 쓰게 합니다.
zinc 언어가 생성하는 “헤더 파일”은 `.zno`를 파일 확장자로 쓰며, “산화아연”의 뜻에서 왔습니다.

`.zno` 파일 내용은 모든 공개 함수 시그니처, 타입 정의, 전역 변수 선언, impl 선언 등을 포함합니다. 컴포넌트를 넘어 인라인할 수 있는 모든 함수의 함수 본체도 포함합니다.

`.zno` 파일 형식은 순수 텍스트 형식, 또는 어떤 사용자 정의 바이너리 형식이든 원리적으로는 문제없습니다. 하지만 컴파일 속도를 높이기 위해 최종적으로 sqlite 파일을 채택해 구현했습니다. 아래에서 이렇게 한 이유를 설명합니다.

이런 장면을 생각해 봅시다. 대형 프로젝트에 매우 복잡하고 많은 컴포넌트가 포함되어 있습니다. 컴포넌트 a가 컴포넌트 b에 의존하고, b는 또 다른 컴포넌트 c, d, e 등에 의존합니다.
단순한 텍스트 파일 형식을 쓰면, 컴포넌트 a를 컴파일할 때 컴포넌트 b의 zno 파일을 전부 읽어 들일 뿐 아니라, 컴포넌트 b가 의존하는 다른 모든 컴포넌트의 zno 파일도 전부 읽어 들인 뒤 문법·의미 분석을 해야 합니다.
C/C++ 컴파일러의 `#include` 기능이 바로 이렇게 구현되어 있습니다.
하지만 Zinc의 모듈 시스템에는 C/C++의 설계를 그대로 베끼는 것이 적합하지 않습니다. C/C++는 파일을 컴파일 단위로 하고, Zinc는 component를 컴파일 단위로 하며, 컴파일 단위의 체량이 더 크기 때문입니다.
비유하면, 비교적 큰 C/C++ 모듈이 직접·간접으로 쓰는 모든 헤더 파일을 하나의 거대한 파일로 합친 뒤, 다른 파일이 언제나 이 거대한 헤더 파일을 include하고, 수동으로 여러 소형 헤더 파일로 나누지 않는 것과 같습니다.
게다가 컴포넌트를 넘는 인라인 요구도 고려해야 하며, 어떤 함수의 함수 본체도 이 헤더 파일에 기록해야 합니다.
대형 프로젝트에서 너무 큰 헤더 파일은 컴파일 시간에 큰 낭비입니다. 이 많은 zno 안의 대부분 내용은 컴포넌트 a를 컴파일할 때 쓰이지 않기 때문입니다.
따라서 zno가 필요에 따라 읽는 기능을 지원하게 해, 컴파일 a할 때 필요한 것만 읽게 할 수 없을까요? 각 “선언” 단위로 zno 파일을 나누고, 파일 단위로 전체를 읽어 들이지 않는 것입니다.
예를 들어 컴포넌트 a가 컴포넌트 b의 함수 `fn f();` 하나만 단순하게 쓴다면, b 안의 다른 함수 선언, 타입 정의 등은 모두 컴포넌트 a와 관계가 없고, b의 의존 항목도 a와 관계가 없음을 알 수 있습니다.
그러면 `b.zno` 파일에서 그런 함수 시그니처 하나만 골라 문법·의미 분석을 하고, 다른 내용은 신경 쓰지 않아도 됩니다. b의 zno 파일이 아무리 방대하고 의존 트리가 아무리 복잡해도, 이는 컴파일 a와 아무 관계가 없습니다.

위 목표를 달성하려면, 전체 헤더 파일을 서로 다른 선언에 따라 여러 부분으로 나누고 인덱스를 만들어 조회하기 쉽게 해야 하며, 바로 이것이 sqlite가 잘 도와줄 수 있는 일입니다.

sqlite 형식을 쓰는 이점은 다음과 같습니다:
1. sqlite는 “필요에 따라 읽는 기능”을 가장 편리하게 지원하는 형식입니다. 우리만의 파일 형식을 설계해 같은 효과를 내려면, 최종적으로 더 단순하고, 더 쓰기 어렵고, 버그가 더 많은 sqlite 형식 파일을 만들게 될 가능성이 큽니다.
2. 읽기·쓰기 속도가 빠르고, 파일 크기도 적당합니다. 기존 보조 도구가 있고, 성숙하고 안정적이며, 디버깅이 편리합니다. 이후 schema를 수정해 기능을 확장하기도 매우 편리합니다.
3. 현재 단계에서는 구현을 단순하게 하려고 sqlite에 직렬화한 소스 코드를 직접 저장하지만, 이후 중간 코드 IR을 저장하도록 바꿔 컴파일 속도를 더 높일 수도 있습니다. 이는 전체 설계를 수정할 필요가 없습니다.

zno 파일은 사람이 읽을 수 있는지를 신경 쓸 필요가 없습니다. 이 파일은 컴파일러가 쓰는 것이지, 사람이 읽는 것이 아니기 때문입니다.
사람이 읽는 기능은 문서 생성 도구에 포함되어야 하며, 아름다운 HTML 형식 문서를 생성하는 doc generator 도구를 제공해야 합니다. 우아한 조판, 코드 강조, 하이퍼링크, 검색 기능 등을 갖춰 사람이 읽기 쉽게 해야 합니다.

## 부트스트랩 bootstrapping

zinc 컴파일러 첫 번째 버전은 C++로 구현했고, 나중에 프론트엔드를 zinc로 다시 구현했습니다(물론 백엔드에 쓰는 LLVM 프레임워크는 포함하지 않음). 이렇게 한 목적은 몇 가지입니다:

1. 프로그래밍 업계에는 “Eating your own dog food”라는 명언이 있습니다. 설계자는 먼저 자신이 설계한 제품을 사랑하고, 장기적으로 자신의 제품을 집중적으로 써야, Plan-Do-Check-Act 순환을 효과적으로 형성해 문제를 일찍 발견하고 개선하는 데 도움이 됩니다. 저는 일상 업무의 프로그래밍 언어가 바로 zinc이기를 매우 바라며, 그것을 직접 써서 자신의 컴파일러를 작성하면 일차적인 사용 경험을 가장 빨리 쌓고, 문제를 빠르게 발견하고 개선할 수 있습니다. 첫 번째 버전을 Rust로 구현하지 않은 것도 이와 관련됩니다. Rust의 사고 습관, 설계 패턴이 zinc와 크게 다르기 때문입니다. 예를 들어 Rust로 구현한 컴파일러 내부의 많은 자료구조는 포인터 대신 인덱스를 써야 하며, 이런 사고방식은 다른 언어와 차이가 큽니다. 나중에 zinc로 다시 쓸 것이 일찍부터 정해져 있었으므로, 첫 번째 버전을 C++로 쓰는 편이 낫고, 그렇다면 두 번째 버전은 주체 아키텍처를 바꾸지 않고 매끄럽게 이전할 수 있습니다.
2. 오픈소스 이후 다른 개발자의 기여를 받기 쉽습니다. 컴파일러 자체가 C++로 구현되어 있으면, 서로 모르는 오픈소스 기여자의 PR을 마주했을 때, 개인적으로 코드 검토를 잘하고 코드 품질을 유지하기 어렵다고 느낍니다. 반면 안전한 프로그래밍 언어로 구현한 기능을 검토하는 것은 훨씬 단순합니다.
3. compiler as a service 이념을 실천합니다. 잘 알려져 있듯이, 한 프로그래밍 언어는 컴파일러 하나를 구현하는 것이 전부가 아니며, 완전한 생태계 한 세트가 있어야 정말로 쓸모가 있습니다. 이 생태계의 도구 체인 부분에는 통합 개발 환경 IDE 지원, 코드 자동 포맷 도구, 패키지 관리 도구, 문서 생성 도구, 사용자 정의 lint 경고, 코드 품질 분석 등 일련의 도구가 포함됩니다. 이런 도구의 많은 부분은 컴파일러와 같은 논리를 공유해야 합니다. 따라서 컴파일러 자체의 각 부분을 호출하기 비교적 편리한 library로 만들고, 안전하고 쓰기 쉬운 API를 갖게 하면, 주변 도구를 구축하는 것이 반의 노력으로 배가의 효과를 냅니다. 반대로 컴파일러가 블랙박스이고 그 컴포넌트를 쉽게 재사용할 수 없으면, 주변 도구를 구축하는 데 대량의 반복 작업이 필요해 배가의 노력으로 반의 효과만 납니다. C++를 컴파일러 자체 각 하위 컴포넌트의 대외 API 인터페이스로 쓰면 충분히 안전하지 않고 쓰기 쉽지도 않습니다.
4. 이후의 메타프로그래밍(매크로, 사용자 정의 lint 등) 기능을 위한 기초를 닦습니다. 이른바 메타프로그래밍은 구현 층면에서 말하면 사실 컴파일러 플러그인 기능입니다. 컴파일러가 어떤 모듈을 동적으로 로드하고, 컴파일 과정에서 이런 플러그인의 기능을 실행해야 합니다. 물론 매크로 정의 자체는 zinc로 구현되기를 바랍니다. 게다가 zinc는 동적 링크 라이브러리로 컴파일하기에 비교적 적합한 언어이며, 컴파일된 라이브러리의 API는 제네릭, trait 등 고급 기능도 지원할 수 있습니다. 컴파일러가 호출 측이고 그것도 zinc로 구현되어 있으면, 이 플러그인 메커니즘이 매우 깨끗하고 간결합니다. 반대로 C++로 zinc의 동적 링크 라이브러리를 동적으로 로드하면, 할 수는 있지만 분명히 곁가지를 치는 번거로운 일입니다.

## 컴파일러 구조 소개

컴파일러는 다음 컴포넌트로 나뉩니다:
* zinc_cli 실행 프로그램, 아래 몇 가지 컴포넌트에 의존합니다. 내부에는 주로 명령줄 처리 기능이 포함됩니다.
    * options
    * session
* zinc_frontend 컴파일러 프론트엔드, 문법·의미 검사를 담당하며, 여러 하위 모듈을 포함하고, 그중 가장 주요한 두 모듈은 다음과 같습니다:
    * zinc_syntax  주요 입력은 소스 코드, 출력은 SyntaxTree라는 자료구조입니다. 문법 오류 보고 기능을 포함합니다. lexer도 이 컴포넌트에 포함됩니다.
    * zinc_semantic  주요 입력은 SyntaxTree라는 자료구조, 출력은 SemanticModel이라는 자료구조입니다. 의미 오류 보고 기능을 포함합니다.
        * hir
        * mir
* zinc_backend 컴파일러 백엔드, 성능 최적화와 코드 생성을 담당하며, 여러 하위 모듈을 포함하고, 그중 가장 주요한 두 모듈은 다음과 같습니다:
    * optimization 성능 최적화, 입력은 SemanticModel이라는 자료구조이며, 그것을 수정·변환합니다
    * llvm_ir_gen 주요 입력은 SemanticModel이라는 자료구조, 출력은 LLVM IR입니다. 그 안에도 일부 성능 최적화가 포함됩니다.


이들은 모두 zinc_std에 의존하며, 이것이 zinc의 표준 라이브러리입니다.

## 매개변수 타입에 기반한 함수 오버로드를 지원하지 않음

주요 목적은 동적 링크 라이브러리로 컴포넌트를 배포하는 것을 더 잘 지원하기 위함입니다.

핵심 장면은 다음과 같습니다. 한 컴포넌트를 동적 링크 라이브러리로 대외에 배포할 때, 이후 라이브러리 버전을 업데이트할 때 하위 사용자가 코드를 다시 컴파일하지 않고 바로 링크해 쓸 수 있기를 기대합니다.

이제 매개변수 타입에 기반한 함수 오버로드를 지원한다고 가정하고, 이런 경우를 생각해 봅시다:
lib_v1에 함수가 하나 있고 시그니처가 `fn f(arg: *Base);`이며, lib_v2 버전에서 오버로드 버전 `fn f(arg: *Sub);`를 새로 추가하고 싶습니다. 여기서 `Sub`는 `Base`를 상속한 trait입니다.
하위 사용자가 코드를 다시 컴파일하지 않고 lib_v2와 함께 쓸 때, 코드는 여전히 실행되지만 영원히 `Base` 버전만 호출합니다. 이 신규 오버로드는 전혀 효과가 없습니다.

“매개변수 타입에 기반한 함수 오버로드를 지원하지 않는다”고 말할 때, 실제 뜻은 “컴파일 타임에 매개변수 타입에 기반해 함수 버전을 해석하는 것을 지원하지 않는다”는 것이며, 사용자에게 런타임에 함수 버전 해석을 하도록 강제합니다.

여전히 위 장면에서, 사용자가 lib_v2에서 `*Sub` 타입 매개변수에 추가 처리를 해야 한다면, 사용자는 오버로드 버전의 함수 시그니처를 새로 추가하는 것이 아니라 원래 함수의 함수 본체를 수정해야 합니다:
```
fn f(arg: *Base) {
    if (arg is s:*Sub) {
        // 패턴 매칭으로 판단, arg가 *Sub 타입이면 특수 논리를 실행
    } else {

    }
}
```
새 버전 lib_v2의 동적 링크 라이브러리가 배포된 뒤, 실행 프로그램을 다시 컴파일할 필요 없이 이 애플리케이션의 동작이 자동으로 업데이트됩니다.

이렇게 하면 물론 실행 효율을 희생합니다. 하지만 동적 링크 라이브러리의 체감 없는 업데이트를 구현하려면, 이 런타임 대가는 반드시 치러야 합니다. 컴파일 타임에 오버로드 해석을 하면 이런 동적성을 얻을 수 없습니다.

이 설계에는 표현 능력 문제가 없고, 실행 성능 문제만 있습니다. 그리고 실행 성능은 각종 최적화 조치로 일부를 메울 기회가 있습니다. 특히 사용자가 “ABI가 안정된 동적 링크 라이브러리를 배포”할 필요가 없을 때는, 컴파일 옵션으로 컴파일러에게 더 공격적인 최적화를 켜라고 알릴 수 있습니다.

## 예외(exception), 스택 되감기(unwind)가 없음

zinc 언어는 `panic` 키워드를 제공하며, 다른 언어의 `throw` 키워드에 비유할 수 있습니다. 하지만 다른 언어의 `throw`나 rust의 `panic!`과는 같은 것이 아닙니다.

Rust의 panic에는 두 가지 동작 모드가 있으며, 각각 `abort`와 `unwind`이고, `rustc`의 다음 컴파일 옵션으로 지정할 수 있습니다.
```
-C    panic=val -- panic strategy to compile crate with
```
* rust의 `panic`은 `abort` 전략에서 프로세스를 바로 종료하며, `catch_unwind` 함수는 작용하지 않습니다. libc의 `abort` 함수를 호출하는 것과 동등합니다.
* rust의 `panic`은 `unwind` 전략에서 스택 되감기(unwind)를 실행하고, 각 층 함수의 지역 변수의 소멸자를 호출하며, ARC 포인터의 참조 카운트 자동 감소 등을 포함하고, `catch_unwind`에 잡혀 스택 되감기 과정을 종료할 수 있습니다. 이 과정은 다른 언어의 exception과 비슷합니다.

zinc의 `panic`은 단순히 함수 호출 스택을 출력한 뒤 abort합니다. unwind 과정이 없고, 잡힐 수 없으며, rust의 `panic`이 `abort` 전략일 때의 동작에만 해당합니다. zinc는 `unwind` 같은 동작을 지원하지 않습니다.

이 설계는 nikomatsakis의 이 [블로그](https://smallcultfollowing.com/babysteps/blog/2024/05/02/unwind-considered-harmful/)에서 영감을 받아 이렇게 선택한 것입니다. 이유는 다음과 같습니다:

1. unwind는 컴파일러, 표준 라이브러리의 구현 난이도를 높입니다
    1. unwind는 코드 크기를 늘립니다. 각 함수 호출마다 스택 되감기가 발생할 수 있으므로, 컴파일러는 스택 되감기가 발생할 수 있는 각 곳에서 어떤 지역 변수의 소멸자를 호출해야 하는지 기록해야 합니다.
    2. unwind는 최적화 기회를 줄입니다. 코드의 제어 흐름 그래프가 복잡해지고, 많은 곳에 unwind가 발생할 수 있는 제어 흐름이 하나 더 생겨, 컴파일러의 정적 분석에 영향을 줍니다.
    3. unwind는 표준 라이브러리가 구현할 때 예외 안전(exception safety) 문제를 고려하도록 요구합니다.
2. unwind는 사용자의 학습과 사용 비용을 높입니다
    1. zinc는 후발 언어로서 독립 생태계를 구축하기 어렵습니다. 대부분의 애플리케이션에서 사람들은 그중 어떤 모듈 하나만 zinc로 개발할 가능성이 크며, 이는 상호 운용이 중요함을 뜻합니다. zinc가 unwind 메커니즘을 도입하면, 이미 있는 C++의 exception, Rust의 panic과 어떤 관계인지, 서로 잡을 수 있는지? zinc로 작성한 하위 모듈을 상위 언어 Go/C#/Java/Javascript/Python 등이 호출하기를 바란다면, 이런 고급 언어가 zinc가 던진 panic을 잡을 수 있는지? 이 메커니즘이 사용자에게 과연 편리한가, 아니면 혼란을 더하는가?
    2. 언어에 unwind 메커니즘을 도입하면, 모든 서드파티 라이브러리가 설계할 때 예외 안전(exception safety) 문제를 고려해야 합니다. 특히 unsafe와 상호 운용이 관련될 때 이 일은 어렵습니다. zinc의 포지셔닝은 단순하고 쓰기 쉬움을 강조하는데, 일반 개발자에게도 예외 안전 설계를 고려하라고 요구하는 것은 요구가 조금 높은 것이 아닐까요?
    3. 어떤 오류 처리 장면이 `Option` `Result`로 표현하기 불편해, 반드시 잡을 수 있는 unwind로 해야 할까요? 이 특성을 구현하면 어떤 장면이 혜택을 받고, 그런 장면이 충분히 설득력이 있을까요?

저는 zinc의 생태계가 이렇게 건설되어야 한다고 생각합니다. 모든 “복구 가능한 오류”는 모두 `Option/Result` 타입을 반환하며, 이런 오류는 본 프로세스가 이런 오류를 만났을 때 처리 수단이 있음을 뜻합니다. 모든 “복구 불가능한 오류”는 모두 `panic`을 쓰며, 이런 오류의 뜻은 현재 애플리케이션이 실행 단계에서 이런 오류에 대해 어떤 처리 수단도 없다는 것이고, 이는 코드의 버그이며, 유일한 해결 방법은 돌아가 코드를 수정하고 프로그램을 다시 컴파일한 뒤 다시 실행하는 것입니다.

이 결정에 동의하지 않는 다른 사람이 있다면, 완전한 설계 제안서를 작성해 토론을 열어야 하며, 내용은 위의 의문에 충분히 답해야 합니다.
