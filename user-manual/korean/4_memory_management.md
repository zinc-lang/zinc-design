# 메모리 관리

## ARC 포인터

zinc는 참조 카운팅을 핵심 메모리 관리 전략으로 선택했습니다. ARC는 automatic reference counting을 나타냅니다. 이 automatic의 의미는, 참조 카운트를 가감할 때 컴파일러가 원자 명령 또는 비원자 명령을 자동으로 선택한다는 것입니다.

힙에 할당된 각 메모리 블록은 강한 참조와 약한 참조 두 개의 참조 카운트 값을 가지고 있습니다.
강한 참조 카운트가 0으로 떨어지면:
* 약한 참조 값이 0이 아니면, 이 메모리의 소멸자가 호출되지만 이 메모리는 해제되지 않습니다. 약한 참조 값도 0으로 떨어진 뒤에야 이 메모리를 해제합니다.
* 약한 참조 값이 0이면, 소멸자를 호출하고 이 메모리를 바로 해제합니다.

참조 카운트 포인터가 가장 자주 쓰이는 포인터 타입이므로, zinc는 가장 간결한 포인터 문법을 ARC 포인터 의미론에 대응시킵니다. `*T` 타입이 바로 `T` 타입을 가리키는 ARC 참조 카운트 포인터 타입입니다.

약한 참조 포인터 타입은 `*weak T`로 표현합니다. `T` 타입을 가리키는 약한 참조 포인터는 `T` 타입의 멤버 변수, 멤버 함수에 접근할 수 없고, 역참조할 수 없습니다.
약한 참조 포인터는 반드시 `std::ptr::upgrade` 함수를 통해 강한 참조 포인터 `*T`로 변환해야 `T`의 멤버 변수, 멤버 함수에 접근할 수 있습니다.

객체를 힙에 할당하려면 `box` 키워드를 사용합니다. `box <expr>` 표현식에서 `<expr>`의 타입이 `T`이면, `box <expr>` 표현식의 타입은 `*T`입니다.
`box` 표현식에서 메모리 할당이 실패하면 바로 panic합니다.
사용자가 정말로 메모리 할당 오류를 수동으로 처리해야 한다면, 스스로 `std::alloc::try_box` 함수를 호출하고 반환값을 판단해 메모리 할당 성공 여부를 확인할 수 있습니다.
메모리 할당 실패를 수동으로 처리해야 하는 장면은 사실 zinc를 쓰기에 그리 적합하지 않습니다. 결국 표준 라이브러리 전체 구현이 OOM일 때 바로 panic하기 때문입니다. 애플리케이션 층에서만 메모리 할당 성공 여부를 판단하는 것으로는 부족합니다.


예시는 다음과 같습니다:
```rust
let x: MyObj = MyObj::new();  // MyObj::new()가 반환하는 것이 MyObj 타입이라면
let y: *MyObj = box MyObj::new(); // box MyObj::new()가 반환하는 것은 *MyObj 타입

let z = y; // z와 y는 같은 MyObj 타입 객체를 가리킴
```

정적 크기 타입(sized 타입을 말하며, 당분간 unsized 타입은 논의하지 않음)을 가리키는 ARC 포인터의 메모리 레이아웃은 아래와 같습니다. 매번 동적 메모리 할당 시 먼저 `malloc(sizeof(UInt) + sizeof(MyObj))`한 뒤 포인터를 객체의 첫 주소로 오프셋합니다.
ARC 포인터로 멤버 변수에 접근할 때 필요한 오프셋은 그 멤버가 객체 첫 주소에 대한 오프셋입니다.
```
                ┌──────────────────────┐
                │ strong_count: UShort │
                │ weak_count: UShort   │
ptr: *MyObj  →  │──────────────────────│
                │ field1               │
                │ ......               │
                └──────────────────────┘
```

순환 참조가 있는 경우, 고리 위에 약한 참조 포인터가 하나만 있으면 그 고리는 정상적으로 회수되고 누수가 발생하지 않습니다. 하지만 언제 약한 참조 포인터를 쓸지는 프로그래머가 스스로 지정해야 합니다.

zinc에는 Rust의 ownership 개념이 없고, `Box<T>` 의미론과 비슷한 타입도 없으며, move-only인 “소유권 타입”도 없습니다.

**주의**: `*mut T` 타입은 없습니다. 바인딩된 변수 자체가 mut이든 아니든, `*T` 타입은 그 멤버에 대해 항상 수정 권한이 있습니다.

예시:

```rust
struct S { m: i32, n: i32 }
fn main() {
    let p1: *S = box { .m = 1, .n = 2 }:S ;
    p1.m += 10; // OK, p1 변수 바인딩에 mut 수식이 없어도 멤버 변수를 수정할 권한이 있음

    p1 = box { .m = 10, .n = 20 }:S; // 오류, p1 변수 바인딩에 mut 수식이 없어 직접 대입할 수 없음
}
```

## 값 의미론과 참조 의미론

[값 의미론과 참조 의미론](https://isocpp.org/wiki/faq/value-vs-ref-semantics#val-vs-ref-semantics) 소개:
1. 값 의미론은 복사할 때 값을 한 벌 복제한다는 뜻이며, 새 변수와 옛 변수는 서로 아무 관계가 없습니다. 어느 하나를 수정해도 다른 변수에는 반영되지 않습니다.
2. 참조 의미론은 복사할 때 포인터를 복사한다는 뜻이며, 새 변수와 옛 변수는 공유 데이터가 있어, 이 공유 데이터의 수정이 두 변수에 동시에 영향을 줍니다.

판단 기준은 아래 의사 코드의 논리입니다:
```rust
let mut y: T = x;
modify(&mut y); // y를 수정
print(x);
print(y);
// y에 대한 수정이 어떤 경우에도 x에 영향을 주지 않으면, 타입 T는 값 의미론 타입이라고 할 수 있습니다. 그렇지 않으면 타입 T는 참조 의미론 타입입니다.
```

zinc는 사용자가 타입을 정의할 때 “값 의미론” 타입으로 설계하기를 장려합니다.

값 의미론으로 정의된 타입 `S`라면, 그에 대응하는 `*S` 타입이 참조 의미론이므로, 사용 측은 장면에 따라 `S` 또는 `*S` 타입을 쉽게 선택할 수 있습니다.
반면 타입 정의 시부터 “참조 의미론” 타입으로 설계하면, 그에 대응하는 “값 의미론” 타입을 얻기 어려워 사용자에게 불편합니다.

## 빌림

왜 빌림 포인터가 필요할까요?

ARC/WEAK 포인터만으로는 표현 능력이 부족하기 때문입니다.
`*T` 타입은 영원히 “동적 할당 객체”의 머리만 가리킬 수 있습니다. 동적 할당 객체는 반드시 참조 카운트 값을 가지고 있습니다. 참조 카운트 값을 조작해야 하고, 참조 카운트 값이 가리키는 주소의 고정 오프셋에 있음을 보장해야 하기 때문입니다.
객체의 중간을 가리키는 포인터가 필요하면 `*T` 타입 포인터를 쓸 수 없습니다.

이 언어의 모든 안전한 포인터가 객체 머리만 가리킬 수 있다면, 객체의 메모리 레이아웃이 조밀해질 수 없습니다. 이런 설계는 값 타입의 발휘에 불리합니다.

객체의 중간 부분에 주소를 취해 새 포인터를 얻는 것을 허용하면, 아래 그림과 같습니다:
```
                ┌───────────────────┐
                │ strong_count: u32 │
                │ weak_count: u32   │
ptr: *MyObj  →  │───────────────────│
                │ field1: i32       │
                │ field2: MyStruct  │ ← borrow_ptr: &MyStruct
                └───────────────────┘
```

그렇다면 이 borrow_ptr 포인터는 반드시 다음 특징을 갖습니다:
1. 런타임에 충분한 정보가 없어, 가리키는 객체 자체가 가진 참조 카운트를 찾을 수 없습니다
2. 런타임에 가리키는 객체의 수명을 능동적으로 제어할 능력이 없습니다

따라서 빌림 포인터의 수명은 반드시 컴파일 타임 정적 검사가 필요하며, 빌림 포인터가 반드시 빌려진 객체보다 짧게 살아 있음을 보장해야 합니다. 그렇지 않으면 댕글링 포인터 문제가 발생합니다.

그래서 zinc도 rust의 빌림 포인터와 수명 매개변수를 유지합니다. 빌림 포인터는 “주소 취하기” 연산으로만 얻을 수 있으며, 컴파일러는 컴파일 타임에 빌림 포인터의 생존 범위를 추적합니다.
서로 다른 읽기·쓰기 권한을 구분하기 위해, 빌림 포인터는 두 가지로 나뉩니다. 읽기·쓰기가 가능한 `&mut T` 타입과 읽기 전용인 `&T` 타입입니다. 대응하는 연산자 표현식도 `&mut <expr>`과 `&<expr>`입니다.

빌림 포인터는 ARC 포인터의 표현 능력에 대한 좋은 보완입니다:
1. ARC 포인터는 힙에 동적으로 할당된 객체만 가리킬 수 있습니다. 빌림 포인터는 힙 위의 객체도, 스택 위의 객체도 가리킬 수 있습니다.
2. ARC 포인터는 힙에 동적으로 할당된 객체의 머리만 가리킬 수 있고 포인터 산술을 지원하지 않습니다. 빌림 포인터는 객체의 머리 또는 중간을 가리킬 수 있으며, 멤버 변수에 대한 빌림 연산으로 포인터 오프셋을 구현할 수 있습니다.
3. `*T` 타입은 복사, 인자 전달 시 항상 참조 카운트를 증감해야 해 추가 성능 오버헤드가 있습니다. 빌림 포인터의 대입, 인자 전달, 반환은 참조 카운트 값을 조작할 필요가 없습니다. 빌림 포인터를 합리적으로 사용하면 중복된 참조 카운트 증감 연산을 줄이는 데 도움이 됩니다.

zinc와 rust의 빌림 포인터의 같은 점은 다음과 같습니다:
* 모두 수명 검사가 있습니다. 즉 컴파일러가 컴파일 타임에 검사해, 빌림 포인터 자체가 빌려진 객체보다 짧게 살아야 함을 보장합니다.
* 모두 읽기·쓰기 권한 검사가 있습니다. `&T`형 빌림은 읽기 권한만 있고 쓰기 권한이 없으며, `&mut T`형 빌림은 읽기·쓰기 권한이 있습니다.

zinc와 rust의 빌림 포인터의 다른 점은 다음과 같습니다:
* 가변성 규칙이 다릅니다. zinc에서 ARC 포인터 타입 `*T`는, 이 변수 바인딩 자체가 가변인지와 관계없이, 항상 이 변수를 통해 `&T`와 `&mut T` 두 가지 빌림을 얻을 수 있습니다.
* zinc에는 “소유권 타입”과 “빌림 검사 규칙”이 없습니다. 읽기·쓰기 빌림은 독점이 아닙니다. 의미 규칙이 훨씬 느슨합니다.


### 예시 1: 빌림이 스택 위 주소를 가리킴
```rust
struct S { m: Int, n: Int }
fn main() {
  // 임시 변수, 리터럴을 직접 가리킬 수 있음. 이때 컴파일러가 익명 지역 변수를 자동 생성한 뒤 빌림 포인터가 그것을 가리키게 함.
  let mut p2: &Int = &1;

  {
    let x1 = { .m = 1, .n = 2 }: S;
    let p1 = &mut x1; // 컴파일 오류, 읽기 전용 변수 x1에 대해 읽기·쓰기 빌림을 얻을 수 없음
    p2 = &x1.m; 
  }
  print(p2); // 컴파일 오류, x1이 p2보다 짧게 삶

  let mut x2 = { .m = 3, .n = 3 }: S;
  let p3 = &mut x2; // 올바름
  let p4 = &x2.n; // 올바름
  p3.m += 1;    // 올바름, p3에 쓰기 권한이 있음
  println(p4); // 올바름, p3과 p4가 동시에 존재해도 문제없고, p3에 배타성이 없음
}
```

### 예시 2: 빌림이 힙 위 주소를 가리킴

zinc 코드 예시는 다음과 같습니다:

```rust
fn main() {
  let mut b: *Int = box 1_i;

  let p1: &Int = &*b; // 허용, 힙 위 주소를 가리킴
  let p2: &mut Int = &mut *b; // 허용, 힙 위 주소를 가리킴

  // p1/p2는 동시에 존재할 수 있으며, mut형 빌림에 배타성이 없음
  println(f"$(p1)");
  *p2 += 1;
  println(f"$(p2)"); 

  b = box 10_i; // b를 다시 대입

  // p1/p2/b를 읽고 써도 문제없고, p1/p2는 무효화되지 않음
  println(f"$(p1)");
  *p2 += 1;
  println(f"$(p2)"); 
  println(f"$(b)");
}
```
위 코드 예시를 Rust로 작성하고 `*Int`를 `Box<i32>`로 바꾸면 컴파일 오류가 발생합니다. Rust의 가변 빌림은 독점이라 다른 빌림과 동시에 존재할 수 없기 때문입니다. 하지만 zinc는 컴파일을 통과하며 메모리 안전 문제도 없습니다.
이유는, zinc에서 ARC 포인터로 멤버 변수에 빌림을 취하는 장면에서 컴파일러가 일률적으로 추가 임시 변수를 생성해 b를 한 번 복사하고, 참조 카운트 값을 +1한 뒤, 다시 멤버 변수에 빌림을 취하기 때문입니다. 이 임시 변수는 현재 block이 끝날 때 해제되며, 이때 참조 카운트가 자동으로 1 감소합니다.
따라서 뒤에 b에 대입해도 원래 가리키던 메모리가 바로 해제되지 않으며, p1/p2는 함수가 끝날 때까지 계속 유효하고, 그때야 원래 그 메모리가 해제됩니다.

아래는 다층 ARC 포인터 장면입니다:
```rust
struct Obj { p: *Int } // zinc에는 move 의미론의 포인터 타입이 없고, * 포인터만 쓸 수 있음.

fn main() {
  let mut o: *Obj = box { .p = box 1_i }:Obj;
  let q: &mut Int = &mut *o.p; // 이때는 p라는 포인터를 임시로 한 벌 복사하며, o를 복사하는 것이 아님
  *q = 2; // q에 수정 권한이 있음

  // ARC 포인터를 통해 빌림 포인터 생성
  let r: &mut Obj = &mut *o;
  r.p = box 10_i; // 허용, 컴파일 오류도 없고 댕글링 포인터도 없음.

  o = box { .p = box 100_i }:Obj; // 허용, 컴파일 오류도 없고 댕글링 포인터도 없음.

  println(*q); // q는 여전히 원래 값을 가리키며, 출력 결과는 2
  println(*r.p); // r.p는 새 값 100을 가리킴
}
```

요약하면, Arc 포인터로 새 빌림 포인터를 만들 때 zinc가 빌림 포인터가 댕글링 포인터가 되지 않게 하는 방법은, 보호적으로 참조 카운트를 늘리고 메모리 해제를 지연하는 것입니다.
컴파일러는 한 함수 내부에서 국소 정적 분석만 하면 메모리 안전을 보장하기에 충분합니다.

실행 성능 관점에서 논의하면: 이 설계는 분명히 실행 성능을 일부 희생하지만, 영향이 너무 크지는 않아야 합니다.

1. 앞에서 말한 것은 의미론 관점에서 코드의 기대 동작을 설명한 것이지, 최적화 관점에서 구체적인 명령을 기술한 것이 아닙니다.

   최적화 관점에서 보면, 새 빌림 포인터를 만들 때마다 일률적으로 참조 카운트를 늘릴 필요는 없습니다. 컴파일러가 컴파일 타임에 빌림 포인터가 가리키는 객체가 이 구간에서 반드시 살아 있음을 보장할 수 없을 때만, 안전을 위해 자동으로 참조 카운트를 늘려 메모리가 너무 일찍 해제되는 것을 피합니다.
   많은 장면에서 컴파일러는 충분한 정보가 있어, 이런 추가 참조 카운트 증감 연산을 바로 최적화해 없앱니다.

2. Rust와 비교하면, 어떤 힙 위 동적 할당 객체의 해제 시점이 미뤄집니다.

   메모리 안전을 보장하는 관점에서, 사실 마크-앤-스윕식 GC도 비슷한 발상입니다. 이 메모리를 가리키는 포인터가 아직 있으면, 런타임이 이 메모리를 해제하지 않음을 보장합니다.
   차이는 마크-앤-스윕식 GC가 순환 참조를 처리할 수 있는 반면, ARC는 처리하지 못한다는 것뿐입니다.
   주목할 점은, 함수 내부에서 만든 빌림 포인터는 분명히 본 함수보다 더 오래 살 수 없으므로, 어떤 메모리가 빌림 포인터 때문에 지연 해제되었다면, 그 빌림 포인터가 있는 코드 블록이 끝난 뒤에는 그 메모리도 해제할 수 있어 너무 오래 지연되지 않습니다.

3. 빌림 포인터를 합리적으로 활용하기만 하면, 모든 곳에서 ARC를 쓰는 설계에 비해 많은 경우 참조 카운트가 발생하는 빈도를 줄일 수 있습니다.
   1. 빌림 포인터 하나는 대입, 인자 전달, 반환에 쓸 때 참조 카운트를 수정할 필요가 없습니다
   2. 빌림 포인터를 통해 그 멤버의 빌림 포인터를 얻을 때, 멤버 변수가 ARC 포인터 타입이 아니면 참조 카운트를 수정할 필요가 없습니다
   3. ARC 포인터 타입의 멤버 변수에 빌림을 취하더라도, 최적화를 통해 일부 중복 참조 카운트 수정을 삭제할 수 있습니다. 이런 최적화는 어떤 ARC 포인터가 가리키는 객체가 어떤 수명 구간에서 해제될 위험이 없음을 컴파일러가 알 만큼 충분한 정보가 있는지에 달려 있습니다.


사용성 관점에서 논의하면: 이 설계는 Rust에 대한 큰 단순화입니다. **borrow checker를 없앴고, &mut형 빌림이 독점식이라는 제한이 없습니다**. 타입 층면에서 move only 타입을 없앴습니다.


메모리 레이아웃 관점에서 논의하면: ARC와 빌림 포인터의 협력은 프로그래머의 메모리 레이아웃 제어력을 보장할 수 있습니다.
1. 모든 타입의 메모리 레이아웃은 결정적이며, 컴파일러가 숨겨진 멤버를 암시적으로 삽입하지 않습니다.
2. `box` 키워드로 힙에 메모리를 할당한다고 명시할 때만, 동적 할당 메모리의 머리에 참조 카운트를 기록하며, 이때 추가 참조 카운트 메모리 오버헤드가 있습니다. 스택에서 쓰는 지역 변수에는 추가 참조 카운트 메모리 오버헤드가 없습니다.
3. 어떤 타입이든 멤버로 쓸 때는 직접 펼쳐지며, 추가 참조 카운트 메모리 오버헤드가 없습니다. 프로그래머가 멤버 변수가 ARC 타입이라고 지정하지 않는 한, 컴파일러는 box 연산과 참조 카운트 값을 암시적으로 삽입하지 않습니다.

## 조금 더 복잡한 빌림 취하기 연산

Zinc의 컨테이너 타입, 예를 들어 `Vec<T>`도 원소에 대한 빌림 연산을 지원합니다. 예시는 다음과 같습니다:

```rust
fn main() {
    let mut vec = (type Vec<Int>)::from(&[1i,2i,3i,4i] as Slice<Int>);
    let p: &Int = vec.index(1); // 이후 연산자 오버로드 기능을 추가하면 &vec[1]로 쓸 수 있음
    vec.push(5); // 여기서 vec가 확장될 수 있음
    println(*p); // p가 합법적임을 어떻게 보장하는가?
}
```

여기서 우리의 전략은 여전히, 빌림 `p: &Int`를 만들 때 내부 배열의 참조 카운트를 늘리고, `p`가 죽을 때 참조 카운트를 줄이는 것입니다.

문제는: `p`가 빌림이라면, 컴파일러는 이 빌림 변수가 죽을 때 참조 카운트 연산을 해야 한다는 것을, 그리고 어느 주소에서 참조 카운트 연산을 해야 한다는 것을 어떻게 알까요?

답: 위 코드가 컴파일되려면 컴파일러와 표준 라이브러리가 함께 협력해야 합니다. 여기서의 빌림 취하기 연산 `vec.index(1)`이 실제로 반환하는 것은 원시 빌림 타입 `&Int`가 아니라, 추가 데이터를 가진 구조체이며, “빌림 타입과 비슷한 스마트 포인터 타입”입니다.
그런 다음 이 임시 변수를 통해 다시 `deref` 연산을 해야 최종 `p: &Int` 빌림 포인터를 얻습니다.

```rust
// 이 타입은 Deref trait을 구현해, 컴파일러가 삽입하는 자동 역참조로 &T 타입을 얻을 수 있음; 그런 다음 &T 타입으로 원소에 접근.
// 이 타입은 Drop trait을 구현해, 소멸 시 대응하는 배열의 참조 카운트를 줄일 수 있음
struct ItemRef<'a, T> {
    ptr: *Shared<T>, // 배열 머리를 가리킴
    item: &'a T, // 진짜 빌림
}
```

위 코드는 컴파일러가 설탕을 제거한 뒤 실제로는 이런 뜻입니다:

```rust
fn main() {
    let mut vec = (type Vec<Int>)::from(&[1i,2i,3i,4i] as Slice<Int>);
    let _temp: ItemRef<Int> = vec.index(1); // 컴파일러가 암시적으로 추가한 지역 변수, 이는 “뚱뚱한 빌림 포인터”
    let p: &Int = _temp.deref(); // 컴파일러가 암시적으로 추가한 “자동 역참조” 연산
    // 주의: index의 반환값을 지역 변수에 바인딩하지 않으면, 이 _temp는 문장 블록이 끝난 뒤가 아니라 index 문장이 끝난 뒤 바로 소멸해야 함.

    vec.push(5); // 확장 시 copy-on-write 조건이 발동되어 새 공간을 할당하지만, 옛 공간의 참조 카운트가 0보다 커 해제하지 않으므로 p는 여전히 합법
    println(*p);
    // 컴파일러가 _temp 변수를 암시적으로 소멸하며, 이때 옛 공간의 참조 카운트가 0이 되어 원래 배열의 내용을 해제
}
```

주: “자동 역참조” 규칙은 패턴 매칭, 인자 전달, 반환 장면에서 `T: Deref<U>`가 있으면 `T`가 `deref` 멤버 함수를 자동 호출해 `U` 타입으로 변환될 수 있다는 것입니다.

위 목표를 달성하기 위해, zinc 표준 라이브러리의 Index trait은 이렇게 정의되어 있습니다:
```
pub trait Index<Idx>
{
    type Output<'a>;

    fn index<'s>(&'s self, index: Idx) -> Self::Output<'s>;
}
```

주의할 점은 index 함수의 반환 타입이 더 이상 고정된 원시 빌림 타입 `&Item`이 아니라, `&Item`과 다른 데이터를 함께 캡슐화한 구조체 타입 `struct ItemRef<'a, Item>`이라는 것입니다.
이를 사용자 정의 스마트 포인터 타입으로 볼 수 있으며, “원시 빌림 타입에 추가 메타데이터를 실어 준” 타입이고, 일종의 “뚱뚱한 빌림 포인터”로 볼 수 있습니다.
따라서 이 `Output` 연관 타입도 반드시 타입 생성자로 정의되어야 하며, 즉 Rust의 generic associated type입니다.
이 포인터에는 구체 원소에 대한 빌림뿐 아니라 내부 배열 머리에 대한 포인터도 포함되며, 이 뚱뚱한 포인터는 소멸자를 가져 런타임에 참조 카운트 값을 올바르게 유지할 충분한 정보가 있습니다.

의미 분석 관점만 보면, 이렇게 하는 것이 성능에 미치는 영향이 커 보입니다. 하지만 여기서 쓰는 `index` `deref` `drop` 몇 가지 핵심 함수를 모두 인라인한다고 생각하면, 성능 최적화 단계에서 추가 참조 카운트 연산을 완전히 삭제할 수 있습니다:
1. main 함수에서 push 등 수정 함수를 호출한 적이 없고, vec에 가변 빌림을 취한 적이 없다면, 컴파일러는 이 메모리에 해제 위험이 없음을 알 충분한 정보가 있어, 모든 추가 참조 카운트 가감 연산과 여분의 지역 변수를 전부 삭제할 수 있습니다.
2. main 함수에서 vec에 가변 빌림을 취해 다른 함수로 전달해 쓰는 경우가 있으면, 컴파일러는 vec가 수정될 수 있는지 확신할 수 없으므로, 이때 보호적 참조 카운트 연산은 필수이며, 이는 성능 낭비가 아닙니다.

## zinc는 고전적인 반복자 무효화 문제를 어떻게 해결하는가

Rust의 메모리 안전 특성을 설명할 때, 다음은 고전적인 예입니다:

```rust
///// Rust code
fn main() {
    let mut vec: Vec<i32> = Vec::from(&[1i,2i,3i]);
    for ref _i in &vec {
        vec.push(4);
    }
}
```

Rust는 이 예에 대해 컴파일 오류를 냅니다. `vec.iter()`가 `vec`에 대한 읽기 전용 빌림을 만들어 반복자 안에 저장하고, `vec.push`는 `vec`에 대한 읽기·쓰기 빌림을 만들어야 하기 때문입니다.
Rust의 빌림 검사 규칙에 따르면 둘 사이에 충돌이 발생하므로 컴파일러가 오류를 내며, 반복자 무효화 문제를 효과적으로 막아 C++에서 흔한 일종의 미정의 동작을 피합니다. 이는 Rust가 칭찬받을 장점입니다.

Zinc는 다른 방식으로 안전을 보장합니다. 아래는 Zinc의 대응 코드로, 소스 코드 층면에서는 매우 비슷해 보이지만 실제 실행 효과는 Rust와 큰 차이가 있습니다:

```rust
fn main() {
    let mut vec: Vec<Int> = (type Vec<Int>)::from(&[1i,2i,3i,4i] as Slice<Int>);
    for ref _i in vec {
        vec.push(4);
    }
}
```

1. zinc에는 “소유권 타입”이 없으므로, `Vec<T>`는 move 의미론이 아니라 copy 의미론입니다. `let vec2 = vec;`를 마음대로 할 수 있고, 그래도 `vec` 변수를 계속 쓸 수 있습니다.
2. `Vec<T>`가 copy 의미론이라고 해서, 복사할 때 바로 모든 멤버를 한 벌 복사한다는 뜻은 아니며, copy-on-write 최적화를 구현했습니다.
`Vec<T>`를 복사할 때는 얕은 복사일 뿐이며, 내부 힙에 할당된 배열의 참조 카운트만 1 늘리고, 원소 내용은 실제로 복사하지 않습니다.
3. 깊은 복사는 `Vec<T>` 변수를 수정할 때 발생합니다. 수정할 때 내부 배열의 참조 카운트가 1보다 크면, 모든 원소를 한 벌 복사한 뒤 수정을 합니다.
4. 위 예에서 반복자를 만들 때 내부 배열의 참조 카운트를 1 늘립니다. 반복 과정에서 `vec`에 대한 쓰기 연산이 없으면, 깊은 복사는 영원히 발생하지 않습니다.
반복 과정에서 `vec.push`가 발생하면, 이때 깊은 복사를 발동해야 함을 발견하고, `vec` 내부에 새 배열을 만들고 끝에 4를 더합니다.
5. 하지만 반복자가 가리키는 배열은 변하지 않았고, 해제되지도 수정되지도 않았으므로 반복은 계속 실행됩니다. 반복자와 `vec`는 이미 완전히 다른 두 배열을 가리키므로, 어떤 미정의 동작도 없습니다.
6. for 루프 실행이 끝난 뒤 반복자의 수명이 끝나면, 소멸할 때 원래 배열의 참조 카운트를 1 줄이며, 이때야 원래 배열의 소멸과 해제가 발동됩니다.

따라서 zinc도 마찬가지로 “미정의 동작”을 피했고 “메모리 불안전”을 도입하지 않았지만, 일정한 성능 대가를 치렀으며, push 연산을 실행할 때 원래 `Vec<T>` 타입이 암시적으로 한 번 깊은 복사를 합니다.
이 대가는 받아들일 수 있습니다. C++처럼 미정의 동작을 갖고 싶지도 않고, Rust처럼 지나치게 엄격한 컴파일 타임 검사를 갖고 싶지도 않으며, “안전”과 “사용성”을 보장하는 전제 하에 실행 성능 손실은 이미 치러야 할 최소 대가입니다.
사용자가 이 깊은 복사를 아끼고 싶다면, 루프 과정에서 원래 vec를 수정하지 않도록 스스로 주의해야 합니다.

Rust에게 메모리 안전과 스레드 안전은 **설계 목표**입니다. “가변과 공유의 상호 배제 원칙” (alias XOR mutation principle)은 목표로 가는 **이론 기반**입니다.
소유권(ownership)과 빌림 검사기(borrow checker)는 **구현 수단**입니다. Zinc는 쓰기 시 복사(copy-on-write) 기술로 같은 목표를 구현하기로 선택했으며, 길은 달라도 같은 곳에 이릅니다.
또는 다른 각도에서 말하면, Zinc의 이 설계는 컴파일 단계의 “가변과 공유 상호 배제” (alias XOR mutation) 정적 검사를 런타임 단계 보장으로 바꾼 것입니다.
copy-on-write의 본질은 메모리를 수정할 때 그 메모리에 alias가 하나만 있음을 보장하는 것이며, ownership + borrow checker와 같은 곡조의 다른 표현입니다. 상세 대비는 다음과 같습니다:

* Rust의 컴파일 타임 ownership + borrow checker 검사는, 컴파일 타임에 객체에 유일한 mutable alias만 있음을 보장합니다. 하지만 동시에 여러 immutable alias가 존재할 수 있습니다.

  alias XOR mutation 원칙을 위반하면 컴파일 오류가 납니다.

* Rust의 `RefCell<T>`는 `borrow` `borrow_mut` 멤버 함수로 사용합니다. 런타임에 객체에 유일한 mutable alias만 있음을 보장하지만, 동시에 여러 immutable alias가 존재할 수 있습니다.

  alias XOR mutation 원칙을 위반하면 런타임에 panic하고 계속 실행을 거부합니다.

* Rust의 `RwLock<T>`는 `read` `write` 멤버 함수로 사용합니다. 런타임에 객체에 유일한 mutable alias만 있음을 보장하지만, 동시에 여러 immutable alias가 존재할 수 있습니다.

  alias XOR mutation 원칙을 위반하면 런타임에 현재 스레드를 막아 대기시키고, 조건을 만족한 뒤에 계속 실행합니다. `Mutex<T>`도 비슷하며, 한 블록의 데이터에 동시에 접근자가 하나만 있음을 보장합니다. 읽기·쓰기와 관계없이.

* Zinc의 copy-on-write 구현 방식은, immutable method 안에서는 ref-count 검사를 하지 않고, mutable method 안에서는 ref-count 검사를 해, 수정할 때 객체에 유일한 alias만 있음을 보장하는 것입니다.

  alias XOR mutation 원칙을 위반하면, 이 힙에 할당된 객체를 한 벌 복사합니다. 메모리를 수정/해제할 때 alias가 하나만 있음을 보장합니다.

위의 모든 구현 기술은 같은 "alias XOR mutation" 원칙을 충족할 수 있으며, 모두 “메모리 안전” 목표에 도달할 수 있습니다. Rust의 설계는 “메모리 안전”을 구현하는 선택 방안 중 하나일 뿐이며, 절대 유일하게 가능한 설계 방안이 아닙니다.

## 수명

이른바 수명이란, 변수가 프로그램 실행 과정에서 어느 구간에서 살아 있는지를 말합니다. 변수의 수명은 생성될 때 시작하고, 파괴될 때 끝납니다.

### 전역 변수의 수명

전역 변수는 프로그램 전체 실행 과정에서 살아 있으므로, 그 수명은 프로그램 시작부터 프로그램 끝까지 계속 존재합니다.

> **TODO**: 현재 구현에서는 모든 전역 변수가 소멸자를 호출하지 않습니다. 이후 이 설계가 합리적인지, 프로세스를 종료하기 전에 전역 변수를 소멸해야 하는지 논의해야 합니다.

### 임시 변수의 수명

임시 변수란 표현식이 생성했지만 구체적인 이름에 바인딩되지 않은 변수를 말합니다.

임시 변수의 수명이 끝나는 시점은 두 가지입니다. 하나는 현재 문장이 끝날 때 끝나는 것이고, 하나는 현재 문장 블록이 끝날 때 끝나는 것입니다. 더 긴 수명의 변수가 그것을 빌렸는지에 따라 달라집니다.

예시는 다음과 같습니다:
```rust
fn f() -> S { ... }
// S에 멤버 메서드 method가 있다고 가정
impl S {
  fn method(&self) -> &S { return self; }
}

fn test() {
  f(); // f()가 반환한 이 변수가 바로 임시 변수이며, 변수 이름에 바인딩되지 않음. 이 임시 변수는 문장이 끝날 때 수명이 끝남.

  let p1: &S = &f(); // f()가 반환한 임시 변수가 빌려졌고, 빌림의 수명이 이 문장을 넘음. 그렇다면 이 임시 변수의 수명은 문장 블록이 끝나는 위치까지 확장되며, 함수가 끝날 때 임시 변수가 파괴됨.

  let p2: &S = f().method(); // f()가 반환한 임시 변수가 빌려졌고, 빌림의 수명이 이 문장을 넘음. 그렇다면 이 임시 변수의 수명은 문장 블록이 끝나는 위치까지 확장되며, 함수가 끝날 때 임시 변수가 파괴됨.
  // p1 p2 사용
}
```

### 지역 변수의 수명

일반적인 경우, 지역 변수(함수 매개변수 포함)의 수명은 생성될 때 시작해 현재 코드 블록이 끝날 때 끝납니다.

non-lexical-lifetime 같은 것은 없으며, 필요도 없습니다. Rust가 이것을 도입한 것은 mut borrow 타입의 독점성 때문이며, 분석이 충분히 정밀하지 않으면 불필요한 컴파일 오류가 많이 나 사용자의 표현 능력을 제한합니다. 컴파일 타임에 mut borrow의 독점성을 검사하는 규칙이 없다면, 컴파일 검사 규칙을 완화할 방법도 생각할 필요가 없습니다.

* 사용자 정의 타입에는 `Drop trait`을 구현할 수 있으며, 이런 타입의 변수는 수명이 끝날 때 대응하는 소멸자를 자동 호출합니다.
* ARC 타입은 수명이 끝날 때 가리키는 힙 메모리 공간의 참조 카운트를 자동으로 1 줄입니다.
* 빌림 타입의 소멸자는 아무 일도 하지 않습니다.

예시는 다음과 같습니다:
```rust
struct S { m: i32 }
impl Drop for S {
  fn drop(&mut self) {
    println("drop S");
  }
}

fn test() {
  let s1 = { .m = 1 }:S;
  let s2 = s1; // 여기서 복사 발생

  // s1과 s2는 test가 끝날 때 소멸
}
```

앞에서 “일반적인 경우, 코드 블록이 끝날 때 지역 변수의 수명이 끝난다”고 한 것은, “특수 경우”도 있다는 뜻입니다. 특수 경우가 바로 `move` 표현식입니다.

zinc 언어에서 move 키워드 뒤에는 표현식을 붙일 수 있으며, 이를 move 표현식이라고 합니다. 이때 이동 의미론이 발생하고, 복사 의미론이 아닙니다.

```rust
fn test() {
  let x = { .m = 1 }:S;
  let y = move x;
  println(x.m); // 컴파일 오류, x의 수명이 이미 끝났으므로 뒤에서 x를 다시 쓸 수 없음
}
```

move하는 것이 ARC 포인터라면, 이 기능으로 일부 장면의 참조 카운트 증감 연산을 줄일 수 있습니다:
```rust
fn f(arg: *S) { }

fn test() {
  let s: *S = box { .m = 1 }:S;
  f(s); // 이렇게 호출하면, 인자 전달 시 복사가 발생해 참조 카운트가 1 늘고, f 함수 본체 끝에서 참조 카운트가 1 줄어듦. test 함수를 빠져나올 때 참조 카운트가 다시 1 줄어듦.
  f(move s); // 이렇게 호출하면, 인자 전달 시 참조 카운트가 자동으로 1 늘지 않고, test 함수 본체 끝에서 참조 카운트가 1 줄지도 않음을 보장할 수 있음. s의 수명이 f의 함수 본체 유지로 이전됨.
  // s가 move된 뒤 s를 다시 쓰면 컴파일 오류가 남

  // ...
}
```

변수 `x`의 수명을 앞당겨 끝내고 싶다면, `move x;` 문장을 사용해 move 표현식의 결과를 어떤 변수에도 바인딩하지 않으면, 이 x는 문장 블록 끝에서가 아니라 그 자리에서 소멸합니다.

요약하면, zinc의 move 의미론에서 선택권은 “타입 정의”에 있지 않으며, 모든 타입은 본디 복사하거나 이동할 수 있습니다.
move 의미론을 쓸지 여부의 선택권은 “표현식”에 있습니다. zinc는 move 의미론의 “표현식”을 제공하며, move 의미론의 “타입”을 제공하지 않습니다.

`return` 문장은 기본이 move 의미론이며, `return expr;`은 `return move expr;`과 동등하고, `move` 키워드를 명시적으로 쓸 필요가 없습니다.

## 소멸자와 `Drop`

소멸자는 객체의 멤버 함수입니다. 객체의 수명이 끝날 때 컴파일러가 명령을 자동 삽입해 소멸자를 호출합니다.

소멸자는 다음과 같은 일을 합니다:
1. 해당 타입이 구현한 `Drop::drop` 함수를 호출합니다. 없으면 호출하지 않습니다
2. 멤버 변수의 `Drop::drop` 함수를 호출합니다
3. 해당 타입에 포함된 모든 Arc 포인터와 Weak 포인터 타입 멤버 변수에 대응하는 참조 카운트를 1 줄입니다. 어떤 ARC 포인터가 가리키는 객체의 참조 카운트가 0으로 떨어지면, 그 객체의 소멸자를 자동 호출합니다.

소멸자는 영원히 컴파일러가 자동 생성하며, 사용자는 `Drop::drop` 함수의 동작만 제어할 수 있고, 그것은 소멸 과정의 일부일 뿐입니다.
어떤 타입과 그 모든 멤버에 `Drop::drop` 함수와 참조 카운트 타입 포인터가 없으면, 그 타입의 소멸자는 비어 있습니다.

일반적으로 사용자는 객체의 소멸자를 능동적으로 호출해서는 안 됩니다. 하지만 unsafe 코드를 쓸 때는, 사용자가 `unsafe fn destruct_in_place` 함수로 객체의 소멸자를 강제 호출하는 것을 허용합니다.

`Drop::drop` 함수는 영원히 사용자가 명시적으로 호출할 수 없습니다.

사용자 정의 타입 `impl std::mem::Drop` trait의 예시는 다음과 같습니다:

```rust
struct S {
  p: *i32,
  m: String,
}

impl Drop for S {
  fn drop(&mut self) {
    println("S is dropped.")
  }
}
```

주의: 사용자 정의 `Drop::drop` 함수는 멤버 변수의 소멸과 메모리 해제를 신경 쓸 필요가 없으며, 멤버 변수의 소멸자는 자동 호출됩니다.
