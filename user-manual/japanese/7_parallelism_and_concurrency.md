
# 並列と並行

## スレッド安全

Rust には比類のない利点がある：プログラムのスレッド安全をもともと保証することである。よく使われるプログラミング言語の中で、それは唯一無二である。Zinc 言語もスレッド安全というこの特徴を残したい。

### Send/Sync trait

スレッドをまたいで安全に渡せるすべての型に、統一的な印を付け、それを `Send trait` と呼ぶ。

まず、[値意味論と参照意味論](https://isocpp.org/wiki/faq/value-vs-ref-semantics#val-vs-ref-semantics) の意味を振り返る。

見てわかるように、値意味論の型はもともと `Send trait` の要求を満たす。例は次のとおり：
1. 基礎型 Bool, Char, Int などは値意味論に合うため、確かに `Send trait` を満たす。
2. 合成型、たとえば tuple/struct/enum などは、すべてのメンバが `Send` を満たすなら、それも必ず値意味論であるため、この種の型も `Send trait` を満たす。
3. ポインタ型は値意味論に合わず、一般の場合 `*T` は `Send` trait を満たさない。しかし具体的な状況に応じた分析も必要である。ポインタ型、あるいは内部にポインタメンバを含む型は、次の二通りの場合にも `Send` を満たす：
    1. copy-on-write 機構によって値意味論を実現したものも、`Send trait` を満たす。たとえば `String` 型は、内部にポインタメンバを含むが、その実装が copy-on-write によって「値意味論」を保証しているため、この種の型も `Send trait` を満たす。`Vec<T>` のような型については、copy-on-write を実装していてもジェネリクスを持つため、`Send` を満たすかどうかには前提条件がある。`T: Send` のとき、かつそのときに限り、`Vec<T> : Send` である。
    2. スレッド同期機構によって、ポインタが指す内容がスレッド安全であることを保証したものも、`Send trait` を満たす。たとえば `*AtomicInt32` 型は、二つのスレッド中の異なるポインタが同じ `AtomicInt32` を指すことが起きうるが、`AtomicInt32` はスレッド同期をしているため、`*AtomicInt32` 型は `Send trait` を満たす。

したがって、もう一つの `Sync trait` を導入し、ある型自体がスレッド同期能力を持つことを表す。すると、`*T` 型については、`T` が `Sync` を満たすとき、かつそのときに限り、`*T` は `Send` を満たす、と言える。
借用ポインタについても同様である。`T: Sync` のとき、かつそのときに限り、`&T : Send` かつ `&mut T : Send` である。

`Sync trait` を満たす型の例は次のとおり：
1. `Atomic` 系列の型
2. `Mutex<T>` `RwLock<T>` などの型。注意：これらの型自体はジェネリクスを持つため、`Sync` を満たすかどうかには前提条件がある。`T: Send` のとき、かつそのときに限り、`Mutex<T> : Sync` である。

この二つの trait があれば、あと二ことをすれば、スレッド安全を保証できる：
1. 標準ライブラリ中で、すべての基礎型、および標準ライブラリで定義した型に、`Send` と `Sync` の印を付ける。
2. 異なるスレッド間でデータを渡す必要がある API に制約を増やし、スレッドをまたいで渡す型が `Send` 条件を満たすよう制限する。

ユーザ定義型は、一般の場合 `Send` `Sync` を手動で印す必要はなく、コンパイラが自分で推論した結果に頼ればよい。
この型の実装が unsafe を使っているなら、このときプログラマ自身がその型が `Send` `Sync` を満たすかを分析し、unsafe impl によって明示指定する必要がある。

### データ競合なし

コンパイラと標準ライブラリ中に上記の `Send` `Sync` 型を用意したあと、コンパイル検査によって業務コード中の「データ競合なし」を保証できる。
データ競合の可能性が現れれば、コンパイラは自動でエラーを出す。

例は次のとおり：

```
// send 関数がすべきことが data を別のスレッドへ送って使うことなら、data の型が Send 制約を満たすよう制限する必要がある
fn send<T>(data: T) where T: Send { }

fn main() {
    send(1_i);
    send(String::new());
    send((type Vec<Int>)::new());
    send(box 1_u); // Error. コンパイルエラー。*UInt は Send 制約を満たさない
}
```

### グローバル変数

グローバル変数はもともと異なるスレッドからアクセスできるため、それにも制限を課してスレッド安全を保証する必要がある。
1. グローバル変数の定義は `static` または `unsafe static` キーワードで修飾できる。`unsafe` で修飾したグローバル変数は、unsafe 領域でのみ読み書きできる。`static` で定義した読み取り専用グローバル変数だけが安全である。
2. `unsafe` 修飾のないグローバル変数の型は、`Send trait` の要求を満たさなければならない。

**注意**：Rust の規則と異なり、Zinc がグローバル変数に要求するのは `Send` 制約であり、`Sync` 制約ではない。

Zinc の `Sync trait` と Rust の `Sync trait` の意味論が異なるからである。Rust で `Sync` を満たす多くの型は、Zinc では `Sync` を満たさない。
基礎型 `Int` を例にとると、Rust では `Sync` を満たすが、Zinc では `Int` は `Sync` を満たせない。
背理法によれば、`Int` が `Sync` を満たすと規定すると、`*Int` というポインタが `Send` を満たすことを意味し、スレッドをまたいで渡せ、それから二つのスレッドが同じ `Int` を指すポインタを得て、しかもスレッド同期をしていない、という様子が見えることになり、これは誤りである。

* Zinc 中の `Sync` が表すのは、内部に追加のスレッド同期機構がある型である。`Sync` 制約を満たす型は、Rust 中よりずっと少ない。 
* Zinc 中の `Send` が表すのは、スレッドをまたいで安全に渡せる型である。主に四通りの場合を含む：

    1. 古典的な値意味論型。内部にポインタを含まず、スレッドをまたいで渡すときは複製をコピーするため、確かに安全である
    2. 型中にポインタを含み、ポインタが指すデータが読み取り専用である。共有データは読み取り専用であるため、安全である。
       たとえば `Str` 型は、対外 API がいかなる変更能力も提供せず、こうして `Str` が `Send` を満たすことを保証できる。
    3. 型中にポインタを含み、ポインタが指すデータが copy-on-write を満たす。あるスレッドが共有データを変更しようとすれば、共有データをコピーしてから変更し、データが共有状態にある限り決して変更されず、変更するのは常に自分でコピーした複製であるため、安全である。
       たとえば `Vec<Int>` 型は、変更能力を持つすべてのメンバ関数が参照カウントを判定し、排他的でなければ先にデータをコピーしてから変更する
    4. 型中にポインタを含み、ポインタが指すデータがスレッド同期の前提で変更できる。スレッドをまたいで渡したあと、複数のスレッドが同じデータへのポインタを持つことになるが、共有データへのすべての読み書きにスレッド同期があるため、安全である
       たとえば `*AtomicInt` `*Mutex<String>` 型


Zinc と Rust が設計した `Send` と `Sync` のいくつかの細部には違いがあるが、いずれもスレッド安全の保証を達成している。



<div style="border: 1px solid black; padding: 10px; background: #F0F0F0">

上記の設計からわかるように、`Vec<Int>` のような種類の型は `Send` 制約を満たす。この種の型を安全にスレッドをまたいで渡せる。

1. `Vec<Int>` を異なるスレッドへ渡し、かつ各スレッドがそれに対して読み取り専用だけなら、浅いコピーだけが起き、実行効率が高い。
2. `Vec<Int>` を異なるスレッドへ渡し、かつあるスレッドがそれを変更するなら、そのスレッドで変更が起きるときに深いコピーが起き、このとき大きな性能オーバーヘッドがあるが、スレッド安全問題はない。
3. `Vec<Int>` をスレッドをまたいで渡し、変更でき、しかも深いコピーが起きないようにしたいなら、プログラマ自身が、複数の浅いコピー実体が同時に存在しないことを保証する必要がある。このことは move 式によって達せられる。
一つの `Vec<Int>` の所有権を異なるスレッドへ移せば、効率の良いスレッド横断変更の目的を実現できる。しかしコンパイラは型の層で所有権を追跡せず、制御フローの層でのみ追跡し、ユーザへの影響を減らす。
4. 参照意味論の `Vec<Int>` を得たいなら、それを box するだけでよく、得られる `*Vec<Int>` が参照意味論の型である。異なるポインタが同じ `Vec<Int>` を変更でき、同じデータブロックを共有する。
`Vec<Int>` は `Sync` を満たさないため、`*Vec<Int>` は `Send` を満たさない。このときコンパイラは、これらのポインタがすべて同一スレッド内部にあることを検査できる。非 `Send` 型はスレッド境界を越えられない。
したがって参照意味論の `*Vec<Int>` 型にもスレッド安全問題はない。しかもこの Arc ポインタの参照カウント操作は non-atomic 加減操作に最適化できる。

以上からわかるように、copy-on-write 最適化は `Vec<T>` のような型にとって非常に重要である。

Zinc 言語がメモリ管理の基礎機構として ARC ではなく GC を選び、`box` 式が返すのが GC trace-able なポインタだと仮定する。
すると `Vec<T>` のようなコンテナ型は、その内部実装が GC ポインタしか使えず、「値意味論」型にはできない。non-Send にしかなれない。しかも move 式も意味を失う。
こうなると、マルチスレッド場面で `Send` 制約を満たせる型はごくわずかになり、スレッド安全を保証するために深いコピーが必要な場面がより多くなり、かえって巨大な追加性能オーバーヘッド代価をもたらす。
したがって ARC メモリ管理と Zinc のスレッド安全目標は最もよく合う。

そしてまさに Zinc もスレッド安全を達成したからこそ、ある ARC ポインタがスレッド境界を決して越えられず、それ自身およびその複製が同一スレッド内でしか使えないことを、コンパイル時に保証できる。
この情報を利用し、コンパイラはそれらの参照カウントの加減操作を非原子操作に最適化し、さらに性能を上げられる。この最適化は型にだけ関係し、制御フローには関係しない。

したがって、スレッド安全と ARC メモリ管理は、互いに補い合い、互いを引き立て合う。

## スレッド

Zinc 標準ライブラリが提供するスレッド関連 API は、オペレーティングシステムのスレッド機能の単純なカプセル化である。スレッドの作成には次の関数を使う：

```
// mod std::thread
pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: Send + 'static + Fn()->T,
    T: Send + 'static,
```

`JoinHandle` は `join()` 関数を呼んでスレッドの終了を待てる。さらに `thread()` 関数を呼んで `&Thread` 型の変数を得られる。

例は次のとおり：

```Rust
use std::thread::spawn;
fn main() {
    let h = spawn.{
        println("thread 2");
    };
    println("thread 1");
    h.join().get_or_panic();
}
```

### ThreadLocal

`ThreadLocal` 型は「スレッド局所」変数を表すために使う。各スレッドが各自の複製を独立して維持する。

使い方は次のとおり：

```
use std::thread::spawn;

fn main() {
    static G: ThreadLocal<Int64> = ThreadLocal::new(0);

    let h = spawn.{
        *G += 1;
    };
    h.join().get_or_panic();
    println(*G);
}
```

## ロック

ロックには `Mutex<T>` `RwLock<T>` が含まれる。

Rust のロックの API 設計には一つの良い利点がある：ロックと保護対象データを一つの型に合併し、ロックと保護対象データが一致しない状況を避け、データにアクセスするときにロックし忘れる場面も起き得ない。

しかしいくつかの小さな問題がある：
1. poison 設計
2. safe コード中で MutexGuard のリークを許し、ロック解除できない場面が現れうる
3. 非同期コード中で、ロック中に await が起きると、デッドロックを起こしやすい

Zinc はこの API に少し小さな変更をした：
1. poison 状態管理を取り消す。Zinc には catch unwind の機構がないからである
2. ロックとロック解除をコールバック関数式に改める

```
fn synchronized(p: &Mutex<String>) {
    // 今後 swift に学び、より多くの糖衣構文を増やし、lambda のこの引数リストも省略できる
    p.lock.{ (data: &mut String) =>  
        data.push_str("tail");
    };
}
```

こうする利点は：
1. ロックする範囲が明確であり、波括弧で囲まれていて比較的目立ち、人間の読書に適する
2. MutexGuard がなく、したがってリークリスクもなく、ロック行為は必ずロック解除行為に対応し、ロックを解放できないリスクを避ける
3. 多層ロックのとき、ロックとロック解除が必ず後入れ先出し原則を満たすことを保証できる。Rust は MutexGuard を露出しており、ユーザが MutexGuard を手動で drop することを許すため、実際のロック解除の順序が非構造的になりうる
4. コールバック関数中では await 式を使えず、コールバック関数 API の型が合わないため、ロックの過程で await が起きるような状況も避けられる

もちろん欠点ももたらす。以前のようにロック中に自然に `break` `continue` `return` といった制御フロー文を使い、コンパイラが自動でロック解除する、ということがもはやできない。コールバック関数中の制御フロー文は lambda 内部にだけ影響し、外部の制御フローを処理する必要があるなら、この lambda の異なる戻り値によって lambda の外で追加の判定処理をする必要がある。もちろん話を戻せば、こう書くことは少なくとも可読性の観点では非常に明確である。制御フロー文を直接使えないことが、必ずしも悪いこととは限らない。

### コピー防止設計

Rust のロックの型は move セマンティクスとして設計されているが、Zinc には move セマンティクスの型がない。これは新しいリスクをもたらし、ユーザが `Mutex<T>` 変数を意図せず複製してしまい、bug を生みやすい。

例:
```
// 疑似コード例。このコードは実際にはコンパイルを通せない
fn test(s: &Mutex<String>) {
    let str_copy = *s; // ある場合このコピーは非常に隠れており、bug が出うる
    str_copy.lock.{ (s: &mut String) => println(s) };
}
```

Zinc では、このような状況が現れるのを避けるため、`UnSized` trait を導入した。この trait は marker trait であり、メンバ関数がない。同時に次を規定する：
1. 型を定義するとき、カスタム型に `impl UnSized for MyType {}` することを許す
2. すべての `UnSized` 型は、グローバル変数、定数、局所変数、メンバ変数として直接使えない。この種の型はポインタを通して間接的にアクセスするしかない。
3. `UnSized` を指すポインタ型の参照外しを許さない。

標準ライブラリ中で `Mutex` のような型を `UnSized` と規定すれば、上の bug が現れるのを避けられる。

```
struct S {
    value: Mutex<MyType>, // Error。Mutex はメンバ変数として直接使えず、*Mutex<MyType> で代用することを勧める
}

fn f() { 
    let local = Mutex::new(MyType::new()); // Error。Mutex は局所変数として直接使えず、*Mutex<MyType> で代用することを勧める
}

static GLOBAL_DATA: Mutex<MyType> = Mutex::new(MyType::new()); // Error。Mutex はグローバル変数として直接使えず、&'static Mutex<MyType> で代用することを勧める

static GLOBAL_DATA: &'static Mutex<MyType> = &Mutex::new(MyType::new()); // OK
```

標準ライブラリ中の `swap` などの関数も、`UnSized` 型には操作できない。したがってこの設計は、上記の「不注意で Mutex 全体をコピーした」誤りを避けられる。

標準ライブラリ中の `File` などの型も、同様の設計である。ユーザは常に「File を指すポインタ型」だけを使え、`File` 型を値型として直接使うことはできない。
