
# 병렬과 동시성

## 스레드 안전

Rust에는 비할 데 없는 장점이 있습니다. 프로그램의 스레드 안전을 본디 보장한다는 것입니다. 상용 프로그래밍 언어 중에서 유일합니다. Zinc 언어도 스레드 안전이라는 이 특징을 유지하고 싶습니다.

### Send/Sync trait

안전하게 스레드를 넘어 전달할 수 있는 모든 타입에 통일된 표시를 붙이며, 이를 `Send trait`이라고 합니다.

먼저 [값 의미론과 참조 의미론](https://isocpp.org/wiki/faq/value-vs-ref-semantics#val-vs-ref-semantics)의 의미를 복습합시다.

알 수 있듯이, 값 의미론 타입은 본디 `Send trait`의 요구를 만족합니다. 예는 다음과 같습니다:
1. 기초 타입 Bool, Char, Int 등은 값 의미론에 맞으므로 분명히 `Send trait`을 만족합니다.
2. 조합 타입, 예: tuple/struct/enum 등은, 모든 멤버가 `Send`를 만족하면 그것도 반드시 값 의미론이므로, 이런 타입도 `Send trait`을 만족합니다.
3. 포인터 타입은 값 의미론에 맞지 않으며, 일반적으로 `*T`는 `Send` trait을 만족하지 않습니다. 하지만 구체 상황에 따라 분석해야 합니다. 포인터 타입, 또는 내부에 포인터 멤버를 포함하는 타입은 다음 두 경우에도 `Send`를 만족합니다:
    1. copy-on-write 메커니즘으로 값 의미론을 구현한 경우, 이들도 `Send trait`을 만족합니다. 예를 들어 `String` 타입은 내부에 포인터 멤버가 있지만, 구현이 copy-on-write로 “값 의미론”을 보장하므로 이런 타입도 `Send trait`을 만족합니다. `Vec<T>` 같은 타입은 copy-on-write를 구현했지만 제네릭이 있으므로, `Send`를 만족하는지는 전제 조건이 있습니다. `T: Send`일 때 그리고 그때만 `Vec<T> : Send`입니다.
    2. 스레드 동기화 메커니즘으로 포인터가 가리키는 내용이 스레드 안전함을 보장하는 경우, 이들도 `Send trait`을 만족합니다. 예를 들어 `*AtomicInt32` 타입은 두 스레드의 서로 다른 포인터가 같은 `AtomicInt32`를 가리킬 수 있지만, `AtomicInt32`가 스레드 동기화를 했으므로 `*AtomicInt32` 타입은 `Send trait`을 만족합니다.

따라서 또 다른 `Sync trait`을 도입해, 타입 자체가 스레드 동기화 능력을 갖추었음을 나타냅니다. 그렇다면 `*T` 타입에 대해, `T`가 `Sync`를 만족할 때 그리고 그때만 `*T`가 `Send`를 만족한다고 할 수 있습니다.
빌림 포인터도 마찬가지입니다. `T: Sync`일 때 그리고 그때만 `&T : Send`이고 `&mut T : Send`입니다.

`Sync trait`을 만족하는 타입의 예는 다음과 같습니다:
1. `Atomic` 계열 타입
2. `Mutex<T>` `RwLock<T>` 등 타입. 주의: 이런 타입 자체는 제네릭이므로, `Sync`를 만족하는지는 전제 조건이 있습니다. `T: Send`일 때 그리고 그때만 `Mutex<T> : Sync`입니다.

이 두 trait이 있으면, 스레드 안전을 보장하기 위해 두 가지를 더 해야 합니다:
1. 표준 라이브러리에서 모든 기초 타입과 표준 라이브러리가 정의한 타입에 `Send`와 `Sync` 표시를 붙입니다.
2. 서로 다른 스레드 사이에 데이터를 전달해야 하는 API에 제약을 추가해, 스레드를 넘어 전달하는 타입이 반드시 `Send` 조건을 만족하도록 제한합니다.

사용자 정의 타입은 일반적으로 `Send` `Sync`를 수동으로 표시할 필요가 없으며, 컴파일러가 스스로 추론한 결과면 됩니다.
이 타입의 구현이 unsafe를 사용했다면, 이때 프로그래머가 스스로 해당 타입이 `Send` `Sync`를 만족하는지 분석하고, unsafe impl로 명시적으로 지정해야 합니다.

### 데이터 레이스 없음

컴파일러와 표준 라이브러리에 위의 `Send` `Sync` 타입이 준비되면, 컴파일 검사로 업무 코드에 “데이터 레이스가 없음”을 보장할 수 있습니다.
데이터 레이스 가능성이 나타나면 컴파일러가 자동으로 오류를 냅니다.

예시는 다음과 같습니다:

```
// send 함수가 할 일이 data를 다른 스레드로 보내 쓰게 하는 것이라면, data의 타입이 Send 제약을 만족하도록 제한해야 함
fn send<T>(data: T) where T: Send { }

fn main() {
    send(1_i);
    send(String::new());
    send((type Vec<Int>)::new());
    send(box 1_u); // Error. 컴파일 오류 *UInt가 Send 제약을 만족하지 않음
}
```

### 전역 변수

전역 변수는 본디 서로 다른 스레드가 접근할 수 있으므로, 스레드 안전을 보장하려면 제한을 두어야 합니다.
1. 전역 변수 정의는 `static` 또는 `unsafe static` 키워드로 수식할 수 있습니다. `unsafe`로 수식한 전역 변수는 unsafe 구역에서만 읽고 쓸 수 있습니다. `static`으로 정의한 읽기 전용 전역 변수만 안전합니다.
2. `unsafe`로 수식하지 않은 전역 변수의 타입은 반드시 `Send trait`의 요구를 만족해야 합니다.

**주의**: Rust의 규칙과 다릅니다. Zinc는 전역 변수가 `Sync` 제약이 아니라 `Send` 제약을 만족할 것을 요구합니다.

Zinc의 `Sync trait`과 Rust의 `Sync trait` 의미론이 다르기 때문입니다. Rust에서 `Sync`를 만족하는 많은 타입이 Zinc에서는 `Sync`를 만족하지 않습니다.
기초 타입 `Int`를 예로 들면, Rust에서는 `Sync`를 만족하지만, Zinc에서 `Int`는 `Sync`를 만족할 수 없습니다.
귀류법에 따르면, `Int`가 `Sync`를 만족한다고 규정하면 `*Int` 같은 포인터가 `Send`를 만족하게 되고, 그렇다면 스레드를 넘어 전달할 수 있으며, 그러면 두 스레드가 모두 같은 `Int`를 가리키는 포인터를 얻고 스레드 동기화를 하지 않은 것을 보게 되는데, 이는 잘못입니다.

* Zinc의 `Sync`는 내부에 추가 스레드 동기화 메커니즘이 있는 타입을 나타냅니다. `Sync` 제약을 만족하는 타입이 Rust에서보다 훨씬 적습니다.
* Zinc의 `Send`는 안전하게 스레드를 넘어 전달할 수 있는 타입을 나타냅니다. 주로 네 가지 경우가 있습니다:

    1. 고전적인 값 의미론 타입으로, 내부에 포인터가 없습니다. 스레드를 넘어 전달할 때 사본을 복사하므로 분명히 안전합니다
    2. 타입에 포인터가 포함되고, 포인터가 가리키는 데이터가 읽기 전용입니다. 공유 데이터가 읽기 전용이므로 안전합니다.
       예를 들어 `Str` 타입은 대외 API가 어떤 수정 능력도 제공하지 않아, `Str`이 `Send`를 만족함을 보장할 수 있습니다.
    3. 타입에 포인터가 포함되고, 포인터가 가리키는 데이터가 copy-on-write를 만족합니다. 어떤 스레드가 공유 데이터를 수정하려 하면 공유 데이터를 한 벌 복사한 뒤 수정하며, 데이터가 공유 상태에 있는 한 분명히 수정되지 않고, 수정하는 것은 영원히 자신이 복사한 사본이므로 안전합니다.
       예를 들어 `Vec<Int>` 타입은 수정 능력이 있는 모든 멤버 함수가 참조 카운트를 판단하고, 독점이 아니면 데이터를 먼저 한 벌 복사한 뒤 수정합니다
    4. 타입에 포인터가 포함되고, 포인터가 가리키는 데이터는 스레드 동기화 전제 하에 수정할 수 있습니다. 스레드를 넘어 전달된 뒤 여러 스레드가 같은 데이터를 가리키는 포인터를 보유하지만, 공유 데이터에 대한 모든 읽기·쓰기에 스레드 동기화가 있으므로 안전합니다
       예를 들어 `*AtomicInt` `*Mutex<String>` 타입


Zinc와 Rust가 설계한 `Send`와 `Sync`의 일부 세부사항은 다르지만, 모두 스레드 안전을 보장합니다.

위의 설계에서 알 수 있듯이, `Vec<Int>` 같은 타입은 `Send` 제약을 만족합니다. 이런 타입을 안전하게 스레드를 넘어 전달할 수 있습니다.

1. `Vec<Int>`를 서로 다른 스레드로 전달하고, 각 스레드가 읽기만 한다면, 얕은 복사만 발생해 실행 효율이 높습니다.
2. `Vec<Int>`를 서로 다른 스레드로 전달하고, 어떤 스레드가 그것을 수정하면, 그 스레드에서 수정이 발생할 때 깊은 복사가 발동됩니다. 이때 성능 오버헤드가 크지만, 스레드 안전 문제는 없습니다.
3. `Vec<Int>`를 스레드를 넘어 전달해 수정할 수 있게 하면서 깊은 복사가 일어나지 않기를 원한다면, 프로그래머가 스스로 얕은 복사 인스턴스가 동시에 여러 개 존재하지 않음을 보장해야 합니다. 이는 move 표현식으로 달성할 수 있습니다.
`Vec<Int>`의 소유권을 서로 다른 스레드에서 이전하면, 효율적인 교차 스레드 수정을 구현할 수 있습니다. 하지만 컴파일러는 타입 층면에서 소유권을 추적하지 않고 제어 흐름 층면에서만 추적해, 사용자에 대한 영향을 줄입니다.
4. 참조 의미론의 `Vec<Int>`를 얻고 싶다면 box만 하면 되며, 얻는 `*Vec<Int>`가 바로 참조 의미론 타입입니다. 서로 다른 포인터가 같은 `Vec<Int>`를 수정하고 같은 데이터 블록을 공유할 수 있습니다.
`Vec<Int>`가 `Sync`를 만족하지 않으므로 `*Vec<Int>`는 `Send`를 만족하지 않습니다. 이때 컴파일러가 이런 포인터가 모두 같은 스레드 내부에 있음을 검사해 줄 수 있으며, non-`Send` 타입은 스레드 경계를 넘을 수 없습니다.
따라서 참조 의미론의 `*Vec<Int>` 타입에도 스레드 안전 문제가 없습니다. 게다가 이 Arc 포인터의 참조 카운트 연산은 non-atomic 가감 연산으로 최적화될 수 있습니다.

위에서 알 수 있듯이, copy-on-write 최적화는 `Vec<T>` 같은 타입에 매우 중요합니다.

Zinc 언어가 메모리 관리의 기초 메커니즘으로 ARC가 아니라 GC를 선택해, `box` 표현식이 반환하는 것이 GC trace-able 포인터라고 가정해 봅시다.
그렇다면 `Vec<T>` 같은 컨테이너 타입의 내부 구현은 GC 포인터만 쓸 수 있어 “값 의미론” 타입을 만들 수 없습니다. non-Send일 수밖에 없습니다. 게다가 move 표현식도 의미가 없어집니다.
이렇게 되면 멀티스레드 장면에서 `Send` 제약을 만족할 수 있는 타입이 매우 적고, 스레드 안전을 보장하려면 깊은 복사를 해야 하는 장면이 더 많아져, 오히려 거대한 추가 성능 오버헤드 대가를 가져옵니다.
따라서 ARC 메모리 관리와 Zinc의 스레드 안전 목표가 가장 잘 맞습니다.

그리고 Zinc가 스레드 안전도 달성했기 때문에, 어떤 ARC 포인터가 스레드 경계를 넘을 수 없음이 컴파일 타임에 보장되며, 자신과 그 복제품이 모두 같은 스레드 안에서만 쓰입니다.
이 정보를 이용해 컴파일러는 그들의 참조 카운트 가감 연산을 비원자 연산으로 최적화해 성능을 더 높일 수 있습니다. 이 최적화는 타입에만 관련되고 제어 흐름과는 무관합니다.

따라서 스레드 안전과 ARC 메모리 관리는 서로 잘 맞고, 서로를 빛나게 합니다.

## 스레드

Zinc 표준 라이브러리가 제공하는 스레드 관련 API는 운영체제 스레드 기능의 간단한 캡슐화입니다. 스레드를 만드는 함수는 다음과 같습니다:

```
// mod std::thread
pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: Send + 'static + Fn()->T,
    T: Send + 'static,
```

`JoinHandle`은 `join()` 함수를 호출해 스레드가 끝나기를 기다릴 수 있습니다. `thread()` 함수를 호출해 `&Thread` 타입 변수를 얻을 수도 있습니다.

예시는 다음과 같습니다:

```Rust
use std::thread::spawn;
fn main() {
    let h = spawn.{
        println("thread 2");
    };
    println("thread 1");
    h.join().get_or_panic();
}
```

### ThreadLocal

`ThreadLocal` 타입은 “스레드 로컬” 변수를 표현하는 데 쓰입니다. 각 스레드가 각자의 사본을 독립적으로 유지합니다.

사용 방식은 다음과 같습니다:

```
use std::thread::spawn;

fn main() {
    static G: ThreadLocal<Int64> = ThreadLocal::new(0);

    let h = spawn.{
        *G += 1;
    };
    h.join().get_or_panic();
    println(*G);
}
```

## 락

락은 `Mutex<T>` `RwLock<T>`를 포함합니다.

Rust의 락 API 설계에는 좋은 장점이 있습니다. 락과 보호되는 데이터를 하나의 타입으로 합쳐, 락과 보호되는 데이터가 맞지 않는 경우를 피하고, 데이터에 접근하면서 잠그는 것을 잊는 장면도 나타날 수 없습니다.

하지만 몇 가지 작은 문제가 있습니다:
1. poison 설계
2. safe 코드에서 MutexGuard 누수를 허용해, 잠금을 해제할 수 없는 장면이 나타날 수 있음
3. 비동기 코드에서 잠근 상태에서 await가 발생하면 교착이 쉽게 발동됨

Zinc는 이 API에 약간의 작은 수정을 했습니다:
1. poison 상태 관리를 취소합니다. Zinc에 catch unwind 메커니즘이 없기 때문입니다
2. 잠금과 해제를 콜백 함수식으로 바꿉니다

```
fn synchronized(p: &Mutex<String>) {
    // 이후 swift를 배워 더 많은 문법 설탕을 추가하고, lambda의 이 매개변수 목록도 생략할 수 있음
    p.lock.{ (data: &mut String) =>  
        data.push_str("tail");
    };
}
```

이렇게 하는 이점은 다음과 같습니다:
1. 잠금 범위가 명확하고, 중괄호로 둘러싸여 눈에 잘 띄어 사람이 읽기에 적합합니다
2. MutexGuard가 없으므로 누수 위험도 없고, 잠금 동작은 반드시 해제 동작에 대응해, 락을 해제할 수 없는 위험을 피합니다
3. 다층으로 잠글 때, 잠금과 해제가 반드시 선입후출 원칙을 만족함을 보장할 수 있습니다. Rust는 MutexGuard를 노출해 사용자가 MutexGuard를 수동으로 drop할 수 있으므로, 실제 해제 순서가 비구조적일 수 있습니다
4. 콜백 함수 안에서는 await 표현식을 쓸 수 없습니다. 콜백 함수 API 타입이 맞지 않기 때문이며, 따라서 락을 거는 과정에서 await가 발생하는 상황을 피합니다

물론 단점도 있습니다. 예전처럼 잠근 과정에서 `break` `continue` `return` 같은 제어 흐름 문장을 자연스럽게 쓰고 컴파일러가 자동으로 해제하는 것이 더 이상 불가능합니다. 콜백 함수 안의 제어 흐름 문장은 lambda 내부에만 영향을 주므로, 바깥 제어 흐름을 처리해야 하면 이 lambda의 서로 다른 반환값으로 lambda 바깥에서 추가 판단 처리를 해야 합니다. 물론 다시 말하면, 이렇게 쓰는 것은 적어도 가독성 관점에서는 매우 명확합니다. 제어 흐름 문장을 직접 쓰지 못하는 것이 반드시 나쁜 일은 아닙니다.

### 복사 방지 설계

Rust의 락 타입은 move 의미론으로 설계되었지만, Zinc에는 move 의미론 타입이 없습니다. 이는 새로운 위험을 가져옵니다. 사용자가 `Mutex<T>` 변수를 의도치 않게 한 벌 복사할 수 있으며, 이는 버그를 쉽게 만듭니다.

예시:
```
// 의사 코드 예시, 이 코드는 실제로 컴파일을 통과하지 못함
fn test(s: &Mutex<String>) {
    let str_copy = *s; // 어떤 경우 이 복사가 매우 은밀할 수 있으며, 버그가 날 수 있음
    str_copy.lock.{ (s: &mut String) => println(s) };
}
```

Zinc에서는 이런 상황을 피하기 위해 `UnSized` trait을 도입했습니다. 이 trait은 marker trait이며 멤버 함수가 없습니다. 동시에 규정합니다:
1. 타입을 정의할 때 사용자 정의 타입에 `impl UnSized for MyType {}`하는 것을 허용합니다
2. 모든 `UnSized` 타입은 전역 변수, 상수, 지역 변수, 멤버 변수로 직접 쓸 수 없습니다. 이런 타입은 포인터를 통해 간접 접근만 할 수 있습니다.
3. `UnSized`를 가리키는 포인터 타입을 역참조하는 것은 허용되지 않습니다.

표준 라이브러리에서 `Mutex` 같은 타입을 `UnSized`로 규정하면 위의 버그가 나타나는 것을 피할 수 있습니다.

```
struct S {
    value: Mutex<MyType>, // Error, Mutex는 멤버 변수로 직접 쓸 수 없음. *Mutex<MyType>으로 대체하기를 권함
}

fn f() { 
    let local = Mutex::new(MyType::new()); // Error, Mutex는 지역 변수로 직접 쓸 수 없음. *Mutex<MyType>으로 대체하기를 권함
}

static GLOBAL_DATA: Mutex<MyType> = Mutex::new(MyType::new()); // Error, Mutex는 전역 변수로 직접 쓸 수 없음. &'static Mutex<MyType>으로 대체하기를 권함

static GLOBAL_DATA: &'static Mutex<MyType> = &Mutex::new(MyType::new()); // OK
```

표준 라이브러리의 `swap` 등 함수도 `UnSized` 타입에 대해 연산할 수 없습니다. 따라서 이 설계는 위의 "부주의로 전체 Mutex를 복사하는" 오류를 피할 수 있습니다.

표준 라이브러리의 `File` 등 타입도 비슷한 설계입니다. 사용자는 영원히 “File을 가리키는 포인터 타입”만 쓸 수 있고, `File` 타입을 값 타입으로 직접 쓸 수 없습니다.
