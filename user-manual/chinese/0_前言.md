# 前言

Zinc 编程语言，是受到Rust启发的，更易用的系统级编程语言。

## 特点

1. 静态类型、轻量级运行时无GC
  * 类型安全
  * 直接编译为机器码，无虚拟机，启动速度快
  * 无GC，内存开销小
  * 具备内存布局控制能力
  * 基于 LLVM 框架作为后端，方便跨平台
  * 互操作方便

2. 安全性
  * 默认内存安全，只有用 unsafe 才能制造出未定义行为
  * 默认线程安全，只有用 unsafe 才能制造出数据竞争

3. 易用性
  * 不追求零开销抽象
  * 没有 move 语义的类型，只支持 move 语义的表达式
  * 有借用类型，但没有 borrow checker，避免 ownership + borrow checker 对整体编程模式的巨大影响，极大改进 Rust 的易用性

4. 泛型函数主要通过表传递实现
  * 支持使用动态链接库发布组件，组件支持复杂接口，包括泛型
  * 支持 virtual 函数携带泛型参数
  * 远期希望支持 ABI 稳定，允许单独更新组件，不需要下游依赖项重新编译
  * 提供编译选项，允许用户在不考虑 ABI 稳定的场景下，选择对泛型函数做实例化，进一步性能优化

### 与 Rust 比较

1. 语法与 Rust 接近，标准库风格与 Rust 接近。同样支持内存安全、线程安全特性。
2. 内存管理主要使用引用计数，而不是所有权机制。
3. 提升易用性：支持借用，但删除 borrow checker；支持move语义表达式，但不支持move语义类型。
4. 更好地支持面向对象编程范式
5. 修改泛型实现，同时支持实例化方案和表传递(dictionary passing)方案，通过编译选项选择
6. 部分语法得到简化

### 与 Swift 比较

1. 更好的线程安全支持，编译时保证 thread-safety
2. 平台中立，不将 macOS 作为主力平台
3. 放弃与 obj-C 的互操作，更多考虑与 C/C++ 的互操作
4. 对 OOP 编程范式的支持方式不同，比如不支持 class 以及继承特性
5. 对 move/借用 功能的支持方式不同

### 与 C++ 比较

1. zinc更安全，在不使用 unsafe 的情况下，没有未定义行为
2. 不同的泛型实现方式，zinc的泛型函数可以做虚函数使用，泛型函数也可以编译成二进制代码使用动态链接库发布
3. 远期来看，zinc可以做到 ABI 稳定
4. 在执行性能方面比 C/C++ 差不少，但是应该能满足应用开发的性能要求
5. 更简单的语言特性、更少的历史包袱、更好的运行时动态特性支持、更小的代码体积

### 与 Go 比较

1. 无 GC，对内存资源的要求更低
2. 更好的语言特性支持，包括泛型、trait、enum、模式匹配等
3. 更适合使用动态链接库发布组件
4. 更好的线程安全支持
5. 更好的跨语言交互能力。Go语言自带GC，很难与其它自带GC的语言互操作。

## 常见问题解答

### 1. Zinc 语言的定位是什么？

Zinc 语言的初衷是，改善 Rust 语言的易用性。

在系统编程语言设计方面，有三个常见的评价维度：安全、性能、易用性。Rust 语言在安全和性能方面做到了极致，但是易用性始终是一个痛点。
Zinc 语言在继续保持安全性的同时，放弃了极致性能，换取了易用性的改善。

之所以做这种修改，是因为作者观察到，普通开发者碰到的绝大多数场景，CPU性能并不是瓶颈，压榨CPU极限的场景毕竟是极少数。
大多数情况下，人们之所以选择无垃圾回收功能的系统编程语言，并不是为了极致性能，而是因为各种其它原因。包括但不限于：

* 希望有较强的内存布局控制力，以及执行性能的可预测性
* 有跨平台诉求，在某些平台上移植虚拟机运行时比较困难
* 在某些平台上内存资源吃紧，无法使用自动垃圾回收机制
* 希望能编写基础公共组件库，它能被各种使用不同 GC 机制的高级语言调用。自带 GC 的语言，很难与使用不同 GC 的语言在一个进程内高效互操作

因此，这样定位的编程语言，应该是有合适的使用场景的：
1. 没有自动垃圾回收机制，方便跨平台，方便与其它各种高级语言互操作。适合编写公共通用模块。
2. 在保证安全的前提下，有很好的易用性。对开发人员要求低，开发产能充裕。
3. 性能水平在线，但不需要追求极致性能，不需要压榨硬件的所有潜力。

这样的设计是不符合 Rust 语言的定位的，因此这种改动只能启动一门新的编程语言来做尝试。

Zinc 语言的定位跟 Swift 语言类似，核心特点是：无垃圾回收 + 安全 + 易用。
但它同时具备线程安全的优点，这是 Swift 不具备的。

### 2. Zinc 语言与 Rust 语言的对比？

* Rust 坚持 “零开销抽象” 原则，Zinc 放弃了该设计原则。当执行性能和易用性无法兼顾的时候，优先选择易用性。
* Rust 使用 “所有权+生命周期” 机制保证内存安全，借用检查器在编译时检查 aliasing XOR mutation。Zinc 使用引用计数和借用机制保证内存安全，编译检查规则要宽松得多。删除 borrow checker 保证了 Zinc 的易用性相比 Rust 有极大改善。
* Rust 使用实例化方式实现泛型，Zinc使用表传递的方式实现泛型。这意味着 Rust 不适合把泛型代码编译成二进制库对外发布，而 Zinc 可以。支持动态链接库、以及 ABI 稳定性是 Zinc 语言后续的重要目标。
* Rust 保证了内存安全、线程安全，Zinc 语言同样也保证了内存安全、线程安全。在安全性方面，并没有弱化，只是付出了一定的性能代价。

总而言之，在语法语义层面，Zinc 与 Rust 语言非常接近；但在执行层面，Zinc 与 Swift 语言非常接近。

### 3. 为什么命名为 Zinc？

Rust 代表的是生锈、腐蚀；Zinc 代表的是锌金属。锌这种金属有一个特点：

>
> 锌在空气中容易与氧气反应，形成锌氧化物层，即锌锭表面的钝化层。
> 钝化层具有一定的保护作用，可以抑制进一步的氧化腐蚀。
> 锌最主要的应用为抗腐蚀的铁镀锌。
>
> Zinc is most commonly used as an anti-corrosion agent, and galvanization (coating of iron or steel) is the most familiar form.
> (from: https://en.wikipedia.org/wiki/Zinc)
>

这个单词反映了这门语言的本质：Zinc 语言表面上像 Rust 语言，但在表层语法之下，它的思想内核是与 Rust 格格不入的。

巧合的是，这个词在中文里读起来也比较顺耳，与 “新语言” 谐音。

### 4. 为什么选择引用计数 reference counting (RC) 作为主要的内存管理机制？

RC 的优点：
* RC 的一个优点是，它可以方便地实现内存安全。实现内存安全的理论基础是 "aliasing xor mutation"。RC 特别适合追踪 aliasing，在此基础上配合 copy-on-write 即可实现很好的安全性。
* RC 非常契合 Zinc 语言在线程安全方面的设计。线程安全与 RC 内存管理，是互相配合，互相成就。这个是 Zinc 无法使用 GC 的核心原因。如果采用 GC，Zinc 没办法达到目前的线程安全水平。
* RC 的另外一个非常好的优点，就是它简单。这意味着对外部环境的约束条件很少，所以它与其它任何语言互操作，都很简单。而 GC 有太复杂的实现细节，不同的 GC 机制难以在同一个进程中高效共存。自带 GC 的语言，与其它不同 GC 机制的语言做互操作的话，就是自讨苦吃，很不方便。

RC 的缺点：
* RC 的一个缺点是，无法解决循环引用造成的泄露问题。但这个问题不是内存安全问题，它的影响相对较小。而且在系统编程语言这个范围内，其它语言包括 C++/Rust/Swift 也都没有解决这个问题。只要让内存分配器和调试器做好配合，该问题不难在开发和测试阶段发现和解决。如果是单纯为了解决这个问题，在运行时增加一个标记清除机制，代价太大了，不符合 Zinc 的定位。当然我不反对实现一个仅在测试阶段使用的堆内存扫描器，结合自动化测试，辅助发现测试用例中的循环引用问题。
* RC 的另外一个缺点是，如果高频率使用原子指令做引用计数的增减，它的执行性能并不好。

但我们可以使用一些优化手段，把执行性能往回拉一点：
1. Zinc 天然鼓励使用值语义类型，在很多时候是不需要动态分配内存的，也具备比较好的对象内存布局控制能力。此事对缓存友好，也可以减少引用计数指针出现的场景。
2. Zinc 保留了 借用指针类型，借用指针类型的拷贝、传参、返回，都是不用修改引用计数的。很多场景使用借用指针比 RC 指针更合理。
3. Zinc 保留了 move 语义，合理使用这个特性，可以大幅减少引用计数的发生频率。
4. Zinc 的 RC 指针是语言内置类型，不是用库模拟出来的。所以编译器有机会在部分场景中通过编译器优化，删除冗余的引用计数增减操作。
5. 用户有机会使用更先进的内存分配器 (如mimalloc) 替代 libc 自带的 malloc/free，提升动态内存分配和释放的执行效率。
6. 利用线程安全语言特性，编译器可以分析出某些 RC 指针及其所有副本，肯定只能在本线程内部使用，因此可以将这些指针对应的引用计数增减操作，翻译成非原子指令。在 Zinc 中，当指针指向的是满足 `Send+Sync` 约束的类型的时候，这个指针才能安全地跨线程使用。如果一个指针指向的是 non-`Send+Sync` 类型，那么我们就可以确信 这个指针及其所有副本 都不可能跨线程使用，这里就有优化机会，使用非原子指令。**这也是为什么把它叫做自动引用计数指针的原因（automatic reference counting），这里的字母 A 代表 Automatic 而不是 Atomic。 “自动” 的主要含义是，编译器自动帮忙选择原子指令还是非原子指令。**

以上区别表明，在其它语言中基于传统的 atomic-rc 实现的引用计数机制，其性能水平结论在 zinc 上并不适用。相比于传统的 atomic-rc，Zinc 具有更好的性能优化潜力。

总而言之，安全、性能、易用是一个不可能三角。
当 Zinc 选择了安全和易用的时候，就注定了无法做到“零开销抽象”，跟C/C++相比一定程度的性能损失是可以接受的。
但我们依然有一系列的优化手段可以保证执行性能不至于特别差。

我个人猜测 Arc 不是 Zinc 的性能瓶颈，泛型实现方案才是。

### 5. 这个项目目标是什么？

Rust 在很多方面的设计都非常好，此事有目共睹。但与此同时，简化 Rust 的学习和使用门槛的呼声也一直不绝于耳。
本人一直觉得，在安全的系统编程语言这个范围内，Rust 的设计方向并不是唯一解，还是有其它的设计空间的。
本项目的目的，就是为了在 “安全的系统编程语言” 这个范围内，探索其它的设计可能性。

但是，如果只是泛泛而谈，我们还可以如何如何设计，是没有人听的。在程序员的圈子里，有一句非常著名的话：
> 
> Talk is cheap, show me your code.
>

所以，我需要一个项目，把所有的想法都真正实现出来，这样才有说服力。

这个项目的核心设计方向是：
**如果保持 Rust 的安全性，牺牲一点执行性能，换取更好的易用性，可能会变成什么样子。**

在此基础上还有几个次要目标：
1. 简化语言特性，反对贪大求全。让不同的语言特性尽可能正交，不要互相影响，语言特性之间可以自由组合使用。尽量不要为语义规则打补丁，设置各种特殊规则。减轻用户思维负担。
2. 简化编译器的实现。Rust 编译器目前已经过于复杂了，没有几个人能完全理解。这种超复杂项目是难以持续进步和演化的。如果一个语言特性实现起来过于复杂，往往意味着语言的使用者很可能也无法完全掌握这个特性，那么我们应该在一开始就避免引入这样的特性。
3. 关注大型项目的编译速度问题，并提供良好的 IDE 提示功能。此事不止是编译器的实现问题，也是语言特性设计问题。
4. 践行编译即服务的理念。编译器不要做成一个黑盒子，而是应该把它本身的各个组件作为公共库公开给社区使用。编译器的各个组件应该具有良好易用的公开 API。这将极大促进周边生态的发展。
5. 基于编译型语言的更好的动态性支持。包括：支持泛型函数作为二进制产物发布，支持泛型函数作为虚函数，支持动态链接库作为二进制发布件，支持ABI稳定，支持动态加载，支持一定程度的运行时反射等能力。这些都是 Rust 不太擅长但 Swift 表现更好的方面。

### 6. Zinc 语言并没有什么特别的创新之处，只是把已有的其它语言的特性重新排列组合了一下而已，有意义吗？

有意义。因为本项目的目的就不是创新，是为了安全与易用。如果这些特性组合最终的结果是让用户感受到了安全、易用、符合需求场景，就足够了。满足用户需求才是我的目标，而不是为了创新而创新。

在系统编程领域，可选的编程语言并不是很丰富。作者认为，依然存在某些场景，我们没有特别合适的编程语言使用。

* C/C++ 非常强大，可是当代码中出现未定义行为的时候，在大规模的代码中找 bug 是极其痛苦的事情。对普通用户来说，绝大部分场景并不需要极致性能，牺牲少许执行性能换取安全性的提升，是这些情况下划算的做法。
* Rust 是很不错的编程语言，可是有些特性设计得过于复杂，编程范式对很多用户不够友好，开发产能低，动态链接库不友好，而且不适合用于需要动态性的场景。
* Swift 也很不错，作为 native 语言具有较好的动态性支持，同时支持二进制兼容性，这都是很好的性质。但它是被苹果公司掌控的，基本只专注于支持苹果的平台。很多场景下，我们想用，但用不了。它也同样存在线程安全问题。
* Zig 作为一门新兴的系统编程语言，还不够成熟。且同样有内存安全、线程安全问题。
* Zinc 则是尽可能吸收 Rust 和 Swift 语言的优点创造出来的。其一，在安全方面向 Rust 看齐，实现了编译时保证内存安全、线程安全；其二，简化了语言特性，降低了使用难度；其三，更好的动态性支持，支持动态链接库的二进制兼容演进。

在工程领域，没有魔法，只有针对不同目标的权衡和取舍罢了。如何找到一个较为常见的使用场景，并设计出满足需求的语言特性，是 Zinc 语言设计的主要挑战。
作者认为 "无GC & 安全性 & 开发易用性" 这种诉求较为常见，且市场上缺乏有足够竞争力的编程语言完全满足需求。
追求 "极致性能"、"zero-cost abstraction" 的场景在真实实践中是非常少的，将性能作为最高优先级的项目，建议使用 C/C++/Rust。
Zinc 语言设计不应该把这类需求作为头等优先级。

如果大家觉得这个设计是有用的，请大家不吝点个赞，或者提出建议，或者创建PR，参与到这门语言的设计和实现中来。

### 7. 在 AI 编程越来越普遍的当下，设计新语言还有价值吗？

个人认为，在 AI 编程时代，Rust 引领的 “内存安全 + 线程安全” 特性，是极具价值的。
毕竟 AI 不会在所有任务上都消耗大量资源去严格证明代码正确性，这时候有个外部工具供它调用，可以很精确地完全避免一类错误，是非常高效合理的做法。这保证了AI生成代码的基本质量。
因此，Zinc 坚持 “内存安全 + 线程安全” 作为所有特性的前提，安全特性是不可放弃的。

在安全性这个前提之下，探寻其它的设计可能性，是对 Rust 的良好补充。
毕竟编程语言的设计目标是多维度的，Rust 选择的设计目标未必适合所有的使用场景。
语言定位这个事情，是无法靠使用者通过 AI 编程弥补的。作者也相信将来会有更多符合 “内存安全 + 线程安全” 的新编程语言出现，这应该是 AI 编程时代的潮流。

### 8. Zinc 语言目前达到了什么状态？

内存管理、线程安全等核心特性已经设计完毕，有了一个基础的标准库。并基于这些基础特性，实现了编译器的自举。

目前的状态可以算是概念验证阶段（proof of concept），只是开了个头，离真正可用还差得远。
很多关键的语言特性，只要不妨碍自举的，都没有实现。以及规划中的性能优化，以及周边工具、标准库完善等等，都还没有做。
后续的继续发展与成熟，工作量还很大，需要借助开源社区的力量才有可能完成。

### 9. 哪些场合比较适合使用 Zinc？准备如何推广？

我觉得一门新语言，如果去抢占已有成熟生态的旧语言的地盘，难度极大。相反，如果能找到一个处于萌芽期的行业，深耕新场景，构建新生态，那么推广难度就相对低多了。
扩增量，而不是抢存量，可以大幅降低推广成本。

有潜力的几个新场景：

1. 智能网联汽车产品
2. 机器人场景
3. IoT设备、嵌入式设备、各种小型智能化设备
4. 人工智能领域

### 10. Zinc 语言选择了哪种开源许可协议？

Zinc 选择了最宽松的 MIT 开源许可协议。因为在目前这个年代，一门不够开放的编程语言无法吸引到足够的社区参与者，是必死无疑的，没有任何意义。
本人希望这个项目不仅是开源的，而且是开放的。我非常愿意听取各位的意见和建议，欢迎各位朋友参与到 Zinc 语言的设计和实现中来。
